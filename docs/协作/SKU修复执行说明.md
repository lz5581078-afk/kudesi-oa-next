# SKU 对照问题修复与受控补齐

代码修复覆盖包装实重与容量分离、中文称重单位、马甲品名、组合品牌、旧命名规则的分类关联、赠品简称、人工变价审核签名、成本预览、分类/场景状态校验、亚克出站重量，以及运费和成本历史精度。

成本采用已确认的旧成本记录口径。来源为 `production_bom` 的记录是构成汇总结果，不能再当额外采购价重复加入构成。原料的系统采购规格与命名规格沿用旧源码的独立语义，不按编码文字隐式拆价。自治地区全称规范化后的有效报价保留，最低售价最后才向上结算到整数分。

## 执行前

- 先部署代码和 `1757000000000-SkuSnapshotPrecision` 结构迁移；CLI 遇到未执行迁移会停止。
- 备份新库和文件目录，检查压缩包完整性并验证备份可读取。旧库只读。
- 只处理指定公司、经迁移账本对应的 SKU 资料。业务快照、报告和备份放私有目录，不提交 Git。
- CLI 不启动出站 worker，不发起流程、不发送通知、不提交聚水潭商品。整个空跑事务回滚。
- 旧环境与新 API 分属宿主机/容器时，在旧环境只读生成限定 SKU 的快照，再由适配器返回快照；正式执行前重新生成并比较来源指纹。不要把旧应用 `.env` 复制到新容器。
- 本工具处理结构字段，不上传商品照片。增量适配器应去掉 `files`，保留现有文件关系；新增附件若有遗漏须在私有报告另列。

## 分阶段空跑与执行

共同参数如下。报告名每次换新，避免覆盖先前证据：

```sh
node apps/api/dist/scripts/repair-legacy-sku.js \
  --source-company <旧公司ID> --company <新公司ID> \
  --actor <新公司管理员ID> --expected-name <公司全称> \
  --adapter <适配器绝对路径> --mode <阶段> \
  --report <私有目录>/<新报告名>.json
```

每阶段先空跑。核对后，加 `--apply --confirm <新库名:新公司ID:旧公司ID> --expected-report <该阶段空跑报告>` 正式执行。后一个阶段必须在前一个阶段完成后重新空跑，不能复用上阶段的报告。

1. `--mode fields`：纠正迁入字段，补马甲名称列表、系统规格、赠品简称和组合品牌，规范 `V01`/`01`，修正纯 OEM 包装分类归属；按实际构成补充重建过行 ID 的 BOM 来源映射。不会重复增加相同构成。人工改过的字段保留并列为冲突。
2. `--mode missing`：只补账本中没有对应对象的相关资料，包括命名规则、单位、基础编码、组合及构成。已有对象不覆盖。空跑有失败时，禁止正式补入。命名规则只按旧分类保存的显式关联映射，不按名称猜测。
3. `--mode verify`：先基础编码、后组合，通过普通验证规则重新核验。任何对象不合格，正式执行整批回滚；有人工冲突或待补资料也不能静默通过。
4. `--mode workflow --warehouse-department <已核对仓库部门ID> --finance-position <已核对财务岗位ID>`：使用统一流程引擎试建并发布，空跑整体回滚。已有人工配置会拒绝覆盖。仓库任一人办理，财务岗位必须恰好匹配一名在职员工。

财务办理岗需要成本查看与组合新增、修改三项权限。只有核对旧办理岗位及旧成本查看能力后，才使用 `--grant-required-finance-permissions` 补齐这三项最小权限；不授管理员、成本编辑或外部同步权限。明确的禁止项仍优先，冲突时发布失败。岗位权限、流程草稿与发布在同一事务内提交，并记审计。

## 验收

- 保留历史编码，不以重生成覆盖人工保存值；新申请按同一主品、马甲、品牌、赠品和规格重放。
- 比较编码、款式编码、名称、简称、规格、重量、构成成本、运费与最低售价；将已确认的成本记录口径、原始单价精度、有效省份匹配差异单列，不伪造“全部数值相同”。
- 验证正常申请、退回重提、人工/商品变价重审、停用场景和平台、无成本权限、重复申请、同构成沿用、批量及失败回滚。
- 正式执行后再次核对数量、来源映射、验证状态和健康检查，确认没有新增外部发送任务。失败保留私有报告和备份，停止后续步骤。

旧 SKU 批量路由仅校验在职员工身份。核对该旧权限口径后，可加 `--restore-legacy-workflow-access`，仅对指定来源公司、迁移账本中的在职账号补回申请中心、我的待办、我发起的三个入口。不会处理新建账号，明确禁止项保留并列入报告；办理人若被明确禁止进入流程则停止发布。入口恢复与发布在同一事务内提交并审计。
