# 旧系统数据迁入新系统：交接说明（给 Codex）

写于 2026-10-26（Claude）。只是动手前的信息汇总，细节以代码为准。旧系统源码只作映射参考，不复用代码。

## 红线（先看）

- 旧生产库**只读**；本地/测试只连隔离的开发库副本；不要把旧库密码写进代码、文档、日志。
- 线上 lc.kudesi.com 的库**已有数据**（首个公司和平台管理员），**禁止自动跑迁移或批量导入**；导入前必须备份并由用户授权（见 `deploy/server/README.md`）。
- 迁移脚本必须：先“试跑”出报告（新增/跳过/冲突各多少），确认后才真写；可重复执行，重复跑不产生重复数据；写入走新系统同一套资源校验（`/api/resources` 的规则），不绕过直接写表。
- 密码、证件号、银行卡、店铺密钥等不要输出明文；不写默认密码。

## 新旧系统关键差异

| 项 | 旧系统 | 新系统 |
|---|---|---|
| 登录账号 | 员工 `login_account`，全局唯一 | `users.account`，**全系统唯一由应用层保证**（库里只是普通索引，同名历史账号登录会被拒）。旧库若有同名账号，迁入前先改名 |
| 登录密码 | 自定 salt+hash | bcrypt。**旧密码无法迁**，迁入后统一走“重置密码”发随机初始密码（`mustChangePassword=true`） |
| 敏感字段加密 | AES-256-GCM，密钥由旧环境密钥派生（`server/core/business-secrets.js`，格式 `iv:tag:密文` 的 base64；还可能用旧版固定密钥 `LEGACY_BUSINESS_SECRET`） | `CryptoService`（AES-256-GCM，密钥来自新环境）。迁入=用旧密钥解密 → 用新密钥重新加密；**需要旧系统的业务密钥**，向用户索取，不要猜 |
| 岗位 | 名称+角色键 | 显式 `positions.workspace_type`（boss/operations/finance/warehouse 等），不要用名称正则判断 |
| 金额 | 元/小数混用 | **整数分**；利润率**整数百万分比**（1% = 1,000,000），公式在 `packages/shared/src/pricing.ts` |
| 公司 | `companies`（含 `company_id` 关联在部门上） | 所有业务表直接带 `company_id`；迁入哪家公司由脚本参数指定，不从数据里读 |
| 资料 | 每种资料一张表+各自页面 | 统一资源框架：`resource_records`（`type`+JSON 字段）、`resource_links`、`resource_files`；类型配置在 `packages/shared/src/resources.ts` / `finance-resources.ts` |
| 附件/图片 | 旧存储 | 七牛（`FilesService`），迁入要上传后改引用 |
| 页面/功能 | 多版本并存（V2/V5/V7 等） | 一个功能一个版本；旧的“版本”只取最终生效的那套规则 |

## 旧库去哪里看

- 表结构：`server/migrations/0001…0010`、`server/org-schema.js`、`server/integration-schema.js`、`server/workflow-task-schema.js`，以及 `server/index.js` 里的 `CREATE TABLE IF NOT EXISTS`（约 37 处，有些表只在那里建）。
- 功能与业务规则调研：`docs/legacy-research/01~04-*.md`（导航组织资料 / 流程中心 / 商品财务成本 / 集成与会话管理）。
- 旧系统里还有一批 `server/scripts/apply-*.js` 是历史“补数据脚本”，说明哪些数据是脚本改过的，不要当成正常增量。

## 建议迁移顺序（有依赖）

1. 公司（目标公司已存在则复用）→ 部门 → 岗位（含权限）→ 员工。员工密码走重置。
2. 资料（店铺、手机号、银行账户、证照、税务、品牌/商标等）：按 `RESOURCE_DEFS` 字段映射；`ref` 类字段要先迁被引用方，再用新 id 回填；跨表引用必须校验属于同一公司。
3. 财务基础资料：销售平台、销售场景、分类（最多 3 级）、品牌、供应商/客户（自动编码 GYS-/KH-）、仓库、费用项目、商品档案、基础编码、组合编码。
4. 数据类：成本表、定价调试、人力成本、快递价格表（有版本和分类树，注意只迁生效版本，历史版本要不要迁先问用户）。
5. 单据与流程：**建议只迁已完结的历史**，进行中的单据在旧系统办完；期初余额用新系统的“期初预付登记”等功能录入，不要伪造单据。
6. 附件、图片最后迁，并回填引用。

## 已有可复用的东西

- 资料导入导出：资源框架自带导入/导出与导入备份（`resource_import_backups`），脚本可复用同一套校验，不要重写。
- 数据工具：`apps/api/src/resources/data-tools.service.ts`（总数据导入、备份）。
- 创建公司/管理员：`apps/api/src/org/company-provisioning.ts`、`apps/api/src/scripts/seed.ts`、`create-platform-admin.ts`。
- 员工创建与账号唯一检查：`OrgAdminService.createStaff`（导入员工请复用，不要直接 insert）。

## 验证清单

- 每类数据：旧库行数 vs 新库行数 vs 跳过/冲突清单三者对得上；金额类对合计；抽样人工核对。
- 迁后在开发库跑 `npm run typecheck`、`npm test`（含真实 MySQL 的 API 测试），再用演示环境登录抽查页面。
- 迁移脚本自身要有测试（映射、幂等、同公司校验、解密再加密）。

## 需要用户提供/决定

1. 旧系统是一家还是多家公司在用；迁到新系统哪家公司。
2. 单据历史迁多久，还是只迁基础资料+期初。
3. 旧库的只读导出文件（不要发连接密码）和旧系统的业务密钥（`server` 环境里的业务加密密钥）。
4. 切换日程：谁在什么时间停旧系统录入、最后一次增量导入的时间。
