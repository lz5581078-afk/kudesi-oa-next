# 实时识别句首时间兼容

用户报告Windows1.7.2实时识别中断。读取正在运行客户端后确认：两个实时房间出现“实时识别连接中断”，普通分段2.0可以出字。随后录像因剩余空间低于原有2GiB保护阈值安全停止；磁盘问题与实时接收线程错误分别处理，未停止或删除用户录像，也未改用户保存位置。

## 已证实的原因

1. OA API进程健康、未重启，真实供应商调用和OA实时代理能返回数据；没有证据支持密钥或额度是本次根因。检查了代理选择，应用对OA域名实际不走环境代理，未修改Clash或系统网络设置。
2. 使用独立目录、SAPI合成录音和仅本机回环的诊断中继，复现实际已交付EXE通过原OA实时桥接接收真实供应商结果的过程。旧代码收到多条结果后不出字，片段state=error，提示与用户一致。
3. Python线程追踪定位在 `RealtimeChannel.receive` 的 `float(utterance['start_time'])`：TypeError，不能转换None。通用异常处理把这个解析错误显示为“连接中断”。
4. 实际供应商第一句有 `definite/end_time/text/words`，但没有句级start_time；words中仍有真实起止时间（本例首词120ms）。旧OA `Number(undefined)`产生NaN，JSON变成null，导致客户端异常。

## 修复

- 只改OA的时间规范化：优先原生句级时间；缺失时使用供应商逐字原生起止时间，不按字数、时长或人工零点插值。
- 保留有效的0ms，拒绝空字符串、布尔、NaN、负数、倒序。临时未确认文字可以等待有效时间；已确认文字和最终结果没有有效原生时间时明确拒绝，不把无效时间推给客户端。
- 实时桥接按final标记选择严格校验，原有公司/员工/额度/协议过滤保留。文件2.0复用同一规范化，保留现有有效句级时间。无新依赖、迁移、密钥、配额或客户端改动。

## 验证

- 新增4个原生时间回归，真实HTTP/WS桥接测试改为缺失句首、具有词级时间的响应，验证恢复40ms且过滤额外字段。
- 候选TS已类型检查、构建。用编译后的原模块仅在诊断进程内加载，未修改线上旧程序；同一个EXE、同一段合成录音、同一真实语音服务通过：首段结束前1句话、首段0片，停止后2句话正确关联唯一视频片段，正常关闭1000，未再出现空值异常。
- 完整常规/MySQL/发布流水线和线上原服务复验结果待补。不使用正常员工JWT做诊断，不签发/冒充员工令牌，不上传用户真实录音。

沿用既有语音功能修复的上线授权，先备份main，再由正式全套验证流程发布。保留用户当前客户端和全部录像。剩余磁盘空间问题已告知用户，需在开始下一次录制前选择有足够空间的录像目录。
