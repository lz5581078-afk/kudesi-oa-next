# 工作台与直播间扫码上下播

分支：feat/live-room-checkin。开发基于 integration，并合入人事补报选择原场次、传统运营担任中控只计提成的现有修改。本轮用户要求“修改好”，未执行生产发布。

## 已实现

- 主播、中控在本人岗位工作台及固定直播间二维码中使用相同场次；二维码可在房间设置打印，二维码不含登录凭证，登录、飞书回调和绑定后保留房间入口，仍按令牌公司和本人身份鉴权。
- 先读取本人排班，无对应排班可以临时开播。提前开播由服务端要求二次确认；以服务端收到确认时的真实时间计时，不采用客户端手填时间。排班快照过期要求重新读取。
- 中控须确认本场信息；另一角色已开播时读取实际场次，可修正账号、店铺、产品和运营后确认本人上播，修正写入审计。每个角色只记录一次本人开播和首次下播时间。
- 下播显示本人实际时长、有效销售额、预估工资、预估提成。传统运营担任中控继续只计提成。聚水潭不可用时允许先记录实际下播，金额显示待核对，并阻止未经完整订单核实的收入审批/发放。
- 第一份报告固定开启30分钟窗口，重复填报不延长。服务端到点立即拒绝其他岗位继续填报；后台每分钟扫描并发起现有场次审核流程。提交失败保留锁定和错误并幂等重试；审批人由已发布流程确定，不硬编码人事、不变更人事权限。
- 审核默认以运营报告为主要依据；无运营报告时可按主播报告审核。改用其他来源须说明原因。只有主播填报也可审核；未实际完成填报的中控不会仅凭排班产生工资、提成。
- 按实际场次时间窗、店铺、平台自动归集聚水潭订单号，保存账号归属、原始订单和退款依据。同店订单去重，跨店同号分别处理，禁止跨场次重复计入。订单失败自动重试，人工填报不会被恢复任务覆盖。
- 结算生成、提交和最终审批前读取最新退款；变化时必须重新生成并核对，失败不当零退款。已在有效销售额中扣除的退款保存基线，只对新增退款再扣提成，保留售后核对依据。

旧场次及人事手工补报保留原模式，不追溯修改历史收入。新增迁移1768000000000，仅改结构；有打卡、锁场或订单快照数据时禁止结构回退。更新切换工具的结构清单以识别新增表。

## 验证

- Node20，类型检查、常规全套测试及全工作区构建。
- 独立本机MySQL8库：整库回归1090项通过；新增退款测试的测试桩类型修正后，直播/退款3组31项重新通过。整库初轮的快递及切换测试5秒超时，30秒时限复查通过，无业务断言失败。
- 专项包含：提前二次确认、排班过期、同场幂等、公司隔离、中控核对修正、首次实际时间、30分钟边界、自动审核失败重试、运营主要依据、主播单人审核、未出勤中控不计薪、订单来源失败恢复、跨场次订单冲突仍可记录下播、新增退款扣减及提交前退款变化拒绝。
- 前端覆盖开播预填、提前确认、中控确认、加入已有场次修正、待核对下播、锁场禁用、公司不符和登录回跳地址约束。
- 390×844本地合成数据页面人工检查：按钮完整可点、无横向溢出。手机截图保存在本机.local-test/live-checkin/mobile-checkout.png；未在真实飞书执行开下播、未写生产业务测试数据。
