# 采购流程（新写）：设计与调整清单

分支 `feat/flow-purchase`，模板 key `purchase-request`（内置模板，名称“采购申请”）。
用户决定：“采购流程旧的本身就不完善，没有运行起来，你可以根据它的情况写个新的出来。”——所以这里不是迁移，不逐条复制旧缺陷，只保留旧功能的用意。
本文最后的“调整清单”是给用户改方案用的：每一项都说明改哪里、改了影响什么。

## 1. 旧系统的用意与缺陷

旧系统采购模板（公司 3，模板 #10）共 16 个节点，顺序：申请 → 方案 → 审批 → 付款 → 预付款复核 → 发货催办 → 到货 → 收货 → 质检 → 异常 → 退款 → 费用 → 结算 → 费用付款 → 关闭（系统）→ 结束。
办理人是写死的员工（财务、老板、出纳各一个）加仓库部门；发起范围是一串角色加三个部门。

旧功能的用意（新方案都保留了）：
1. 采购要有申请理由、商品明细、供应商、期望到货日。
2. 方案由采购定（供应商、单价），金额大要老板批。
3. 付款要登记，要核对；预付款要和后面的费用冲抵。
4. 供应商发货、到货要催办（旧的 `waitingTiming`：先 5 分钟、之后每天催）。
5. 到货要验收、质检；不合格、短少要走异常、退货、退款。
6. 合格的货要入库，并且和财务单据衔接。

旧系统的缺陷（新方案刻意不照搬）：
1. 没有跑起来过：只有 1 条被取消的测试单，时限 60/120/240 分钟是随手填的，没有真实数据验证过。
2. 靠“路由事实”决定下一步走哪条线，配置很难；一个 16 节点的图里有“关闭 → 发货催办”这样的回环，没人说得清什么时候走。
3. 引擎是几套互相重叠的机制，节点类型、分支、自动动作混在一起。
4. 前端用名字判断“当前是哪一步”（15 多个固定名称），改名字页面就坏。
5. 办理人找不到时退回到发起人兜底，等于谁都可以点。
6. 发起范围对 SKU 不校验，申请的商品、供应商没有同公司校验。
7. 数据里 `legacy` 和需求两种模式混用。
8. 成本、单价对所有人可见。
9. 费用、结算、费用付款三个节点把“采购”和“费用报销”混在一起，职责不清。

## 2. 新方案总览

完全走统一流程引擎：线性步骤 + 条件步骤 + 退回到指定步骤。办理人全部用现有的九种办理人来源，岗位类型是显式字段 `positions.workspace_type`，**找不到人或匹配到多人就不允许发起**（不兜底、不回退到发起人）。

### 2.1 步骤、默认办理人、时限

| # | 步骤 | 类型 | 默认办理人建议 | 默认时限 | 条件 |
|---|---|---|---|---|---|
| 1 | 提交采购申请 | 发起 | 发起人 | - | - |
| 2 | 部门审核 | 审批 | 发起人的直属上级 | 1 天 | - |
| 3 | 采购方案（定供应商和单价） | 办理（固定） | 岗位类型“采购” | 2 天 | - |
| 4 | 采购负责人审核 | 审批 | 岗位类型“采购” | 1 天 | - |
| 5 | 财务审核 | 审批 | 岗位类型“财务” | 1 天 | - |
| 6 | 老板审批（大额） | 审批 | 岗位类型“老板” | 1 天 | 方案金额 ≥ 10000 元（1,000,000 分）才走 |
| 7 | 下单与付款登记 | 财务（固定） | 岗位类型“出纳” | 1 天 | - |
| 8 | 到货验收 | 办理（固定） | 岗位类型“仓库” | 14 天；有承诺到货日时按承诺日当天结束 | 可多次，分批到货 |
| 9 | 验收异常处置 | 审批，退回到“到货验收” | 岗位类型“采购” | 1 天 | 验收结果为“有不合格”或“数量短少”才走 |
| 10 | 退款到账确认 | 审批 | 岗位类型“出纳” | 3 天 | 异常处置选“退货退款”或“取消未到货部分”才走 |
| 11 | 入库登记 | 办理（固定） | 岗位类型“仓库” | 1 天 | - |
| 12 | 尾款付款登记 | 审批 | 岗位类型“出纳” | 3 天 | 付款方式为“预付定金”或“货到付款/账期”才走 |
| 13 | 结束 | 结束 | - | - | - |

“默认办理人建议”只是模板自带的建议。**管理员必须在流程设计器里确认每一步的办理人**，设计器改步骤时仍要通过引擎的校验（固定步骤不能删、不能加条件）。
督促（remind）：每个步骤都配了到期前提醒和超时后重复提醒；到货验收的提醒是“到期前 1 天、之后每天”。

### 2.2 字段

发起（申请表）：
- 采购用途（必填，下拉：日常补货/新品备货/活动备货/包装耗材/样品试用/其他）
- 申请理由（必填）
- 采购商品明细（必填，从商品档案选，最多 100 行，数量最多 4 位小数，同一商品不能重复；不能是自制商品）
- 期望到货日期（必填，不能早于今天）
- 关联店铺、关联项目（选填）
- 建议供应商（选填，从供应商档案选，同公司）
- 预计单价（选填，**有“成本查看”权限的人才看得到、填得了**）
- 附件（选填，报价单、图片等）

各步办理表单：
- 采购方案：供应商（必填）、各商品单价（必填，元，最多 6 位小数，即分 4 位小数）、方案金额（系统按数量乘单价算，只读）、报价说明、报价附件。
- 下单与付款：采购订单号、下单日期、承诺到货日、付款方式、付款账户、实付金额、付款日期、付款流水号、付款凭证。预付要全额，定金要大于 0 且小于总额，账期可不付。
- 到货验收：到货日期、物流单号、各商品本次到货数量和合格数量（累计），验收结果由系统按累计结果推出（全部合格/有不合格/数量短少），不让办理人自己选。
- 验收异常处置：处置方式（按合格数量入库、不再补 / 不合格品退回供应商退款 / 取消未到货部分退款）、说明、预计退款、退货物流单号。
- 退款到账确认：实际退款金额、日期、收款账户、流水号、凭证。
- 入库登记：合格数量大于 0 时，要么在“采购摘要”里点“生成采购入库单草稿”，要么写明不生成的原因。
- 尾款付款：付款账户、金额、日期、流水号、凭证。累计付款不能超过批准金额。

### 2.3 流转与异常

- 正常路径：申请 → 部门审核 → 方案 → 采购负责人 → 财务 → （大额时老板）→ 下单付款 → 到货验收 → 入库登记 → （定金/账期时尾款付款）→ 结束。
- 退回：每个审批步骤可以退回；退回到申请人修改后重新提交，重新走审核。已经付款后不能退回到付款前；已经生成入库单草稿后不能退回到入库前（要先处理草稿）。
- 撤回：没有人办理过的申请，发起人可以撤回。
- 转办、会签：沿用引擎已有能力（转办按原规则；部门办理人可设为“全员会签”，设计器里选）。
- 分批到货与“循环”：验收后如果有短少/不合格，走“验收异常处置”；如果选择继续等货，就用“退回到到货验收”，到货数量累计，累计合格数量不能超过申请数量。
- 收尾：已付款或已有到货后，不能直接“废除”流程；只能走异常处置（取消未到货部分、退货退款）并登记退款到账，再入库、结束。
- 采购退货与不合格品：异常处置 + 退款到账确认这一条线就是旧系统“质检 → 异常 → 退款”的用意，入库单草稿只带合格数量。
- 超期提醒：到货验收按承诺到货日（没填就按期望到货日）当天结束计时，到期前 1 天提醒，超期后每天提醒；其余步骤按分钟时限。

## 3. 金额与成本脱敏

- 金额都是整数分；单价是分，最多 4 位小数，计算走 `packages/shared/src/unit-price.ts`（数量乘单价后才结算到分，各行相加）。
- 方案金额由服务端按“数量 × 单价”算，办理人不能直接填。条件分支读它判断是否走老板。
- 价格、金额、付款字段（预计单价、各商品单价、方案金额、实付、退款金额）在表单定义里带 `permission: 'product.cost.view'`。没有该权限的人：
  - 模板目录里没有这些字段；
  - 流程详情里 payload、步骤表单、字段定义、我的可填字段都没有这些值；
  - 提交时带来的这些字段被丢弃；
  - 退回重提时，看不到这些字段的人不会把原值清掉；
  - 采购摘要接口不返回单价、金额、付款。
  这是服务端强制的，不是前端隐藏。
- 因此，**采购方案、采购负责人、财务、老板、出纳、需要看金额的人都要有 `product.cost.view`**。没有该权限的采购员办理方案时会被明确拒绝（提示需要成本查看权限），不会静默失败。

## 4. 与制单中心衔接

- 验收后，入库登记步骤的办理人（仓库）在流程详情的“采购摘要”里选仓库，点“生成采购入库单草稿”。这要同时满足：当前正停在入库登记步骤、自己有这一步的待办、拥有新权限 `flow.purchase.inbound-draft`。
- 草稿通过现有的 `FinanceDocumentsService.createDraft` 生成（类型 `purchase-in`，往来方为供应商，行数量为累计合格数量），**只生成草稿，不过账、不自动记账、不写分录**，会计科目由制单中心现有规则和有权限的人处理。
- 幂等：同一个流程只能生成一次（`sourceKey = flow-purchase:{流程号}:inbound`，同时记在流程里），重复点击返回同一张。草稿备注里写明实付金额和“草稿未提交、未过账”。
- 引擎没有“自动节点”，所以这是入库登记步骤上的手动按钮，流程事件里记一条“生成入库单草稿”。
- 外部系统（聚水潭）全程只读，本流程不写任何外部系统。

## 5. 引擎改动（最小、向后兼容）

1. 表单字段的 `permission` 在流程里生效（上面第 3 节），没有声明 `permission` 的字段（SKU、专属品、直播、售后、费用等）完全不变。
2. 新增事件动作 `draft`（生成入库单草稿）。
3. 流程附件：`/files/upload` 新增 `flow:<模板 key>` 类型，只允许内置模板里声明的 `files` 字段；未绑定时只有上传人能看，绑定到流程后按流程可见性（总览权限、发起人、各步办理人/收件人、抄送人）。
4. 流程详情额外返回 `files`（文件号 → 名称、类型、大小）。
5. 没有新增迁移。

没有动其他流程的适配器与步骤定义；SKU、专属品、直播、售后、费用等流程的数据库测试全部重新跑过（见测试结果）。

## 6. 权限键

- 新增：`flow.purchase.inbound-draft`（采购流程：在入库登记时生成采购入库单草稿），定义在 `packages/shared/src/navigation.ts` 的 `SPECIAL_PERMISSIONS`，并列入权限目录。
- 复用：`flow.apply.view`（商品选择接口）、`product.cost.view`（成本字段）、`finance.docs.create`（由适配器内部用引擎身份创建草稿，不要求办理人自己有；但必须有上面那个新权限）。
- 采购摘要接口 `GET /api/flow/purchase/runs/:id/summary` 只要登录，但先走流程详情的可见性检查，看不到流程的人拿不到。

## 7. 没做的和原因

1. **自动节点、条件循环、命令重试、变更/终止收尾节点**：引擎没有这些能力，按“尽量用现有能力”的原则没有为本流程扩引擎。分批到货用“退回到到货验收 + 累计验收”实现；终止用异常处置收尾；生成草稿用手动按钮。如要真正的自动节点，需要引擎单独立项（属于 feat/flow-gaps 的范围）。
2. **自动过账、预付款冲抵登记**：没有，草稿只入库；预付款核销交给制单中心后续单据。需要的话要先和财务确认科目规则。
3. **运费、杂费分摊到成本**：没有做，草稿按合格数量带入，不分摊。
4. **飞书通知**：只有 SKU 流程接了飞书；采购流程只用引擎的站内待办和督促提醒。
5. **发起范围（谁可以发起）**：属于并行任务 feat/flow-gaps（发起人范围），本分支没做，合并后在设计器里设。
6. **退款回单类单据**：只登记退款确认，不生成收款/退款单据。
7. **供应商一直不发货的自动催办**：只有督促提醒，没有自动联系供应商。
8. **旧系统“费用、结算、费用付款”三个节点**：不放在采购流程里，费用走费用模块。

## 8. 上线后管理员要做的事

1. 在流程设计器打开“采购申请”，逐步确认办理人：
   - 部门审核按发起人上级；
   - 方案、采购负责人审核、异常处置：岗位类型“采购”；
   - 财务审核：岗位类型“财务”；
   - 老板审批：岗位类型“老板”；
   - 下单付款、退款确认、尾款：岗位类型“出纳”；
   - 到货验收、入库登记：岗位类型“仓库”。
   每个类型必须只对应一个人（或改成指定员工/职责组），否则发起会被拦住并提示。
2. 给采购方案、采购负责人、财务、老板、出纳授予 `product.cost.view`。
3. 给仓库人员授予 `flow.purchase.inbound-draft`，并确认制单中心的采购入库单规则、仓库档案。
4. 按公司实际改“大额”门槛（老板审批步骤的条件，默认 1,000,000 分 = 1 万元）和各步骤时限。
5. 发布新版本（启用），新申请才会用新配置。

## 9. 调整清单（用户可按需改）

| 想改什么 | 在哪里改 | 影响 |
|---|---|---|
| 大额门槛 | 设计器 → 老板审批步骤 → 条件（字段 `form.plan.amountCents`） | 只影响新发起的申请 |
| 谁来批、谁来办 | 设计器 → 各步骤的办理人 | 必须唯一匹配，不兜底 |
| 时限、督促 | 设计器 → 各步骤时限与提醒 | 到货验收的承诺日规则在 `apps/api/src/flow/purchase.ts` 的 `stepDueAt` |
| 付款方式 | `packages/shared/src/purchase.ts` 的 `PAYMENT_MODES` | 同步改下单、尾款条件 |
| 用途下拉 | `PURCHASE_PURPOSES` | 只影响新申请 |
| 是否要求财务审核 / 采购负责人审核 | 设计器 → 删除对应非固定步骤 | 固定步骤（方案、下单、验收、入库）不能删 |
| 是否必须生成草稿 | 入库登记步骤校验在 `purchase.ts` 的 `beforePass('inbound')` | 现在要“草稿或写明原因” |
| 谁能生成草稿 | 权限 `flow.purchase.inbound-draft` | 另外还得是入库登记的待办人 |
| 谁能看单价 | 权限 `product.cost.view` | 服务端强制 |
| 要不要自动节点 | 需引擎单独立项 | 见第 7 节第 1 项 |
