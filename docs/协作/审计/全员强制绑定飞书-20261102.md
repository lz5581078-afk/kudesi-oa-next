# 全员强制绑定飞书

用户明确要求：取消稍后绑定；所有未绑定飞书的员工，登录系统都必须完成本人企业飞书绑定。作为本次已授权上线的扫码入职和飞书绑定功能后续，验证后继续发布。

## 规则

- 统一覆盖所有公司员工：人事手工建立的旧账号、通用码及岗位码员工、公司管理员，均不豁免。不再按岗位入职审计或通知标记判断是否需要绑定。
- 有效绑定必须同时匹配登录员工、所属公司、公司当前飞书主应用和租户。已有正确绑定的员工不重复授权，旧绑定的全通知标记为0也有效；其他公司/应用/租户的绑定不能冒充当前绑定。
- 平台管理员沿用独立平台账号和平台后台，不属于公司员工；平台令牌仍不能访问公司业务接口。
- 本次没有数据库迁移，不修改既有已执行迁移，不批量回填或改写员工绑定。

## 服务端限制

- 新增必需依赖 `FeishuBindingPolicy`，由登录返回、会话恢复和全局JWT守卫共用。业务接口每次读取当前有效绑定，配置缺失/解密失败不会放行业务。
- 未绑定登录仍得到可完成绑定的登录状态，但不能读写业务数据。业务访问返回403及 `FEISHU_BINDING_REQUIRED`；不靠客户端状态或JWT里的绑定声明放行，原有旧令牌也受限制。
- 绑定前仅允许本人信息、本人密码修改和飞书绑定状态/发起/完成等账号流程；其他 `AuthenticatedOnly` 业务接口也必须绑定。公共登录/健康等公共能力及独立机器令牌流程保持原有鉴权。
- 复用一次性state、浏览器Cookie、企业身份及一对一冲突校验。所有员工新完成飞书绑定后打开其本人OA新通知标记，沿用既有出站队列和公司发送开关。
- 采集器HTTP与WebSocket继续经过同一个JWT守卫，未绑定也不能借采集器绕过限制。

## 网页与手机

- 移除“稍后绑定”和旧暂缓缓存逻辑。所有未绑定员工登录/恢复后停留在绑定页，业务导航不加载；直接打开工作台、资料或账号地址同样不能跳过。
- 取消授权、冲突、未配置或网络失败，只提供重试和退出登录。没有“进入OA”或账号设置的未绑定通行入口；手机和电脑同规则。
- 已进入系统的旧页面收到服务器绑定拦截时，会切回强制绑定状态，保留用于完成绑定的登录令牌；普通权限403不触发此行为。
- 绑定回调在刷新员工身份前后保持同一个页面，避免绑定成功后状态刷新重建页面而丢失授权结果。成功确认后才可进入OA；通知总开关关闭与绑定是否完成分别判断。
- 初始密码修改不会成为绕过绑定的业务通道；完成绑定后原初始改密要求继续有效。
