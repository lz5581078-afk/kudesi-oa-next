# UI 审计：直播管理（u9）

范围：旧系统「功能 › 直播管理」整套（旧前端 `src/live/` 10 个文件、旧后端 `server/modules/live/` 12 个文件、旧表 `live_*`）。新系统此前没有任何直播功能，所以本次是新建。
规则依据：旧系统直播管理规格文档与旧后端代码；旧测试用例已移植为新测试。不复制旧代码，只复刻功能和业务规则。
符号：✓ 已对齐　✗ 缺失　≠ 有意不同（原因写在备注里）。

## 一、旧功能清单

### A. 角色与权限（旧 access.js、navigation-state.js）
1. 管理员/老板、人事部门人员：排场、改提成规则、生成月结、看全部场次与提成。（按部门名称含「人事」判断）
2. 直播部门主管（直播部门内「主管」层级岗位，按部门名含「直播」判断）：看全览、排场、场次记录，提成只看本人。
3. 主播、中控（岗位工作台模板为主播/中控工作台）：只在工作台办理本人场次，看本人提成。
4. 运营岗位可以以中控资格报上播、报下播，提成按中控计算，登录后仍进运营工作台。
5. `visibleForLive`：主播、中控账号的左侧菜单只剩自己的主播/中控工作台和任务中心。
6. 场次可见：有查看权限，或本人是该场主播、中控、运营、上播人，或是审核流程的办理人。

### B. 全览图（LiveOverview）
7. 西走廊平面：南侧一排、走廊、北侧一排，名字没有南/北的放走廊尽头；大房间双倍宽度。
8. 每个直播间一块：状态（正在直播/今日已结束/未开播）、正在直播的开播时间/已播时长/计划结束/主播/运营/中控/抖音号；未开播显示下一场；时间条（06:00–次日 02:00，含「现在」线）；最多 3 条当天排场摘要。
9. 日期选择、统计（几间正在直播/几个直播间/几场排场/几场待审核）、筛选（全部/正在直播/过时未上播）、手动刷新、页面可见时每 30 秒自动刷新、切回页面立即刷新。
10. 点房间：当天详情（排场列表、实际直播列表、过时未上播提醒），可进场次详情。
11. 没有直播间时的引导（在资料「西走廊办公室」下加名称含「直播间」的房间）。

### C. 排场（LiveSchedules）
12. 今天及未来 7 天，按天签 + 按房间分块；显示已取消开关；每场显示时间、主播/中控/运营、抖音号/店铺/备注、状态（未开始/直播中/已播/已取消/已到时间未上播/已过时未上播）。
13. 新增/修改/取消（原因必填）排场；已上播、已结束、已取消的不能改。
14. 校验：日期范围、开始结束时间（结束早于开始＝跨日）、单场最长 16 小时、房间必须是直播间、主播必须是主播岗位、中控必须是中控岗位、运营必须是在职员工、抖音号必须是抖音平台账号、店铺必须是抖音店铺；同一房间时间段不重叠、同一主播不能同时在两个房间（相邻不算重叠）。
15. 排班通知：保存/调整/取消后通知相关人员；开播前 30 分钟提醒；被移出排场的人收到「已不再参与」。（旧版走飞书队列）

### D. 报上播、报下播、提交审核（LiveWorkspace + routes.js）
16. 报上播：从排场带出（排场开始前 2 小时到结束前可上播）或临时加场；必须选抖音号、抖音店铺（店铺要有唯一聚水潭店铺绑定）、至少 1 个在卖产品（≤100）；上播时间不能晚于现在 5 分钟、不能早于 12 小时前；同一直播间/同一主播同时只能有一场「直播中」；所在月份已进入结算审批或已结算不能新建场次。
17. 报下播：只能本人填报自己的角色（主播报主播、中控报中控；兼任中控的运营报中控；运营可选填运营报告）。主播填销售额；中控填销售额和投流费用；主播/中控必须从聚水潭勾选本场订单（金额与付款时间以服务端重查为准）；查不到订单不能报下播；下播时间必须晚于上播、不能晚于现在 5 分钟。场次下播时间以主播所报为准。
18. 提交审核：主播和中控（有中控时）必须各自本人报过下播；本场主播、中控或管理人员可提交；已提交需审核人退回才能改。
19. 退回后可修改并重新提交；被拒绝或撤回时场次回到「已退回」并解除与该次流程的关联。
20. 预估提成：随输入防抖刷新；只向本人展示本人角色，全员权限者看全部，已审核场次只显示保存的快照。
21. 主播工作台：进行中的场次、待审核、本周排场（可直接上播）、本月提成与工资合计、最近 20 场。
22. 工作台历史（LiveHistory）：按月/起止日期/全部查看本人场次，分页；汇总（累计/本月/上月：场次、时长、提成、工资、工资时长）。

### E. 审核（review.js + LiveReviewDialog）
23. 一场一张审核单，走流程中心「直播场次审核」，审批人在流程里配置，不写死。
24. 审核人选最终销售额来源：主播所报/中控所报/主播订单合计/中控订单合计/手填（手填必须写原因）；所选来源缺失或没有勾选订单时拒绝。
25. 运营人员在审核时由人事最终确认：沿用排场的、改人、或「本场没有运营」；运营不能同时是主播；运营兼任中控时不另算运营提成。
26. 主播工资（按小时）：默认取场次上下播时间与兼职档案的计时时薪，审核时可改时间/时薪/说明，试算由服务端算；时薪必填（档案没有计时时薪时必须手填）。
27. 通过：同一事务写主播/中控/运营提成记录（含规则版本快照）、主播工资记录，场次改为已审核；所在月份已结算审批则拒绝。
28. 退回（场次回到已退回并记原因）、拒绝/撤回（场次回到已退回并解除流程关联）。

### F. 提成与工资（commission.js、wage.js、LiveRecords）
29. 规则版本：只追加，生效日期当天起适用于场次日期；同一生效日期不能建两个版本；规则含档位（含下限/含上限）、投产阈值、不足时主播/中控扣减点数、运营固定比例；规则编辑器带试算。
30. 计算：见 `packages/shared/src/live.ts` 的 `liveComputeCommission`，与旧公式逐项对照并移植旧测试用例。
31. 场次记录：筛选（日期/直播间/主播/中控/状态，记住本机筛选）、分页、点开详情；可导出。
32. 提成记录：按月，汇总到人+角色，明细；有全员权限看全部，其他人只看本人；可导出 CSV。
33. 主播工资记录：按月汇总和明细，同上权限；可导出。

### G. 月底结算（settlement.js、LiveSettlement）
34. 人事按月生成结算单：所有场次必须已审核；每条提成按本场保存的订单只读核对聚水潭退款；扣减 = 退款 × 原比例（不超过原提成）；正销售额但没有保存订单的历史场次拒绝；任一店铺查不到退款就不生成。
35. 重新核对（待提交/已退回可以）；提交走流程中心「直播提成月结审批」；审批人通过后锁定，只能在月份结束后通过；退回后可重新核对再提交；撤回/拒绝回到已退回。
36. 页面：月份选择（月初 10 天默认上月）、合计、按人员、明细（点行看场次）、退款依据、历史结算、导出 CSV。

## 二、新实现方案

| 旧做法 | 新做法 |
|---|---|
| 员工表、岗位模板键、部门名称含「人事/直播」判断角色 | 员工就是 `users`。主播/中控靠显式岗位类型 `positions.workspace_type`（新增 `live_anchor`、`live_control`；运营沿用 `operations`），**不按名称猜**；管理/查看靠权限键 |
| 人事=管理、直播主管=查看 | 页面权限 `features.live.view`（看全览/场次/规则）、`live.manage`（排场、改规则、生成月结、提交审批）、`live.commissions.view`（看全员提成、工资、月结）；`features.live-desk.view`（我的直播：报上播/下播/提交/本人提成）。给岗位勾选即可，不写死部门 |
| `visibleForLive` 只剩工作台和任务中心 | 菜单本来就按权限过滤：主播/中控岗位模板只授予「我的直播」+工作台/任务页面权限，其余页面自然不出现；不再写专门的菜单过滤 |
| 流程中心「直播场次审核」「直播提成月结审批」，节点处理器 | 统一流程引擎两个新模板 `live-session-review`、`live-settlement`（办理人由管理员在「流程配置」里配置并发布，未发布则提示不能提交）；业务页面发起（`entry`，不出现在申请中心）；引擎只加三个可选钩子（退回、可重新提交人、结束），不认识直播 |
| 金额 DECIMAL(元)、比例 DECIMAL | 全部整数分；比例用「百分数×100」整数（3.5% = 350）；投产 ×10000 整数；公式在 `shared/live.ts`，前后端共用 |
| 房间来自 company_locations | 来自资料「房间与档案位置」：名为「西走廊办公室」下，名称含「直播间」的启用房间（分侧、大房间规则照旧） |
| 抖音号来自 self_media_accounts、店铺来自 stores、产品来自商品基础编码 | 来自新资料 `self-media`（平台=抖音）、`stores`（平台=抖音，新增字段「聚水潭店铺编号」）、`finance-base-codes`（只返回编码、名称、规格，不返回成本） |
| 聚水潭订单/退款只读查询 | 注入接口 `LiveOrderSource`：默认「未接入」（报下播会明确提示原因），测试用假实现；**真实聚水潭读取客户端未授权，不实现**；任何写入没有 |
| 飞书排班通知 | 站内通知（飞书未接入）；开播前 30 分钟提醒由定时任务扫描 |
| 兼职档案时薪 | 员工的 `payType=hourly` 且 `hourlyRate>0` 才作默认时薪（`liveArchiveHourlyRate`） |
| 初始规则由迁移种入 | 迁移只建表；默认规则在公司开通（provisioning）和种子脚本里写入，规则从 2026-01-01 起生效 |

数据表（迁移 1749000000000，全部带 company_id）：`live_schedules`、`live_sessions`（直播中唯一键：同房间/同主播同一时刻只有一场）、`live_session_products`、`live_session_reports`、`live_session_orders`、`live_commission_rule_versions`、`live_commission_records`、`live_wage_records`、`live_settlements`、`live_settlement_lines`、`live_settlement_refunds`。

页面（导航新增一级「功能」分区，图标新增 `live`）：
- 我的直播（`/features/live-desk`）：开播、进行中场次、报下播、提交审核、本周排场、本月提成与工资、历史。
- 直播管理（`/features/live`）：全览图、排场、场次记录、待审核、提成记录、主播工资、提成结算、提成规则（页面内标签，按权限显示）。

### 3.3 缺口与不做项
- 聚水潭订单/退款只读客户端：外部系统读取未授权，只留 `LiveOrderSource` 接口位和“未接入”默认实现；授权后只需新增一个实现并在 `AppModule` 替换。
- 飞书排班通知：飞书未接入，改站内通知。
- 旧系统死代码：无单独列出的死代码（旧演示数据模式不迁移）。
