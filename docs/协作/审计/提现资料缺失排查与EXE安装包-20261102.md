# 提现资料缺失排查与 EXE 安装包

2026-11-02 用户要求做成安装包，并查清以前填写的提现资料为什么没有显示；用户进一步确认，原资料填写在旧版 oa.kudesi.com。本轮没有授权发布或写生产数据。

## 排查结论

已在当前正式界面以山东优冠管理员身份只读核对：`财务→店铺提现`，登录态“全部”、负责电脑“全部电脑”、无搜索条件；显示0家店铺、0台授权电脑，没有接口错误提示。旧站重新载入显示“旧系统已停止写入，资料完整保留；未覆盖内容保留后补”。未点登录店铺、提现或其他写入动作。

根因是**旧提现会话数据没有迁入新版业务表**，不是列表筛选隐藏，也不是新助手删除资料：

- 旧程序 `server/modules/session-manager/store-credential-service.js` 从 `session_managed_shops` 读取 `withdrawal_login_account`、`withdrawal_login_password`，按公司/工作区/店铺隔离；工作区来自 `session_workspaces`，设备来自 `session_devices`。
- 新程序 `SessionService.overview()` 读取新库 `session_shops`，工作区为 `finance_withdrawal`；字段名及加密结构不同。店铺档案迁入并不会自动生成这些提现登录记录。
- 当前 `scripts/migration/legacy-adapter.cjs` 的读取/映射和 `source-row-catalog.cjs` 没有旧 `session_managed_shops` / `session_devices` / `session_workspaces`。`source-coverage.cjs` 将非空未读取表计入 `source-table.unmapped`，并非按成功业务表处理；不存在此组资料的新旧字段转入逻辑。
- 私有迁移盘点 `source-inventory.json`（2026-10-31快照，仅读取表名/计数元数据，没有查看账号密码）：旧公司3的 `session_managed_shops` 271行、`session_devices` 8行；工作区表全库4行，其中旧公司3为2行。271行包含不同工作区，不能称271家提现店铺，也不能作为今天旧库的实时行数。
- 既有正式切换审计《全公司重新迁移-20261031.md》末节记录：旧公司3→新公司1，按用户当时核定范围先切换，仍有71张未覆盖旧表保留后补；旧库、程序配置和附件保留。服务器私有最终封存目录 `/www/private-migrations/full-remigration-final-20261101`。本轮没有读取原始备份或登录旧生产数据库，不能声称逐条核验当前账号内容完整性。

正确后续处理是专项补迁这组资料，不能清空新库、重跑全公司导入或让用户重复录入：从服务器冻结快照按公司与 `workspace_key` 精确筛选，利用已有迁移账本映射店铺ID，将账号及旧密码在服务器内解密后用新加密服务重加密；先预览数量与冲突，原记录及新站已有编辑不覆盖。旧设备认证令牌和电脑浏览器Cookie不直接恢复为新站授权，需新助手重新绑定；不得重放旧登录/远程/提现任务。该补迁尚未实施，须另行核定并验证后写入。

## 安装程序 1.2.1

新增独立编写的 NSIS 中文 `.exe` 安装向导，非旧代码复制。包含现有助手程序和绑定窗口，自动准备运行环境；联网安装，需要Chrome/Edge及访问OA、Node官网、npm仓库。以当前Windows用户安装，无管理员提升。

- 运行 `npm run pack:exe -w @kudesi/agent` 生成 `apps/agent/release/KudesiAssistant-Setup-1.2.1.exe`。
- NSIS编译器来自官方社区包：Homebrew `makensis` / Windows Chocolatey `nsis`。
- 取消绑定或安装失败返回非零，不登记安装成功。成功后提供桌面、托盘入口及Windows已安装应用的卸载项；卸载默认保留本机店铺Profile。
- 仅程序、模板进入EXE，无账号密码、设备令牌或Profile；本轮没有给负责电脑绑定、升级或实际提现。
- 新增 `/S /VALIDATEONLY`，只解压临时程序并初始化两个窗口，不安装运行环境、不绑定、不写卸载注册或本机身份，用于Windows原生冒烟检查。
- 编译产物未做代码签名。不指导绕过Windows安全警告，企业电脑策略按公司管理员规范处理。

## 完整检查中发现的既有缺口

Windows EXE原生编译及 `/S /VALIDATEONLY` 已通过。常规回归中的资源页Esc测试出现一次时序失败，单项17项及重跑常规通过；随后全量API暴露录音文件票据的篡改拒绝用例偶发失败。定位为Buffer宽松Base64解析接受密文尾部额外字符，使伪造包装可能继续调用供应商；不是密码/公司校验被绕过。限定在CollectorFileService.decode中检查外层Base64URL、UTF8及内部密文Base64的规范形式，保留AES-GCM和现有正常票据格式；增加尾部换行、非法字符、多段的确定性拒绝回归。未修改通用加密服务、数据库或提现资料。

该入口修正后，本地类型检查、常规全套（shared354/API327/web953/agent75）和独立临时MySQL全量169套1051项通过，新增确定性拒绝校验7项专项通过。最终交付EXE取自通过Windows原生冒烟的Actions产物，SHA256 `cb71e7eafd51c7a1fede289da69af632891bb1217f1a00d1e4571b01b89b6e58`。完整PR云端结果以最新提交检查为准。
