# 岗位入职绑定飞书与通知

用户要求：通过岗位专属二维码入职后，将本人飞书与新建 OA 账号绑定，后续有 OA 通知可以推送到该员工飞书。本次作为已上线扫码入职功能的后续完善，按原上线指令继续验证与发布。

## 行为

- 员工仍只填姓名、手机号、登录密码，岗位由邀请令牌固定。登录成功后自动进入本人企业飞书授权，复用既有 HTTPS 回调 `/feishu-bind`，无需增加飞书应用的回调地址。
- 岗位入职来源由服务端原始入职审计记录判定，登录及恢复会话返回绑定待完成标记。已在上次版本通过岗位码加入的员工，也会在下次登录得到引导，不靠前端缓存判断员工来源。
- 员工使用自己的企业飞书确认身份。服务端校验 JWT 员工、浏览器状态 Cookie、一次性 state、过期时间、飞书 app/tenant 及一对一绑定；不按姓名或手机号猜测飞书身份，不能覆盖其他员工的绑定。
- 岗位入职人员授权成功后，在该飞书绑定上开启 OA 通知标记。通用码和原有普通员工绑定沿用原通知范围，不批量修改其他员工授权。
- 未配置、取消授权、绑定冲突、网络失败时，保留已经建立的 OA 账号；可以重试或先进入 OA。暂缓只对应当前公司/员工，之后可在账号设置继续绑定。绑定完成后的状态刷新失败不会误报为绑定失败。
- 成功绑定后刷新 OA 身份；公司通知开关开启时返回本人岗位首页，开关关闭时明确显示绑定成功及尚未开启发送的原因。

## 通知

- 所有生产站内通知写入点统一调用 `writeNotification`：流程待办/结果/抄送/退回、SKU及批量汇总、任务、工作台个人任务、催办、监督异常/升级、超时、直播排班等。
- 新员工完成上述飞书绑定后，只复制今后实际产生的本人 OA 通知。通知和飞书出站任务在同一业务事务中写入，业务回滚同时撤销两者；独立调用会建立事务。不会在通知生成期间直接调用飞书网络接口。
- 发送继续使用现有飞书唯一 worker、公司开关、公司配置、人员绑定及身份校验。关闭时不入队，统一链路不扫描历史通知来补发；既有出站任务按原队列规则处理。没有自动打开公司通知开关或群发测试消息。
- 普通 OA 通知使用 notice 通道，没有单独配置该通道时使用公司主应用；显式关闭的通道仍然关闭，直播和流程保留其通道设置。
- 同一个通知使用通知ID幂等；原流程/直播场景沿用原业务版本幂等键，已统一推送的员工不再走旧模板重复入队。直播排班调整取消原待发通知的逻辑保留；结果未知不自动重发的既有行为保留。
- 飞书身份只在服务端使用，页面只返回绑定/开关状态。应用需已启用且员工在飞书应用允许范围内；不以 OA 岗位权限替代飞书授权。授权方式参见[飞书官方说明](https://open.feishu.cn/document/client-docs/build-login-free-system-)。
