# 排班开始10分钟仍未上播通知

用户追加要求：直播间排班开始10分钟后仍无人上播，也通知人事部门和总经办。沿用已上线开播偏差提醒的同公司部门成员识别，覆盖有效主岗/兼岗及启用子部门；继承直播通知开关、站内通知、飞书绑定与出站/通道开关。本次仅开发，未部署，不发送真实测试消息。

在原每分钟扫描中增加提醒，10分整即达到条件，9分59秒不触发。以排场计划开始时间计算；仅处理原扫描范围内仍为scheduled、未关联session_id且不存在任何已关联场次的排场。消息包含房间、排班主播/中控/运营、完整计划开始时间和核对时间。不能直接判断平台真实开播，故消息明确为“仍未登记上播”。

按公司/排场/排场通知版本/员工去重，重复扫描不重复通知；改期后按新版本和新时间重算。飞书发送前重新检查当前时间、版本、排场状态、已开播记录及收件人部门资格，已开播/取消/改期或调离人员的旧队列失效。记录和出站与扫描事务一起提交/回滚。保留原先5分钟催本场人员、30分钟升级房间管理员的逻辑。无数据库迁移、UI或权限变更，不开启任何现有关闭的开关。

采用现有扫描的启用时间及两天范围限制，沿用调度频率，每分钟检查一次；实际发送还遵循现有飞书队列处理和配置。

验证：独立依赖后的类型检查、隔离MySQL177套1096项通过。新增数据库测试覆盖10分钟边界、重复扫描、改期重算、开播/取消、异常遗留状态已有场次、公司隔离、事务回滚、飞书入队、调离和开关关闭。最初按工作树脚本复用node_modules时，共享包符号链接仍指向旧工作目录，导致已有扫码直播字段枚举测试失败；改用本工作树独立npm ci并重新构建共享包后完整通过，未修改其他任务代码。
