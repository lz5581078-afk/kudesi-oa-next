## 1. 时限与督促（编号 1）

**旧版**：`workflow_template_nodes.due_hours` 虽然叫 hours，实际单位是**分钟**（`node-timing.js`），SKU 仓库、财务节点真实配置是 60 分钟；督促 `defaultSkuTiming` 是提前 20、10 分钟各提醒一次，超时后每 5 分钟一次。

**新版问题**：内置 SKU 模板的 `dueMinutes` 写成了 3600（按小时思路填的，实际变成 60 小时），且没有督促。

**现在**：
- `packages/shared/src/flow.ts`：`SKU_DUE_MINUTES = 60`、`SKU_REMIND = { beforeMinutes: [20, 10], overdueEveryMinutes: 5 }`，SKU 的 `warehouse`、`review` 和专属品的 `approve` 都用它们。
- 节点面板（`NodeEditor`）本来就能改“处理时限”和“督促时效”（首次提前、再次提前、超时间隔），内置节点也能改（只有没有编辑权限才禁用）。补了前端测试覆盖这三项编辑和只读状态。
- 三级超时链路确认：**节点 > 流程 > 公司**。节点的时限在 `StepDef.dueMinutes`；节点级超时与处罚策略在“超时与处罚”页签按节点覆盖；没有节点覆盖用流程级；再没有用公司默认。单位处处是分钟，进入步骤时 `dueAt = 现在 + dueMinutes × 60 秒`。

## 2. 发起人范围（编号 2）

**旧版**（`start-access.js`）：模板配置里的 `starterSources`，来源有 员工 / 角色 / 岗位 / 职责组 / 部门，**命中任一项即可发起**；公司管理员永远可以发起；部门是精确匹配。采购、专属品在旧库里真实配置过。

**新版**：
- 共享层 `packages/shared/src/flow-starter.ts`：`StarterScope { users, departments, positions, positionTypes, dutyGroups }`。“角色”落到**岗位类型**（`positions.workspace_type`，不用名称判断）。`normalizeStarterScope` 去重、每项最多 200、编号必须是正整数、岗位类型必须是已知类型；`starterScopeAllows` 做匹配。
- **默认语义**：范围为空 = 不限制（沿用“有申请中心权限即可发起”），所以上线不会让任何现有流程突然没人能发。范围一旦配置，只有命中的人能发起，公司管理员始终可以。
- **服务端拒绝**（默认拒绝）：`FlowService.start()` 取发起人的部门/岗位/岗位类型/职责组（只信令牌里的用户，从库里查，不读请求），不在范围内返回 403“你不在这条流程的发起人范围内”。
- **入口隐藏**：`/flow/templates` 返回每个模板的 `startable`，申请中心不显示不可发起的模板。
- **随版本保存**：`flow_definitions.starter_scope`（JSON）跟流程版本一起，保存草稿、发布后生效；在办的流程不受影响。保存时校验引用的部门/岗位/员工/职责组属于本公司。
- **设计器**：流程设计页新增“发起人范围”区（五类下拉添加、标签移除、未配置时提示“现在不限制”），没有配置权限时只读。
- 测试：共享层 5 个；API `flow-gaps.db.spec` 覆盖空范围/部门/岗位/岗位类型/员工/职责组/并集/版本化/引用校验；前端编辑器测试。

## 3. SKU 申请汇总、批量办理、整单与个别退回（编号 3）

**旧版**：
- 待办列表**一张申请单一行**（`workspace-list.js`），不是一个规格一行。
- 批量动作（`batch-requests.js`）：`/:id/actions` 一次 1–100 项，每项带版本号，**逐项独立处理、允许部分成功**；退回、废除、拒绝必须写原因。
- 仓库**整单退回运营**（`warehouse-return.js`）：这张申请单在仓库手里的规格**必须全是当前人的**，必须写原因，一个事务全退。旧库里仓库退回 146 次、平均每申请约 10 个规格。
- 仓库“批量套用发货组成”：一份配置套用到选中的所有规格。

**新版保持“规格独立流转”不变**（`splitSpecs` 拆成一规格一条流程，共用 `_batchKey`），在上面加一层汇总，所有动作仍走流程引擎（办理资格、版本号、适配器校验、审计、通知都和单条办理一样）：

| 能力 | 做法 |
|---|---|
| 汇总待办 | `FlowService.todos()` 把同一 (batchKey, 步骤, 办理人, 分类) 折叠成一行，返回 `batchKey/batchName/batchCount`；各分类的计数用同样的折叠规则。没有拆开的申请（一条流程多个规格）仍是一行。 |
| 汇总面板 | `SkuBatchService.board()`：每个规格一行，显示当前步骤、办理人、截止、被退回原因；`me` 里给出你手里的步骤、数量、能否整单退回；带办理历史。前端 `SkuBatchPanel`，从待办“批量办理”、通知链接或 `?batch=` 打开。 |
| 批量通过 | `act(pass)`：逐项独立事务，部分成功，失败项逐个报原因。仓库一份发货组成套用到选中规格；财务勾选“已核对”（可选加入聚水潭同步队列，仍然只入队）。 |
| 批量退回/拒绝/废除 | 原因必填；单次 1–100 项；重复项拒绝。 |
| 整单退回 | `returnAll()`：一个事务、全退或全不退；这一步申请单里所有在办规格都必须是你名下的待办（否则 403）；版本号不一致整体失败；原因必填。 |
| 个别规格退回 | 拆开办理的申请：勾选规格后“批量退回”。**没拆开的一张申请**：`returnSpecs()` 把被退回的规格**拆出**成一条新流程（带着已办理的步骤历史、同一个 `_batchKey`），拆出的那条退回申请人；剩下的规格留在原流程继续往下走，并重算财务核对指纹 `_reviewSig`，避免财务通过时报“编码发生了变化”。全部规格都选等于整条退回，不拆。 |
| 申请人修改后重新提交 | 汇总面板里申请人看到被退回的规格和原因，“修改并重新提交”打开原来的流程详情改字段重新提交，或“原样重新提交”（`act(resubmit)`）。重新提交保留 `_batchKey/_splitIndex/_splitTotal`。 |
| 通知 | 批量动作用“静默模式”（`markQuiet(em)`）不逐条给站内通知，办完后每个人收到**一条汇总通知**（“被退回：10 月新品（3 个规格 · 仓库完善）”，带原因和进入汇总面板的链接）；飞书入队仍然逐条（由出站队列统一处理）。 |
| 审计与历史 | `flow.sku.batch.<动作>`、`flow.sku.return-all`、`flow.sku.return-specs` 写审计（含被处理的流程、原因、失败项）；每个规格的流程里仍有完整事件和步骤记录。 |

另外发现并修复一个已有问题：**第一个办理步骤（SKU 里就是仓库）在流程详情里没有“退回”按钮**——`me.canReturn` 要求“已完成步骤数 > 1”，而新发起的流程只有发起这一步，结果仓库根本退不回运营（服务端其实允许）。改成“至少有一个已完成步骤”，并加了测试。

## 4. 管理员批量改派（编号 7，审计 B2）

**旧版**：10 月靠脚本重派了 31 个规格（`docs/SKU财务待办重派.md`），没有界面。

**新版**：`POST /flow/reassign`，只有公司管理员；必须选原办理人和新办理人（同一公司、不能相同），可限定流程类型/步骤；先“预览”（dryRun，列出将改派的前 100 条和总数），再填原因（2–500 字）确认；单次最多 500 条，每条一个事务；已完成/已结束的不动；写一条“转交”事件、通知新旧办理人、写审计 `flow.reassign`。界面在“流程总览”右上角“批量改派”，只对管理员显示。

## 5. 保存草稿与发布留审计、版本记发布人（编号 8，审计 B3）

保存草稿写 `flow.draft.save`，发布写 `flow.publish`（含上一个启用版本）；`flow_definitions.published_by` 记发布人，版本记录页新增“发布人”列。

## 6. 逾期扫描漏单（编号 9，审计 B4）

**问题**：`scanOverdue` 用 `where { status: 'open', overdueNotifiedAt: undefined }`，TypeORM 里 `undefined` 等于**不过滤**，再 `take(500)` 且没有排序；已经通知过但仍开着的待办会一直占满前 500 条，后面真正新逾期的永远扫不到。

**做法**：先写能复现的测试（520 条已通知 + 520 条未到期 + 1 条新逾期，旧代码扫出 0 条，测试失败），再修：改为 `status='open' AND overdue_notified_at IS NULL AND due_at < now AND id > 上一批最大 id ORDER BY id LIMIT 500`，最多翻 40 页。`FlowTimeoutService` 的提醒和未结束的超时事件也改成按 id 分页（1000/500 一页，上限 2 万），不再只看第一页。

## 7. 逾期提醒去重（编号 10，审计 B5）

三条路径：①待办逾期扫描（`scanOverdue`）②督促时效（`remind.overdueEveryMinutes`，给办理人）③三级超时升级（主管/老板）。

- 办理人本人的逾期提醒：节点配置了督促超时间隔的，由督促负责，逾期扫描不再重复发；没配置的由扫描发一次。
- 升级对象（流程级升级人、三级策略里的主管/老板）统一走 `overdue-notice.ts` 的 `claimNotice/claimEscalations`：以 `INSERT IGNORE` 写 `flow_reminder_logs`（唯一键 work_item_id + kind），**谁先占到谁发，其他路径不再发**；并且不会把升级通知再发给办理人自己。超时事件 JSON 里记 `dedupedIds`，可追溯“没发是因为已经有人发过”。
- 测试：两个去重用例（同一待办只收到一次升级、办理人本人不重复）。

## 8. 附件字段显示（编号 11，审计 B6）

自建流程里“附件”类字段在详情页以前显示成文件编号（`String(v)`）。现在 `FlowValues` 对 `files` 字段显示**文件名 + 下载链接**（临时签名链接，按需获取）；没有权限或文件已被删除时显示“文件 #编号（无法打开：没有权限或文件已删除）”。

## 迁移与权限

- 迁移 `1755000000000-FlowGaps`：`flow_definitions` 加 `starter_scope JSON NULL`、`published_by INT UNSIGNED NULL`。只改结构、向后兼容，旧数据为空即“不限制”。已登记任务板迁移占用表。
- **没有新增权限键**：新接口都是 `@AuthenticatedOnly()`，权限在服务里判断——批量办理由流程引擎的办理资格判断；批量改派只允许公司管理员；发起人范围由流程配置的 `flow.templates.manage` 管（沿用）。

| 项 | 原因 |
|---|---|
| 在办申请迁移（A4） | 用户决定不做；上线时旧系统在办单需要运营自己收尾或重新发起 |
| 飞书通知（A3） | 用户决定不做；飞书入队逻辑保持原样，批量动作仍逐条入队 |

## 上线后管理员要做的

1. 打开“流程配置 → SKU 批量申请”，确认仓库、财务节点的办理人（旧配置里仓库=部门、财务=岗位）和时限 60 分钟、提前 20/10 分钟提醒；点“保存并发布”。已经发布过的版本里如果还是旧的 3600，要再发布一次才会生效（在办的流程仍用启动时的时限）。
2. 需要限制谁能发起的流程（采购、专属品、SKU 等），在“发起人范围”里选部门/岗位/角色/职责组/员工，保存并发布；**不配置就是不限制**。
3. 员工离职或调岗：流程总览 → 批量改派，先预览再确认。
4. 告知仓库、财务：待办里同一张申请单只有一行，点“批量办理”进入汇总面板；整单退回要求这一步所有规格都在自己名下。
