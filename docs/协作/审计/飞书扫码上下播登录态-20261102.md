# 飞书扫码上下播登录态

根因：tokenStore仅使用sessionStorage，飞书每次扫描打开独立WebView/页面时无原窗口令牌，应用渲染LoginPage，员工被迫重复输入密码。原JWT默认12小时有效期也不会因重复扫码自动延长。

修正：同源持久保存令牌，升级前会话读取后迁移，存储受限时回退本窗口；退出及401清理两处存储，跨窗口退出/换账号重取本人身份权限，旧响应不覆盖新身份。飞书UA内扫描合法上下播码但无有效登录态时，按码中的公司在已启用飞书企业列表中匹配，自动通过现有OAuth开始认证，保留公司/房间/二维码token，完成后回到原扫码页；失败/取消不循环，未绑定员工保留账号密码登录与本人绑定入口。离开页面后迟到授权不触发跳转。

沿用服务端JWT有效期、企业/员工/绑定校验、一次性OAuth state及HttpOnly浏览器绑定Cookie，不凭二维码认定员工身份。外部浏览器与飞书容器不保证共享存储，因此增加现有飞书身份授权路径补偿；首次授权是否需要确认由飞书决定。不修改后端、生产数据库、开下播规则或当前绑定提醒策略，无新增迁移。

验证：本地Node20常规shared354/API349/web1129/agent75共1907项通过（API数据库773项未在本次本地常规测试执行，完整数据库检查交由PR的MySQL8 CI）。新增扫码/持久化15项覆盖旧会话迁移、新窗口恢复、退出/过期、受限存储、跨窗口换账号、公司匹配、错误码/普通浏览器、StrictMode防重及取消回调。npm run typecheck、npm run build通过。未操作真实员工账号、未提交真实上下播。真实手机飞书扫码/OAuth需发布后最终验收，不能把模拟测试记为真实手机验证。
