## 3. 后端与口径

- 迁移 `1753000000000-DocDiscount`：`finance_documents.discount_cents`（默认 0，只加列；老单据不变）。`amount_cents` 仍是单据金额（优惠后）。
- `DocInput.discountCents`：仅商品类单据；非商品类单据保存草稿时被忽略（存 0），开立校验会报“只有商品类单据能填优惠金额”；优惠必须小于明细合计。
- 费用单 `offset: 'prepayment'`：分录 借费用 / 贷银行(实付) / 贷预付款(冲抵) / 贷应付(余额)；冲抵必须选往来对象（供应商等）；过账沿用原有预付余额检查。
- 新增两个只读接口（均 `@AuthenticatedOnly()`，服务内要求制单/历程/草稿任一权限，全部带 company_id，跨公司对象按“不存在”处理）：
  - `GET /finance/party-balance?partyKind&partyId` → 应收/应付/预收/预付余额、客户赊销额度（需 `resource.finance-customers.view`）。
  - `GET /finance/line-hints?productIds=1,2&warehouseId=` → 账面库存；`lastPurchase*` 仅 `product.cost.view` 返回；`lastSale*` 仅 `product.price.view` 返回（服务端不给字段）。
- 权限键、导航、流程引擎：无改动。店铺提现、经营历程、草稿中心、成本表、基础资料、流程引擎没有改动；草稿中心的“编辑草稿”弹窗共用 DocForm，原有测试全部不改断言通过（仅把“最后一行回车加行”的触发格从单价改为备注，因为回车现在先逐格前进）。

## 6. 第二批：口径决定落地

第一批汇报里有 6 个需要拍板的口径问题，用户的决定是“1 做、2 不做、3 做、4 做、5 可以、6 不用独立”。本节逐项记录 A8 逻辑要点、采用的口径、向后兼容、没做的部分及理由。迁移只有一个：`1754000000000-DocPayAccountsTransferFee`（只加列）。新权限键只有一个：`finance.docs.confirm-transfer`。科目是代码里的内置科目，没有种子数据，也没有写进迁移。

### 6.1 收款单、付款单的“优惠金额”影响往来（决定 1：做）

- A8 逻辑要点（3.7.3.1）：销售/采购类单据里的优惠金额不计入往来（第一批已按此做）；收付款单里的优惠金额会影响往来，“优惠金额与单据金额之和，为这笔业务扣减的应付账款”（例：该结 10002 元，供应商只收 10000 元，2 元优惠不用付，应付减少 10002 元）。
- 采用的口径：
  - 收款单：借 银行（到账金额）、借 预收款（冲抵）、借 财务费用（优惠）；贷 应收账款（到账 + 冲抵 + 优惠）。收款优惠是给对方让利，借方 = 费用增加。
  - 付款单：借 应付账款（付出 + 冲抵 + 优惠）；贷 银行（付出金额）、贷 预付款（冲抵）、贷 财务费用（优惠）。付款优惠是对方给的折扣，贷方 = 费用减少。
  - 科目：新增内置科目 `finance_cost`（财务费用·现金折扣/手续费），借正贷负，账户 id 固定 0。没有做成“费用档案里的一个费用项”，原因是费用项要靠种子数据，每家公司都要先建、可能被停用/改名，会让过账失败或口径不一；内置科目不依赖任何档案。
  - 存储复用已有的 `finance_documents.discount_cents`（收付款单：到账/付出之外的优惠；商品类单据：整单优惠，两种含义不同但都是“优惠额”，列表按单据类型区分）。收付款单的 `amount_cents` 仍是到账/付出金额。
  - 按单据/按商品结算：本次结算金额 = 到账 + 冲抵 + 优惠（对应 A8 “收付款金额 + 优惠金额 = 单据结算金额”），分配合计必须等于它。
- 报表联动（逐个核对，口径一致、不重复）：
  - 往来余额（应收/应付）：来自分录，自动按“到账 + 冲抵 + 优惠”减少；
  - 收付款结算明细表：分配金额含优惠部分，合计等于应收减少额；
  - 未完全结算的收付款单：总额 = 到账 + 冲抵 + 优惠（`unsettledReceipts` 同时返回 `discountCents`）；
  - 财务经营：新增“财务费用”卡片（`financeCostCents`，借减贷，可以为负）；净利润 = 收入 − 成本 − 费用 − 财务费用 + 其他收入；趋势按日/月的利润同样扣财务费用；“费用”卡片仍只含普通费用，不变；台账（最近 60 笔）加入财务费用分录（借方显示支出，贷方显示收入）；
  - 现金银行查询：只受“到账/付出”影响，优惠不进银行；
  - 单据详情分录：新科目显示为“财务费用（现金折扣/手续费）”；
  - 销售/采购商品单据自带的“整单优惠”仍然不进往来、不进财务费用（销售收入/库存成本按优惠后），和收付款优惠互不重复。
- 向后兼容：老收付款单的 `discount_cents` 本来就是 0，分录、报表数字不变；红冲把优惠和财务费用分录一并取反；复制带上优惠；预收款单、预付款单、转款单等其他单据仍不能填优惠（草稿里被忽略，开立校验会提示）。
- 没做/限制：填优惠必须先选往来对象（冲减的是他的往来余额）；不做“优惠不得超过往来余额”的强制校验（和到账金额一样，往来余额本来允许为负，保持一致）。

### 6.2 往来核销单（决定 2：不做）

按决定不做，页面、接口、科目都没有任何入口或残留。应收冲应付、预收冲预付、债权债务转移仍然通过现有的“冲抵预收/预付”和收付款单处理。

### 6.3 多账户收付款（决定 3：做）

- A8 逻辑要点：单据表尾（销售出库单、采购入库单、收付款单等）有“多账户选择”，用于把一笔收/付款分摊到多个账户。
- 采用的口径：
  - 支持的单据：普通销售单、网店销售单、销售退货单、采购入库单、采购退货单、预收款单、收款单、付款单、预付款单、其他收入单、费用单（共 11 种，`payRole()` 统一判定方向：钱进银行为 `in`、钱出银行为 `out`）。转款单本来就有多账户；店铺提现单是平台提现到账的一个账户，不支持。
  - 单据上每个账户一行（账户 + 金额），存在已有的 `finance_document_accounts`（role 沿用 in/out 两个值，无需改表）。
  - 校验：账户不能重复、金额大于 0、方向要对、账户必须是本公司的有效银行账户；有商品明细的单据，各账户合计 = 实收/实付，写明的实收实付不一致时草稿就拒绝；收款单、付款单等没有挂账概念的单据，各账户合计必须等于单据金额。多收/少收的差额仍按原有规则挂应收/应付。
  - 过账：每个账户一条银行分录；主表 `bank_account_id` 记第一个账户，所以旧列表/旧查询只看主表也不会出错。
  - 现金银行查询、银行账本、账户余额、结算明细表都直接读分录，所以每个账户的流水和余额自动正确；经营历程/草稿列表显示“甲户 等 N 个账户”。
  - 红冲：账户行金额取反、银行分录取反；复制为草稿：带上全部账户；打印：结算账户一栏列出每个账户和金额。
  - 界面：账户栏下有“分多个账户收款/付款”按钮，展开后每行选账户填金额，实时显示合计，“差额填入最后一行”，“改回单个账户”；实收/实付自动等于各账户之和；全款/欠款等结算方式按钮在分账户时也能用（欠款/用预收预付结算会自动改回单账户）。
- 向后兼容：老单据没有账户行，继续用 `bank_account_id` 单账户；界面不点“分多个账户”就和原来完全一样；草稿从分账户改回单账户时，账户行会被清掉。
- 没做：币种/汇率；同一单据同一账户分多行（A8 也是每个账户一行）。

### 6.4 转款手续费与“确认入账”（决定 4：做）

- A8 逻辑要点（3.9.6.3.1 资金调拨单）：转出账户、转入账户、调拨金额、“手续费扣除账户”、手续费金额；“是否确认”是调出方审核过账后，调入方“确认入账”才回写的标识。
- 采用的口径：
  - 手续费：`fee_cents` + 承担方 `fee_bearer`（out 转出方 / in 转入方），由承担方的第一个账户扣：银行减、财务费用借。转出方承担 = 转出账户多扣；转入方承担 = 转入账户少收。
  - 在途：转款单可勾选“先登记为在途”（`transit_status = pending`）。过账只从转出账户扣；转入侧记内置科目 `in_transit`（在途资金，账户 id = 转入账户）。**转入方承担的手续费到确认到账那一刻才扣**，转出方承担的手续费过账就扣。
  - 确认入账：单据详情“确认入账”按钮（`POST /finance/docs/:id/confirm-transfer`，权限 `finance.docs.confirm-transfer`，可填到账日期和备注）。在同一单据上追加分录：在途资金转入银行，状态变为 `confirmed`，记录确认人/时间，写单据事件 `confirm-transfer` 和审计日志 `finance.confirm-transfer`。已确认不能重复；已红冲、非在途、未过账、非转款单都拒绝；跨公司按不存在。
  - 流程引擎：不写死审批人、不新增流程节点。确认入账服务方法 `confirmTransfer(user, id, opts, outer?)` 和 `post()` 一样可以接收流程引擎传入的事务，想要审批时由统一流程引擎既有方式（流程办理时在引擎事务里调用）接入；这一批没有改动流程引擎任何代码，流程测试照常通过。
  - 现金银行查询：账户行新增“在途待确认”列，页面顶部汇总卡片“在途待确认转款”（有在途时才出现），导出 CSV 也带；在途金额不计入余额。经营历程新增“转款在途：只看在途待确认的转款”筛选，列表上有“在途待确认”标签。
  - 财务经营：手续费计入财务费用（见 6.1）。
  - 约束：在途未确认的转款单不能财务审核；已确认入账的转款单不能改单据日期（确认分录有自己的日期）；红冲会把过账、确认两批分录一并取反，没确认就红冲则在途资金冲回。
- 向后兼容：老转款单手续费 0、`transit_status` 为空，分录与原来一致（有测试对比）；单账户老写法也能带手续费。
- 没做：现金调拨/账户转账业务类型、分支机构间调拨、外币；“调入方”和“调出方”不是两个机构，所以确认入账由有权限的财务人员操作，不区分机构范围。

### 6.5 经手人改成员工选择器（决定 5：可以）

- 口径：`finance_documents.handler_id` 保存员工 id，`handler` 同时记姓名快照；列表、详情、银行账本读的时候优先取员工当前姓名（员工改名后跟着变）。员工必须是本公司的；停用员工不能新选，但原来就选着他的老单据保留。新开单默认当前登录员工。
- 向后兼容：老数据只有 `handler` 文字（无 id），下拉里作为第一个选项“xxx（原文字）”保留，编辑保存时不丢；经营历程“修改单据”也用同一个选择器，选回“原文字”则保持文字。取不到员工名单（无权限/网络错）不影响开单。
- 没做：A8 的“根据往来单位自动刷新经手人 / 录单时不允许修改经手人”配置项。
