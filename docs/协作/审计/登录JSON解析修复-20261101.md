# 登录请求 JSON 解析修复

## 线上症状与只读核对

Windows1.7.1发送的账号、密码均为正常字符串，JSON格式和Content-Type正确；公网及容器内部127.0.0.1请求均返回400，提示account/password缺失或类型错误。请求在DTO校验阶段被拒，尚未进入AuthService的账号查询。这不是本次数据库迁移未完成造成的参数校验错误。

通过既有SSH运维通道，只初始化DataSource进行只读核对，没有启动应用worker。当前库有61个员工账号、1个启用公司；截图中的账号已存在、启用且未要求首次改密。没有读取密码或密码哈希、没有尝试员工真实账号密码、没有修改业务数据。本文不记录员工账号及其他个人信息。

## 根因及修复

先前为/api/collector/file在Nest初始化前注册了局部express.json(6MB)。Nest11 ExpressAdapter按中间件函数名jsonParser判断“已经注册”，因此跳过了默认全局JSON解析器；只有音频路径能解析JSON，其他接口req.body为空。现有接口守卫测试使用测试模块默认解析，未覆盖该生产启动组合，这是原接入变更的覆盖缺口。

现在显式关闭Nest自动bodyParser，并从common/body-parsers统一注册：音频路径6MB JSON、普通路径100KB JSON、100KB URL编码表单。main.ts只做最小挂接。DTO白名单、拒绝额外字段、账号验证、权限及公司隔离全部沿用，不以放宽校验掩盖错误。

官方参考：[Nest请求体处理](https://docs.nestjs.com/faq/raw-body)、[Express body-parser](https://expressjs.com/en/resources/middleware/body-parser/)。根因已对照当前依赖ExpressAdapter.registerParserMiddleware/isMiddlewareApplied源码，并通过真实NestFactory启动重现，不仅依据文档推断。

## 回归验证

新增真实NestFactory启动、真实AuthController和LoginDto、假的登录服务，验证传输层输入；没有连接业务库或供应商。旧启动组合出现3失败/2通过：有效JSON登录400、普通JSON字段缺失、普通请求大小限制未生效。修复后5项全部通过：

- 正常JSON账号密码到达登录服务，返回模拟凭据错误401，而不是参数缺失400。
- 普通JSON与URL编码表单的中文/字符串字段均正确读取。
- 200KB音频JSON可解析，普通接口超过100KB拒绝413。
- 音频超过6MB拒绝413。
- 畸形JSON、缺字段、额外字段仍400，且不进入登录服务。

本地首次专项命令缺少已编译的shared依赖，补跑build:shared后才进行上述红/绿验证，没有把编译失败算作缺陷复现。

最终本地类型检查及完整常规1260项通过（shared334/API196/web656/agent74），API的553项真实MySQL交既有CI；未修改无关测试或跳过失败断言。

上线后用合成的不存在账号核对正常JSON不再报字段缺失，同时检查空/畸形JSON仍被拒；不使用真实员工密码或伪造生产身份来宣称实际账号登录验收。
