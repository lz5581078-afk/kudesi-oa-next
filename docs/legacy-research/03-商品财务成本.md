## 1. 业务概念与领域模型

### 1.1 核心概念
| 概念 | 含义 |
|---|---|
| 商品档案（archive / finance_products） | 实物或物料主数据，分五类（加 OEM 包装共六种类型码）：原料 raw(YL)、自制品 self_made(ZC)、采购品 purchased(WG，supply_mode = original_purchase 原装采购 / supplier_oem 供应商OEM)、产品包装 package(BZ)、发货物料 shipping_material(FH)、OEM 包装 oem_package(OEM) |
| 基础编码（base code，finance_product_base_codes） | “可销售的普通商品”，对应聚水潭普通 SKU；通过 source_product_id 或 finance_product_code_links 关联一个或多个档案 |
| 原料成品名“马甲”（alias） | 原料档案的 rawFinishedNames 生成别名基础编码，字段 canonical_base_code_id + raw_finished_name_id；编码 `YL-` + SHA-256 前 20 位十六进制；每个原料最多 100 个；验证走真实（canonical）编码 |
| 组合编码定义（bundle definition） | 一个组合品的构成定义（主品+赠品、数量、weight_mode 重量模式） |
| BOM（finance_product_bundle_boms / lines） | 组合构成明细，带 component_signature；基础编码 × 数量 |
| 组合编码（bundle code / SKU） | 定义 × 平台 × 销售场景 × 配置号 展开的最终销售编码，同步聚水潭组合装 |
| 成本条目（finance_bundle_cost_entries） | 当前生效的 SKU 成本表：发货前成本、运费、最低售价；含事件历史 |
| 旧成本版本（finance_cost_versions / finance_sku_costs） | 第一版成本模块：版本、辅助成本、加价率、底价，后端仍在、前端已不挂载 |
| 验证（verification） | 基础编码/组合编码的 pending / verified / reverify 状态与组成签名快照 |
| 分类树 | 每类档案一棵 finance_product_categories，与 finance_product_code_dictionary(product_category / bundle_category) 双向镜像 |

### 1.2 关系链（ER 文字描述）
- company 1—N 一切（所有表有 company_id，多租户）。
- finance_products N—1 archive_type；N—1 category（必须叶子）；1—N archive_costs（有生效日期的成本行）、photos、boms/bom_lines（自制/OEM）、labor_lines、freight_history、zero_value_reasons。
- finance_products 1—N base_codes（经 source_product_id / code_links），一个基础编码可聚合多个档案（code_links 保存数量/单位关系）；alias 基础编码 N—1 canonical 基础编码。
- base_code 1—1 当前 data_verification（+ events）。
- bundle_definition 1—N bundle_boms（版本）1—N bom_lines（引用 base_code，含 role=main/gift/package/label/instruction/other）；definition 1—N labor_lines；definition 1—N composition_revisions。
- bundle_definition × platform × sales_scenario × configuration_code → bundle_code（唯一键 company_id+bundle_definition_id+platform_id+sales_scenario+configuration_code；company_id+final_code 唯一）。
- bundle_code 1—1 bundle_data_verification；1—1 当前 bundle_cost_entry（+ events）；bundle_cost_margins（按分类/全部默认的利润率）。
- 聚水潭：jst_product_outbound_states/logs（基础编码）、jst_bundle_outbound_states/logs、jst_bundle_price_states/logs（价格）、finance_bundle_archive_jobs（失效归档任务）、jst_category_sync_*（分类同步）。
- 快递：finance_express_catalogs（每公司一行，carriers_json 含 carriers→branches→versions→rules，recommendations_json 分区建议）；finance_express_cost_estimates（每公司一行，rows_json 重量段预估运费，max_weight）。
- 包装方案：packaging_schemes 1—N lines / rules。
- 人工成本：labor_cost_versions 1—N items(+events)；work_categories、work_types、billing_units。
- 导入：master_data_imports、master_data_snapshots（重置/回滚）。
- 过账：finance_documents/lines 1—N document_sources、posting_entries、payment_references、prepayment_allocations、workflow_cost_events。
- 外部：verified_bundle_api_keys（哈希存储）；商品专属：product_exclusive_members/slots/grants（迁移 0171）。

### 1.3 数据流主线
档案(五类，含成本) → 基础编码(同步聚水潭普通商品) → 验证通过 → 组合申请(运营选主品/赠品/平台/场景 → 仓库补包材/标签/人工 → 财务终审) → 终审同一事务内创建 定义+BOM+组合编码+验证快照+成本条目 → 同步聚水潭组合装与价格 → 外部只读接口输出。
档案重量/成本变更 → refreshCurrentBundleValues 重新关联成本/重量并写事件。

## 3. 成本与最低售价公式

### 3.1 当前 SKU 成本表（实际在用，bundle-cost-register.js）
- 组合成本 = Σ(组件 costPrice × 数量)，任一组件无成本则为 null；含包材/标签/人工行。
- 重量 = Σ(组件重量 × 数量)；weight_mode='manual' 时用手工重量。
- 发货前成本 preShipCost = 采购 + 中转 + 发货前包装 + 生产（旧模型口径）；目前 bundle cost price 等于 preShipCost。
- 有效运费 effectiveFreight：由 billing_weight（定义的称重重量）匹配 finance_express_cost_estimates.rows_json 的重量段（start < w ≤ end）；手工金额(manualAmount)优先于自动值；超过单包上限的拆包求和 (split_parcel_sum)；重量 ≤0 或 >1000 为 null。
- **最低售价 = ceil( (preShipCost + effectiveFreight) / (1 − profitRate) × 100 − 1e-8 ) / 100**；运费或利润率缺失则 null。profitRate ∈ [0,1)，百分比最多 6 位小数。
- 利润率优先级：SKU 覆盖 > 本分类 > 逐级祖先 > “全部默认”(category_id=0) > 无。
- 精度：成本 4 位，售价 2 位向上取整到分。
- 发布时机：组合申请财务终审或构成修订发布，同一事务写入；档案重量/成本变化触发 refreshCurrentBundleValues；每次变更写 event。

### 3.2 旧版成本模块（cost-calculator.js、sku-cost-engine.js，后端存在，前端不再展示）
- preShipCost = 采购+中转+发货前包装+生产；totalCost = preShipCost + 发货包装 + 预估快递；floorPrice = totalCost × (1 + effectiveMarkup)；effectiveMarkup = SKU 覆盖，否则版本默认（默认 20%）。
- 所有项非负，0 需显式录入；BOM 参考成本 = 数量 × (1+损耗率) × 单价，仅作参考不覆盖手工值。
- 辅助成本应用方式：add / fallback / override；成本类型归入六个桶（purchase、transfer、preShipPackage、production、shippingPackage、express）。
- 注意两套公式不同：加价率（乘）vs 利润率（除以 1−p）。重写只应保留后者，除非业务确认。

### 3.3 档案成本
- 档案总成本 = 采购价 + 运费 + 装卸费（8 位小数），任一缺失/负数则 null。
- 自制品/供应商OEM 派生成本 = Σ(数量×(1+损耗)×组件当前单价) + 运费 + 装卸（也按数量缩放）+ 人工行；组件缺成本则“未就绪”。
- 成本为带生效日期的行(finance_product_archive_costs)，来源 manual / purchase_order / raw_supply_source / production_bom / excel_import / archive_purchase_price；人工锁定后不被自动覆盖；同日不同来源不覆盖；区间不得重叠。
- 采购联动：采购单价与单位物流费进入当前成本表；已锁定的版本保留快照。
- 原料系统规格重量换算（regex systemWeightKg）：千克/公斤/kg=1，克/g=0.001，斤/j=0.5kg，两=0.05kg，毫克，吨/t=1000kg。
- 自制品重量 = Σ组件重量；OEM 采购重量 = 商品重量 + 包装重量。

### 3.4 快递运费与重量规则（shared/express-routing.mjs、express-shipping-weight.mjs）
- 每个价格版本有 shipping_weight_min（默认0，含）/ shipping_weight_max（含，空=不限），重量必须 > 0；超出范围则该承运商不可用，不降级。
- 单条价格规则：固定价或公式 首重价 + ceil(重量 − 首重) × 续重价；选择规则：省份专属 > 全国；其次重量区间更窄；再次靠前。
- 重量段预估（estimateTypicalProvinceFreight）：段为 0–0.5，其后每 1kg 到 30kg（可配至 100）；每省取最便宜报价；取相互差在 15% 内的最大簇，均值 ×1.1（method=provincial_majority_mean_plus_10_percent）；省份样本少于 3 个为 null；仅 6kg 以上允许降级：去掉最高 20% 与孤立低价后均值 ×1.1（provincial_upper_trimmed_mean_plus_10_percent）；样本承运商须覆盖整个重量段。
- 超过单包上限：拆为多包求和（split_parcel_sum）。
- 自动分区建议：按省份+重量区间生成聚水潭分区规则。

### 3.5 SKU 批量申请流程（工作流）
运营（选主品/赠品基础编码、平台、场景）→ 仓库（补包材/标签/说明书/其他行与人工）→ 财务终审。终审同一事务：建定义+BOM+编码+验证快照+成本条目。来源分类根限制：主品 = 供应商OEM成品/原料档案/原装采购成品；赠品另加发货物料档案；包装 = 产品包装档案；标签/说明书/其他 = 发货物料档案。

## 4. 命名、编码、分类树规则

### 4.1 编码字符
- 新码仅 A-Z 0-9 `-`（内部兼容 `+` `*`），正则 `^[A-Z0-9+*]+(-[A-Z0-9+*]+)*$`；建议 ≤32，硬上限 48；库内 VARCHAR 120 兼容旧码。
- 数量小数点写作 D，如 2.5 → 2D5。

### 4.2 档案编码
段落：类型段(YL/ZC/WG/BZ/FH/OEM) – (WG: YZ|OEM) – 分类链编码 – 品牌拼音首字母(原料不含) – 名称拼音首字母 – 规格段(数量+单位码) – 形态款式(原料、自制、采购、包装不含)。
单位码：克G 千克KG 斤J 吨T 毫升ML 升LTR 粒L 棵K 包B 袋D 盒BOX 箱CTN 瓶BTL 罐CAN 件PCS 个EA。

### 4.3 基础编码
样式码 = 分类链编码 + 品牌码(可选) + 品种拼音首字母；编码 = 样式码 + “-” + 规格数量 + 单位码；可手改须填原因。

### 4.4 组合编码
- 生成：`ZH-` + [平台码，GENERAL 不加] + 主品编码以 `+` 连接 + 可选 `+ZP-` 赠品编码；场景 supply_chain 加 GYL 段；配置号区分同构成多配置。
- 名称：“组合-” + 品名以 `+` 连接 + “+赠:” + 赠品名。
- 同一基础编码数量合并；可加单位（1斤×5 → 5斤）。
- 命名规则可按来源分类配置并沿树继承；品牌、品种、总规格是独立字段。
- 编码变更 = 禁用旧码并创建新码，不改原码。

### 4.5 分类树
- 根：原料档案/YL、产品包装档案/BZ、发货物料档案/FH、原装采购成品/WGYZ、供应商OEM成品/WGOEM；组合另有 bundle_category（显示名前缀“组合-”）。
- 名称全局唯一（NFKC 归一、大小写折叠、去空白后比较）。
- V3 层级上限 4（旧计划文档写 6，文档与实现不一致）；商品必须挂叶子分类。
- 档案分类与字典 product_category 双向镜像（product-archive-linkage.js）。

## 5. 权限
- 仓库角色（warehouse/warehouse_manager、仓储/仓库部门及后代、兼职仓库岗位；管理员除外）：只能查看档案（字段白名单，价格剥离）并上传照片；不能编辑、删除、导入、导出价格（product-archive-access.js）。
- 运营：看不到成本金额（canReadBatchCosts 控制成本登记册，operations-cost-boundary）；仍可发起组合申请。
- 财务/管理员（admin、company_admin、boss、财务角色、或部门名含“财务”）：可编辑成本表、利润率、终审。
- 组合：view（读构成、验证预览） vs manage（保存、发布）；sync（聚水潭同步）单独权限。
- 基础编码删除需 finance-product-base-codes.manage，且有个人拒绝覆盖。
- API 密钥：仅公司管理员创建/吊销；SHA-256 哈希存储，只展示一次，请求头 X-API-Key；两种范围 verified_bundle_read（旧接口）与“商品与成本数据”（/api/external/catalog/v1/{sku-costs,cost-categories,bundle-codes,bundle-categories}），互不通用；列表 afterId/limit(≤100) 游标分页，非增量同步。
- 照片上传：/api/product-photo-upload 公开，基于哈希 token + 过期时间，手机扫码。
- 商品专属授权：product_exclusive_* 控制基础编码家族的独占使用。

## 8. 现有 UI/逻辑问题（重写应避免）
1. 超大文件：FinanceProductArchivePage.jsx 5544 行；FinanceArchivePage.jsx 3880 行；ExpressPriceTablePage.jsx 2940 行；FinanceProductBaseCodePageV5.jsx 2544 行；server/index.js 约 13k 行；costs.js 约 129KB（613 行，长行）。FinanceCostTablePageV3.jsx 与多个服务端模块为一行式压缩代码，难维护。
2. 版本并存：基础编码页 V1-V5、组合页 V1/V2、成本页 V1/V2/V3 以及 FinanceProductBundlePage/FinanceProductBundleCodePage 旧文件仍在树内；后端 product-base-codes.js/-v2.js、sku-cost-engine-preview-v2/v3.js 并存。V3 成本页约 150 行死代码。
3. 两套成本体系：finance_sku_costs（加价率、版本、辅助成本）与 finance_bundle_cost_entries（利润率、最低售价）公式不同并存，前端仅暴露后者；旧体系 API 仍可调用。
4. 存储：档案以 payload_json 大 JSON + 整体 PUT /workspace 保存（遗留自 localStorage 原型），会重写整份快照并删除“缺失”的商品；单位表删后重插；三套单位表；照片 base64 存 MySQL；快递目录与预估运费各为一份 JSON 文档（20MB 上限、乐观锁整份覆盖，多人并发易冲突）。
5. 分类重复：档案分类与字典分类两表双向镜像，依赖同步函数，易漂移；全局名称唯一规则对用户不直观。
6. 信任边界：前端计算自制品构成成本并把快照提交服务端（calculateSelfMadeCompositionBreakdown），服务端校验不足。
7. 文档与实现不一致：分类层级文档 6 层 vs 代码 4 层；编码字符文档仅 A-Z0-9- vs 代码允许 + *；已放弃的 catalog_* 设计与实际 finance_* 表并存；“OEM 包装档案”含义含糊（oem_package 与 WGOEM）。
8. 公式口径混乱：最低售价（利润率除法）与“公司底价”（加价乘法）并存；bundle cost price 恒等于 preShipCost；两个字段冗余。
9. 迁移含公司专属修复：迁移 0130 检查 company id 3 与公司名；0090-0096、0111-0114 含种子数据，不可复用到新系统。
10. 交互：校验大量使用 window.alert；成本页 15 秒轮询；页面向组件注入数十个 props（page-loaders）；层级深（档案 → 分类 → 类型 → 单位 → 成本 → 重量，跨页跳转多）；基础编码需先验证才能使用，但失效/重新验证原因不直观。
11. 权限分散：仓库、运营、财务判断散在 product-archive-access、operations-cost-boundary、bundle-cost-register.mayEdit（按角色名与部门名字符串匹配“财务”），应改为显式权限点。
12. 导入导出：多处各自实现，确认串/回滚机制不统一。

### 重写建议要点
- 以关系表替代 payload_json；统一单位与分类单表；照片走对象存储。
- 只保留利润率最低售价公式；成本与运费快照化并版本化。
- 快递目录拆成表（公司/网点/版本/规则）；预估运费按行存储。
- 验证与同步状态机统一，写意图+回读核对原则保留。
- 命名/编码规则配置化，沿分类树继承，保留唯一键与重复检查三层。
- 权限点化：档案查看/编辑/看成本/看价格/导入/成本编辑/终审。
