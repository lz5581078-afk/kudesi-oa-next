## 1. 导航树与角色可见性

### 1.1 应用外壳行为
- `AppShell.jsx`（约 633 行，单个 `App` 组件）。**没有路由器**，导航由三个状态变量驱动：`active`（页面）、`resourceView`（资料子页）、`workspaceView`（工作台子页）。localStorage 键：`oa_session`、`oa_platform_session`、`oa_navigation`。无 URL 深链。
- 左侧窄栏显示一级分组 `navGroups`，点击展开"大面板（mega panel）"显示二级/三级项。"系统"分组底部展示版本、部署时间、数据库状态（`/api/system/status`）。
- 顶栏：
  - 多行搜索（`/api/search`，按换行拆关键词，最多 100 个；返回店铺/执照/员工/任务/流程各 8 条，合计最多 20 条）。
  - 租户标签（公司名）、刷新、飞书通知提示（`FeishuNotice`）、通知铃铛（`/api/notifications` 最近 30 条）、退出登录。
- 页面数据按 scope 缓存（`page-request-cache`），scope：`resources:stores / organization / phones / fee-settings / <view>`、`process-data`、`customer`、`integrations`、`workspaces:<view>`。
- 登录后 `/api/bootstrap` 返回：公司、当前用户、accessProfile、通知(10 条)+未读数、`sessionManagerWorkspaces`、系统信息。带 `sessionWorkspaceKey` 的导航项在无权限时隐藏。
- 登录页：账号+密码；另有"申请开通公司"弹窗（公司名、联系人、手机号、管理员密码、职务、备注）。

### 1.3 角色可见性
- **老板/管理员**（`role_key` ∈ admin / company_admin / boss）：全部导航，全部权限。
- **财务（非运营非仓库）**：`fullAccess`，可看全部成本与财务。
- **运营账号**：登录后强制进入"工作台-运营"；菜单只保留 workspaces(operations、positions)、`task-system`、`finance-pricing-debug`(定价调试表)、`workflow-overview`（前端函数 `visibleForOperations`）。后端 `operations-cost-boundary` 拦截 `/api/finance*`（定价调试及 `GET /api/finance/product-bundles/options` 除外）、`/api/dashboard/boss`、`/api/integration-center`、`/api/integrations/*`，`/api/process-center`、`/api/workflow-instances/*` 强制 `canViewCosts=false` 并剥离成本字段。
- **仓库账号**：可访问 `/api/finance/product-archives/*`（商品档案）；其他受限同运营边界。
- **其他员工**：按权限键生成菜单；还原上次导航，默认进 workspaces/positions。
- 菜单项显隐 = 权限键 `menu.<group>.view` 与 `<pageId>.view` / `resources.<id>.view`，deny 覆盖 allow。
- 平台管理员：仅平台 UI，`/api/platform/*` 需平台 token。

## 2. 角色 / 岗位 / 权限模型

### 2.1 多租户
- 租户 = `companies`。`departments.company_id` 为租户锚点；`roles / positions(经 department) / employees(经 department) / 绝大多数资源表` 都带 `company_id`。迁移 0039 补齐 `roles`、`workflow_templates` 的 company_id，并把唯一约束改为按租户：roles(company_id, role_key)、positions(department_id, position_key)、responsibility_groups(company_id, group_key)、资产分类/固定资产/档案项。
- Token：`{type:'company'|'platform', companyId, employeeId, roleKey, iat, exp}`，HMAC-SHA256，默认 12 小时（`AUTH_TOKEN_TTL_SECONDS`）。`enforceApiAudience` 强制把 `req.body.companyId`、`actorId` 覆盖为 token 里的值；`/api/platform/*` 要平台 token。
- 公开路由：`/api/health`、`/api/auth/context`、`/api/auth/feishu/callback|confirm`、`/api/auth/login`、`/api/platform-auth/login`、`/api/company-applications`、商品图片上传(检查/上传)、`/api/session-manager/agent/*`。
- 登录 `/api/auth/login`：先查 `platform_admins`，再查 `employees.login_account`（**登录账号跨公司全局唯一**）；密码 scrypt+salt，`timingSafeEqual` 比较。

### 2.2 权限计算
- 管理员角色：admin / company_admin / boss（employees.role_key）→ 全部权限。
- 有效权限键 = `position_permissions`（经生效中的 `employee_positions` 与生效岗位）∪ `role_permissions`（经生效 `employee_roles`），再套 `employee_permission_overrides`（effect=allow 加，deny 减）。
- `canAdminister` = 管理员角色 或 键 `system.permissions.manage` 或 `resources.organization.manage`。
- 中间件：`/api/permissions`、`/api/admin` 需 `requireCompanyAdministration`；`/api/organization` 写操作需 `requireOrganizationMutation`；非管理员持 `resources.employees.create|edit` 只能增改员工，且不能改角色 key，不能碰管理员目标的角色/岗位绑定。
- 权限键约定（由 `SystemPages.buildPermissionTree` 从导航生成）：`menu.<group>.view`、`<pageId>.view`、`resources.<id>.{view,detail,create,edit,deactivate,delete}`；特殊键：`finance.session-manager.manage`、`resources.company-store-maintenance.manage`、`resources.stores.credentials.view`、`finance-product-base-codes.manage`、`finance-product-bundles.sync`。
- 默认角色（迁移 0002 种子）：boss、supervisor、operator、customer_service、warehouse、procurement、finance、general_admin、hr_admin。
- `employeeProfile`（`server/core/employee-profile.js`）：用正则匹配角色/职务/岗位/部门名（运营 / 仓库|仓储 / 财务）推断 `workspace='operations'`、`warehouseArchives`、`canViewCosts`（仅财务）。

### 2.3 岗位与工作台
- 部门树：`departments(parent_department_id, sort_order, is_system)`；系统部门"离职员工"（`is_system=1`）收容停用人员。
- 岗位：`positions`(department_id, position_key 部门内唯一, name, level boss/manager/staff, default_role_id, supervisor_position_id, workspace_template_key, status)。`workspace_template_key` 取自 `shared/position-workspaces.json` 的 29 个模板：operations、customer_service、customer_manager、general_admin、hr_admin、boss、warehouse_manager、print_clerk、finance、procurement、warehouse、design、content、technology、personal、assistant、shipping_staff、logistics_safety、cashier、branch_manager、sales、retail、automation_operator、finance_manager、hr_manager、operations_manager、technology_manager、content_manager、blank。未显式指定时按岗位名（可加部门）走 `legacyBindings` 回退，仍无则 `blank`；新建岗位默认 blank。
- 员工-岗位：`employee_positions`(is_primary, started_at, ended_at, status)；员工-角色：`employee_roles`(source, status)；`employees.role_key` 与 employee_roles 重复存在。
- 职责组：`responsibility_groups` + `responsibility_group_items` + `employee_responsibility_groups`。流程节点指派优先级（PRD）：职责组 > 岗位 > 角色 > 指定人员 > 直属主管 > 老板兜底。
- `/api/workspaces/access` → `{actor, permissions, denied, fullAccess, accessProfile}`；`fullAccess` = 管理员 或 财务(非运营非仓库)。`/api/workspaces/catalog` 返回岗位列表，只有 `resources.position-profiles.view` 或 fullAccess 能浏览全部岗位，其余只看自己的。`/api/workspaces/tasks` 个人任务面板（视图 new/processing/review/done，pageSize ≤ 30）。
- 工作台里的业务链接按 `${id}.view` 或 `resources.${id}.view` 过滤并尊重 deny；运营账号除"财务商品"仓库特例外不开放任何链接。

## 3. 各页面 / 模块功能清单

### 3.1 登录与平台申请
- 员工登录：账号+密码，成功后写 `last_login_at`。
- 公司申请（公开）：`company_applications`(公司名、联系人、手机、管理员登录账号=手机号、密码 hash/salt、职务、备注、status pending/approved/rejected)。
- 平台管理员（`PlatformAdminDashboard`，110 行）：指标 待处理/已开通/总数；平台级第三方应用配置表(app key 脱敏、secret 是否已配置、base URL、状态，按 production/test 环境，`PUT /api/platform/integration-app-configs/:key`，key/secret 加密+脱敏副本)；公司申请表，"通过并开通"按钮。
- 开通规则：创建 `companies`(status=normal)；创建 `finance_sales_platforms` 一行"通用 (GENERAL)"；创建 7 个默认部门(老板办/运营部/客服部/仓储部/采购部/财务部/综合部)；在老板办创建 boss 角色管理员员工，登录账号=联系手机号，**全员工范围内必须唯一，否则 409**；已通过的申请不能重复通过。

### 3.2 老板总控台 / 监督 / 其他看板（`src/dashboard/OperationalPages.jsx`）
- `BossDashboard`：今日销售/利润/异常店铺/资质+手机号预警/未关闭异常；店铺利润排行(7 天)；异常列表；利润趋势；人员异常排行。后端 `/api/dashboard/:role` 来自 `sales_snapshots`、`stores`、`phone_numbers`(status=abnormal 或 `next_recharge_at` 7 天内)、`qualifications`(异常或 30 天内到期)、`tasks`、`exceptions`。
- `SupervisionDesk`：汇总(总数/待处理/超时/完成)、开放异常、人员表、无人处理预警、监督规则(主管可见/老板可见分钟数)。PRD 规则：员工未处理主管可见，主管未处理老板可见；异常关闭必须填写原因与处理结果。
- `FeatureHome`（占位）、`OrderAppealsPage`(店铺列表 → 9 个申诉入口卡 + 记录页签，无真实数据 "待接入")、`CustomerDesk`(售后工单表 + OCR/AI 预填，使用桌面桥接截图/剪贴板，后端 `/api/after-sales`，表 `after_sales_cases`)。

### 3.3 岗位工作台（`src/workspaces/*`）
- `PositionWorkspaces`：按部门路径分组的岗位下拉，"我的岗位"标注；用岗位对应模板渲染——`operations` → `OperationsWorkspace`，其余 → `RoleWorkspaces`。
- `RoleWorkspaces`：抬头；"常用业务"快捷链接(权限过滤)；"流程与待办"页签 待我处理/我的申请/已办结(`/api/workflow-center`，每页 8，关键词搜索)；"个人任务"面板；"发起申请"(模板来自 `/api/workflow-batches/templates`、`/api/business-runs/templates`，仅可发起类型：bundle_application、purchase、product_exclusive)；"待接入业务"占位列表。
- `OperationsWorkspace`：每日经营(昨日/今日切换；营业额/推广费/利润/利润率——**目前仅演示数据，"待接入"**)；流程待办；任务区(仅演示)；发起申请分类(常用/商品/费用/人事/采购)；"常用工具"入口=定价调试表。运营工作台文档：运营账号不得看到成本/财务；定价调试只暴露公司低价，不暴露成本和利润率(后来改为可见预留利润额+比例)。
- `workspace-catalog.mjs`：各岗位链接，例如 客服→售后工单/订单申诉/店铺档案；综合行政→店铺档案/营业执照/手机号/资质证照/账号与服务/固定资产；人事行政→人员档案/组织架构/岗位档案/职责组；老板→经营总控/财务经营/兜底监督/经营历程/组织架构；财务→成本表/经营历程/草稿中心…；多个岗位带 `pending:[…]` 占位(如打单员"订单打单""面单异常与批次交接")。

### 3.4 组织架构（`src/organization/OrganizationPages.jsx` 1667 行）
- **组织架构页**：左侧部门树(拖拽排序/换父级)；中间所选部门：4 张统计卡(部门人数/在职人员/岗位数量/部门主管)、岗位卡片、成员列表(搜索)；右侧栏(下级部门/岗位/兜底规则)。"管理架构"弹窗为多栏下钻(1 级/2 级…)，可新增/编辑/删除/排序部门。**删除部门必须选择承接部门**，承接岗位、在职员工、固定资产；离职员工自动入"离职员工"系统部门；承接部门内 position_key 冲突返回 409。
- **岗位档案页**：列表列=岗位名称/岗位层级/上级岗位/默认角色/在岗人数/职责数量/状态/操作；筛选=关键词/部门/层级。详情：基础字段(名称、key、部门、层级 boss/manager/staff、默认角色、上级岗位、状态、说明)；五类职责存于 `position_duties`(category：岗位职责/入职培训/绩效考核/监督规则/流程节点说明；字段 title、description、frequency、related_module、completion_standard、is_key_duty、status)；右侧：在岗人员、岗位权限、摘要、操作日志。**删除岗位：有在岗人员或有职责则禁止，只能停用。**
- **职责组页**：新建(groupKey、name、description、scope)、职责项、绑定员工、编辑/停用/删除。
- **人员档案**（`EmployeeResourcePage`，在 resource-shared.jsx）：字段=部门、直属主管、姓名、登录账号、初始/重置密码(填账号未填密码则默认 `123456`)、基本工资、岗位、角色、role key、职责组、状态。能力：CSV 导入(预览)、导出；详情页签 人事记录/工资变更/工资发放/奖励/处罚/任务记录/审批流程记录/交接记录；工资变更自动写 `employee_compensation_records`(salary_change)。
- **员工停用/离职**：必须填原因；执行 `executeHandover`，停用 `employee_positions`、`employee_roles`。交接接口：`GET /api/organization/employees/:id/handover-preview`、`POST .../handover`；对象=task_instances/workflow_instances/exception_records/旧 tasks/旧 workflows；目标=`resolveAssignee`（同职责组→同岗位→同角色→直属主管→部门主管→老板）或手工指定；每笔写 `handover_records`；找不到则创建 `exception_records`(type=unassigned_fallback)。另有 `POST /api/assignment/scan-unassigned`、`/api/assignment/reassign`。PRD 还要求临时代理人、岗位空缺提醒（未确认已实现）。

### 3.5 用户与权限（`src/system/SystemPages.jsx` `UsersPermissionsSettings`）
- 设置员工登录账号/密码：`PUT /api/auth/employees/:id/account`（账号跨公司唯一）。
- "权限模板"=岗位：`PUT /api/permissions/employees/:id/position`（**同时改写员工部门和职务为该岗位的**）。
- 员工个人允许/拒绝覆盖：`PUT .../overrides`；编辑岗位权限 `PUT /api/permissions/positions/:id/permissions`；角色权限 `PUT /api/permissions/roles/:id/permissions`；设置角色 `PUT /api/permissions/employees/:id/role`（同时写 `employees.role_key`）。
- 权限树来自导航自动生成。

### 3.9 店铺档案（`StoreResourcePage` 2612 行，`/api/resources/stores*`）

## 5. 现有 UI / 操作逻辑问题（新系统设计应避免）

### 5.1 页面和文件过大
- 前端：`FinanceProductArchivePage` 5544 行、`FinanceArchivePage` 3880、`ResourceDetailPages` 3413（合作人/商标/自媒体/账号备忘/银行/宽带/微信共用一个文件）、`ExpressPriceTablePage` 2940、`BusinessLicensePage` 2912、`PhoneNumberPage` 2707（内部还塞了 `TaxProfilePage`、`QualificationResourcePage`）、`StoreResourcePage` 2612、`FinanceProductBaseCodePageV5` 2544、`ResourcesDesk` 2545、`resource-shared` 2541、`WorkflowDesigner` 2017、`OrganizationPages` 1667、`SystemPages` 1130。
- 后端：`server/index.js` 13202 行，路由、建表辅助、业务逻辑全在一个单体文件（认证/组织约 3755-6900，资料约 6896-10500，集成约 10510-11090，流程/任务约 11090-12700）。

### 5.2 外壳与导航
- `AppShell.jsx` 一个组件约 35 个 `useState`，靠长 if 链 `rawContent` 渲染页面；**没有路由、没有 URL 深链**，刷新/分享链接无法定位页面。
- 同一页面要在 3 处同步登记：`AppShell.getPageKey`、`getResourcePageUrl`、`standaloneResourceViews`；scope 字符串散落。
- `page-loaders.js` / `page-registry.js` 用 `createPageLoaders(deps)` 注入约 90 个依赖，每页是 `createXxxPage(deps)` 工厂，耦合重、难测试。
- 导航层级深且量大：财务大面板约 70 个入口；"资料"约 25 页；一次要展开大面板再点三级。
- 16 个岗位工作台既在"工作台"分组直接列出，又能在"岗位总览"下拉里选择，**两条路径同一功能**。
- "人员档案"在资料与组织两处出现；"用户和权限"与"岗位档案"都能编辑岗位权限，职能重叠。
- 占位/半成品入口留在导航：功能首页、订单申诉、聚水潭同步能力中心(静态)、OCR 设置(说明页)、工作台各种 `pending` 占位、运营工作台营业额/利润仅演示数据。软件账号有资源无入口。

### 5.3 重复版本与重复代码
- `FinanceProductBaseCodePage.jsx`(143 行桩) + V2/V3/V4/V5（V5 才是在用）；`FinanceCostTablePage` + V2/V3；`FinanceProductBundleCodePage` / V2 / `FinanceProductBundlePage`；商品基础编码 CSS 三份（`.css`、`-v3.css`、`-v4.css`）。
- 后端同类：`product-base-codes` / `-v2` / `-v3`、`sku-cost-engine` / `-preview-v2` / `-preview-v3`、`auxiliary-cost-excel-utils` / `-v2`。
- `LicenseRecordModal`、`RelationMiniList` 在多个文件重复定义。
- 每个资料页各自实现一套 CSV 导入/导出/模板/说明/删除原因/详情原位编辑逻辑（各数百行），表单字段同时在 `fields` 与 `createFields` 两套配置里维护。
- 前端 `navigation-state.isOperationsSession` 与后端 `employee-profile` 用同一套正则重复判断运营/财务/仓库。

### 5.4 权限与安全问题
- 权限键由导航自动生成，但服务端**大多数 `/api/resources/*` 路由并不校验 `resources.*.view/create/edit`**，只有少数特殊键真正强制，菜单隐藏≠接口受限。
- 运营/财务/仓库身份靠**名称正则**推断（职务/岗位/部门名），改名即变权限，非常脆弱。
- `role_key` 与 `employee_roles` 双份存储；"权限模板=岗位"会**覆盖员工的部门和职务**，副作用隐蔽。
- 多个处理器默认 `actorId = 1`；平台管理员审批的 `platformAdminId` 取自请求体。
- `GET /api/permissions/positions` 的 `position_permissions` 查询无 company 过滤（跨租户泄漏）；`PUT .../positions/:id/permissions` 对岗位归属公司的校验只靠部门查询。
- 敏感信息：合作人身份证号/银行卡号、执照银行账号明文；默认密码 `123456`；加密密钥缺省回退硬编码 `'kudesi-oa-local-secret'`；登录账号跨租户唯一（公司开通用手机号作账号会撞号）。
- 删除执照/店铺会硬删 `sales_snapshots` 并置空大量外键，难以恢复。

### 5.5 操作繁琐
- 执照/店铺/手机号详情模块过多，店铺详情 15+ 模块需手动拖拽排序和折叠，偏好分散在 localStorage 和服务端两处。
- 停用/删除必填原因的弹窗在每个资源重复，层层确认；执照新增后会自动联动创建手机、合作人、税务、银行档案，用户不易察觉、难以撤销。
- 手机号表单随 `usage_type` 变化字段，同一手机号还要在"绑定关系"面板另行绑平台店铺；一个号码多平台绑定，列表却按平台拆列，导入列繁杂。
- 资料首次加载整个 scope 的全部行（workspace 接口），图片懒加载补丁式处理；列表分页和全量加载并存。
- 店铺领取规则（配额、合规、回收）只是界面文字，未落地，容易让用户误以为已生效。
- 员工离职交接分散在停用对话、交接预览、`assignment` 扫描三处，没有统一入口。

### 5.6 对重写的设计建议（基于以上）
1. 引入真实路由与 URL 深链；导航用单一注册表（页面 id、权限键、scope、角色可见性）一处定义。
2. 资料页用通用"资源引擎"：配置驱动的列表/详情/表单/导入导出/日志/停用原因，特殊页只扩展模块。
3. 权限改为服务端统一中间件强制 `resource.action`；岗位/角色/覆盖三层合一并显式存储"工作台类型"，不要用名称正则。
4. 岗位工作台只保留一个入口（按本人岗位自动进入，管理员可切换）。
5. 密钥与证件号全部加密，密钥必须来自环境配置，去掉默认密码和硬编码回退。
6. 关联关系统一用 `resource_links` 模型并在详情页集中展示；导入前预览、导入后可恢复沿用。
7. 后端按模块拆分（auth / organization / resources / workspaces / platform），去掉 V2/V3 并行版本。
