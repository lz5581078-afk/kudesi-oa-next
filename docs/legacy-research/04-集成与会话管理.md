研究方式：只读。以下规则均来自源码与 docs，结论后括号内标出主要出处。"（文档）"= 仅 docs 描述，"（代码）"= 已读代码核实。

## 1. 聚水潭（Jushuitan, JST）集成

### 1.1 授权与调用层（代码：`modules/integrations/jushuitan/routes.js` 前 140 行，`server/index.js` 10589 附近）

- 数据模型三层：`integrations`（集成目录，key=`jushuitan`/`feishu`）→ `integration_app_configs`（平台级 app_key/app_secret，加密，`environment=production`）→ `integration_accounts`（**每企业一条**授权账号：`coid`、`access_token`、`refresh_token`、`token_expires_at`、`authorized_shop_scope`、`base_url`、`auth_status`）。
- 运行时（`getJushuitanRuntime`）：取平台 key/secret + 企业 access_token 解密；缺任何一项直接 400。返回 `account{id,name,coid,authStatus,tokenExpiresAt}`。
- 签名：`MD5(app_secret + 按参数名 ASCII 排序的 key+value 拼接)`，公共参数 `app_key/access_token/timestamp(秒)/charset=utf-8/version=2/biz(JSON)/sign`，POST `application/x-www-form-urlencoded`，超时 30 秒，响应 `code!=0` 视为失败并带 `error.remote=原始响应`。
- **没有 token 自动刷新**：全库搜索 `refresh_token` 只出现在"保存/脱敏展示"，没有刷新调用。token 过期靠人工在页面重新填写（"更新账号"接口 `PUT /api/integrations/jushuitan/account`，token 为空则保持旧值）。系统告警通道里有"授权到期前 24 小时"提醒（飞书系统助手，见 §2）。
- 前端永远只拿到 `access_token_configured: true/false` 与脱敏串，不返回明文（文档要求：不要把 token/密钥/完整原始响应返回浏览器）。
- 限流：`createCategorySyncTransport`（代码）——所有出站调用串行（Promise 链）、两次调用间隔 400ms；命中限流（code 429 或文案含"频繁/限流/too many"）时指数冷却 1500×2^n ms；**只有读接口可重试（最多 3 次），写接口永不盲重试**，直接抛"调用频率受限，已暂停操作"。
- 已实测通过的接口（文档）：`/open/shops/query`、`/open/logisticscompany/query`、`/open/wms/partner/query`、`/open/orders/single/query`、`/open/orders/out/simple/query`、`/open/sku/query`、`/open/skumap/query`、`/open/mall/item/query`、`/open/combine/sku/query`、`/open/category/query`、`/open/refund/single/query`、`/open/aftersale/received/query`、`/open/supplier/query`、`/open/purchase/query`、`/open/inventory/query`、`/open/inventory/count/query`、`/open/allocate/query`。写接口只实际使用：`/open/jushuitan/itemsku/upload`（普通商品）、`/open/item/combinesku/upload`（组合装）、`/open/webapi/itemapi/category/addorupdate`（分类）。

### 1.2 通用"外部动作"基础设施（核心设计，新系统应沿用思想）

**A. 外部动作授权规则 `workflow_external_sync_rules(company_id, action_key, enabled, target_key, authorized_by)`**
- 每个动作（`jushuitan_category_sync`、`jushuitan_bundle_category_sync`、`jushuitan_product_sync`、`jushuitan_bundle_sync`、`jushuitan_product_disable`、`jushuitan_bundle_disable`、`jushuitan_bundle_price_sync`）每企业一行，**必须管理员显式启用**才会产生事件；`target_key = sha256(账号id + coid + appKey + baseUrl)`，即"授权目标指纹"。
- 目标指纹变化（换账号/换 coid/换 baseUrl/换 appKey）→ 所有自动动作停止，要求人工重新核对并重新授权。文档原话：更换授权目标后须重新开通。

**B. 事件队列 `workflow_external_sync_events(id, company_id, action_key, source_id, operation, status, message, finished_at)`**
- 业务事务内 `INSERT`（与业务数据同一事务提交，回滚则不产生事件；不用 MySQL 触发器、不需要 SUPER 权限——靠应用数据库访问层在事务内记录）。`enqueue()` 用 `INSERT…SELECT FROM rules WHERE enabled=1`，没有启用规则则 `affectedRows=0` → 409"请先由管理员确认并启用该企业的外部同步动作"。
- 调度器：进程内 `setTimeout` 每秒 `drain()`，按 `(company_id, action_key)` 分组取最早 pending（每轮最多 10 组）→ 调对应 action handler。`busy` 标志防重入。状态：`pending / paused / success / failed`（商品同步另有"confirming"表达在业务状态表，不在事件表）。
- 合并语义：事件只是"信号"，执行时读取**当前最终状态**，同一时刻多个事件合并成一次；执行以 `MAX(id)` 为截止（cutoff），后提交的事件留给下一轮。
- **没有统一的"禁用全部工作器"开关**（CLAUDE.md 明确说明）：恢复生产库到别处时，后端启动即会启动同步/通知/超时三个工作器。

**C. 通用防事故规则（每个出站同步都遵守，是业务规则的精华）**
1. **预览 → 签名 → 确认**：手动操作先"刷新差异/预览"，返回 `signature`（对计划+本地快照的 hash）；执行接口必须回传同一 signature，否则报"两端资料已变化，请刷新差异后重新确认"。
2. **写入前再读**：每次写之前再读 OA 最新数据、再取授权运行时、再读远端快照，任何一项与预览时不一致即停止剩余操作（已成功的保留）。
3. **写入意图先落库**（pending_json / uncertain 状态）再发请求；结果不确定（超时、响应缺字段、进程崩溃）**只回查、绝不重发**；明确拒绝（code≠0 的结构化错误）才允许人工修正后重试。
4. **写后回查**：写完立即读远端并逐字段比对；比对通过才标记成功；回查未一致进入 `confirming`，后台 10/30/60 秒各回查一次（共 3 轮，`next_check_at` + `confirmation_attempts` 持久化，重启不丢），耗尽后标失败并保留证据，**不得重新上传**。
5. **不接管/不覆盖**：远端已有同编码商品但 OA 没有"已关联"记录 → 禁止覆盖；远端与上次成功快照不同 → 报"已被其他操作修改，请核对差异"，不提供强制覆盖。
6. **锁**：MySQL 命名锁 `GET_LOCK(name,0)`（不等待，拿不到就返回/报"正在执行"）：`oa:jst:category:{companyId}`、`oa:jst:products:{companyId}`、`oa:jst:bundles:{companyId}`（组合装上传、组合调价、组合禁用共用）。商品同步与"来源删除禁用"共用公司商品锁，避免交错。
7. **去重按"真身"**：商品有"真实商品（canonical）+ 马甲（alias，canonical_base_code_id 指向真身）"，上传一律按真身字段，多个马甲的验证事件可以保留但实际写入按真身串行，资料未变则跳过。
8. **每次写入留证据**：`*_logs` 表保存上传响应、每次回查值、逐字段差异（`evidence_json`），UI 的"记录"可展开 OA 值 vs 聚水潭值。
9. **读响应不完整即失败**：分页缺失、重复记录、`code≠0`、`datas` 非数组 → 一律停止，不"尽力而为"。

### 1.3 分类同步（`category-sync-service.js` / `category-sync-plan.js` / `docs/商品分类聚水潭同步.md`）

- 范围：仅商品基础编码分类（`finance_product_code_dictionary.dictionary_type='product_category'`）；组合编码分类有**独立一套**同样服务（`dictionaryType='bundle_category'`，action `jushuitan_bundle_category_sync`，路由 `/api/finance/jushuitan/bundle-category-sync`）。两者的映射互不串。
- 映射表 `jst_category_sync_links(company_id, target_key, dictionary_type, local_id, remote_id, local_json, remote_json, pending_json, status)`，唯一键 `(company_id,target_key,remote_id)`。link 状态：`linked / uncertain / rejected / retired`。
- 运行日志 `jst_category_outbound_runs(mode, status, details_json…)`；旧的拉取日志 `jst_category_sync_runs` 保留不删（迁移 0136 把旧数据复制到新表以避免冲突——历史包袱）。
- 流程：
  1. **读远端**：`/open/category/query` 分页 100/页，最多 500 页；`has_next` / `page_count` / 短页 三种判断；任何重复/缺页/超限直接报错。
  2. **构造计划 `buildPlan`**：操作类型 `create / update / bind(关联已有) / disable / retire / conflict`；父先于子创建，子先于父停用；有未知子级则禁止停用父级。
  3. **首次同名同父级分类不自动认领**，只允许在手动差异确认后"关联已有分类"。
  4. 删除 = 远端 `enable:false`（聚水潭无物理删除），本地 link 变 `retired`；停用后远端查询可能直接查不到，视为预期终态。
  5. 写 `addorupdate`：`c_name, parent_c_id, sort, enable, is_pv:false`（有 remoteId 则带 `c_id`）；回查通过 `remoteMatches` 比对；聚水潭不返回排序/启用时只能"按 OA 配置写入"，UI 提示"无法判断远端是否单独修改"。
- **自动同步开关**：默认关闭；开启条件 = 手动核对后差异为 0 + 勾选"每次分类操作均自动写入聚水潭" + 授权目标与预览一致。开启写 rule + 一条 `activation` 事件；关闭则把 pending 事件置 `paused`。授权目标变更自动停止（`rule.target_key !== plan.targetKey`）。
- `ensureCategory(categoryId)`：商品上传前强制保证其分类链已同步（"依赖分类"），并校验：分类末级、未停用、远端无同名分类（因 JST 商品只能用分类名定位）、关联未漂移。分类就绪后 `onSynchronized → resumeCategories` 自动把因"分类未同步"而 blocked 的商品重新排队。
- 失败重试 `retryFailed`：只重排队"当前仍有效分类"对应的失败事件，不处理旧停用冲突。

### 1.4 普通商品（基础编码）同步（`product-sync-service.js`、`docs/商品基础编码聚水潭同步.md`）

**要上传的字段（11 个，全部逐项回查严格比对）**：`sku_id(真实商品编码)`、`i_id(款式编码)`、`name`、`short_name`、`properties_value(颜色及规格)`、`c_name(分类)`、`brand`（原料/发货物料无品牌则不发送）、`unit(系统规格)`、`weight(kg)`、`cost_price(总成本价)`、`purchase_price`。重量比较容忍聚水潭 4 位小数精度（`round(x*10000)/10000`），其余缺失即不一致。

**状态机 `jst_product_outbound_states.status`**：
`blocked`（资料待补齐/编码变化未确认）→ `pending`（排队）→ `confirming`（已写入，等回查）→ `success` / `failed`；另有 UI 虚拟状态 `unsynced`（当前资料签名≠已同步签名）。
- 业务验证与外部同步是**两件事**：人工"验证"通过后才可同步；验证提交与同步事件在同一事务落库；旧的已验证资料**不自动批量上传**，需单条同步或集中维护明确提交（每批最多 50 项且必须勾选确认）。
- 关键判断（drain 内）：
  - 签名 `desired_signature = hash([item, 验证快照签名, targetKey])`；验证后资料/授权/验证状态变化 → "验证后资料已变化，停止上传"。
  - 读远端 `/open/sku/query`（必须带 `flds` 显式列出字段，否则返回字段被裁剪；分类用 `c_id` 经 link 表反查 OA 分类名，不按路径后缀猜）。
  - `远端存在且一致`：若本地没有关联记录且没有待确认意图 → "未建立同步关系，禁止自动覆盖"（即使名称相同）。
  - `远端存在但与上次成功快照不同` → 冲突，停止。`远端不存在但本地有 uploaded_code` → "禁止自动重新创建"。
  - 写入：保存 `pending_json=item` → 调 `/open/jushuitan/itemsku/upload`（`{items:[item]}`）→ 解析 `rejectedResponse`（is_success=false / code≠0）→ 立刻回查 → 不一致则 `confirming`。
  - 成功后写 `uploaded_code / uploaded_json`，清 `pending_json`。
- **改码（商品编码变化）**：聚水潭官方**没有 SKU 改码接口**（`聚水潭商品改码接口核查.md` 在沙箱做了大量试验：新 sku_id+原 autoid、`is_update`、`old_sku_id/new_sku_id`、`auto_id` 等组合全部变成"新增独立商品"，且接口返回"成功"但并未改码；仅 `i_id`、`sku_code` 可更新）。因此：
  - 默认：编码变化 → `blocked`，提示"编码已变化，不会自动另建"。
  - 用户确认的替代方案"**禁用旧码 + 新建新码**"（`product-code-replacement.js`，`replacement_json` 保存授权/旧新编码/真身与马甲备份/旧商品回查资料/阶段）：阶段 `approved → disable_pending → disabled → create_pending → verified`，每阶段先持久化再发送；旧商品必须"启用状态且 autoid 可核实且与上次上传资料一致"；新编码已存在即停止（不接管）；旧码禁用回查通过才建新码；新商品只用 OA 已验证资料，**不复制旧商品销售价/市场价/其他价格**；完成不代表历史库存/在途订单/组合装/店铺映射已迁移（确认勾选文案要求人工已处理）。
  - "删除后重建"方案被明确阻塞（公开 API 没有删除接口），文档列出了解锁证据清单。
- **来源已删除编码 → 禁用**（`product-disable-service.js`，action `jushuitan_product_disable`）：二次验证列表中"来源已删除"行可删除；本地 `status='deleted'` 归档（保留身份、关联、验证、成本、同步记录，**编码永不释放复用**）；与禁用任务在同一事务提交，任务存于 `finance_product_base_code_logs(action='source_delete', request_json, response_json)`（复用日志表，不新增表）。禁用请求仅 `{sku_id,i_id,name,enabled:-1}`；先读远端校验 款式/名称/autoid；远端不存在→记"无需禁用"（不调新建）；若原上传结果待确认，则持续回查而不当作"不存在"，也不重发上传；回查为禁用或确认不存在才完成；10/30/60 秒回查。需要服务器重新检查：来源确已不存在、无组合 BOM 引用、无未完成 SKU 申请、无成本配置/未完成换码；确认窗口必须填原因并勾选禁用。

### 1.5 组合装同步（`bundle-sync-service.js`）

- 复用商品同步引擎（`createProductSyncService` 传入 adapter）：状态表 `jst_bundle_outbound_states`、日志表 `jst_bundle_outbound_logs`（建表时 `LIKE` 商品表）。
- 字段：`sku_id(组合编码)`、`i_id`、`name`、`properties_value`、`childList[{src_sku_id, qty}]`（同 SKU 合并、按编码排序、qty 必须正整数）、`compose_sale_price`。
- 读写接口：`/open/combine/sku/query`、`/open/item/combinesku/upload`（body `{is_cover: 已关联?, is_null_cover:false, items:[…]}`）。
- **依赖检查 `assertDependencies`**：每个组成商品必须"已验证 + 无资料问题 + 已同步成功 + 签名与最近成功快照一致 + 目标账号一致 + 远端回查一致"；组成商品正在 pending/confirming → 组合装 `dependencyPending`，10 秒后重试，最多 12 轮；还要求"组合基本售价待回查"已结束。
- 组合装的分类不能绑定到组合装接口（只同步到分类库）。
- 权限：组合装同步用独立权限 `finance-product-bundles.sync`（管理员角色 admin/company_admin/boss 直通，且**个人 deny 覆盖优先，对管理员也生效**）；普通商品同步用 `requireCompanyAdministration`。
- 组合装"归档/删除禁用"：`bundle-disable-service.js`（同商品禁用思路）。

### 1.6 组合装基本售价同步（`bundle-price-sync.js`、`docs/组合装基本售价同步.md`，2026-10-13 用户确认）

- 口径：`compose_sale_price = SKU 成本表最低售价 = (预发货成本 + 当前有效预估运费) / (1 - 生效利润率)`，**向上取整到分**；利润率沿用单品覆盖 > 分类及上级继承 > 全局默认；0% 有效；缺运费或利润率则阻止（不以 0 兜底）。与成本表共用 `loadPricingContext/serialize/minimumSellingPrice`，保证网页与同步口径一致。

## 2. 飞书（`feishu.js`、`feishu-channels.js`、`docs/飞书通知接入.md`）

### 2.1 目的与范围
飞书应用机器人 = 默认通知渠道；**通知不得阻断 OA 待办办理**；收件人沿用流程中心/任务权限，不硬编码；**不向运营暴露成本**；同一待办不得同时按"流程/任务/普通通知"重复发送。

### 2.2 六个通道（每个是一个独立飞书企业自建应用，共用账号绑定、队列、日志）
| channel_key | 应用 | 触发源 |
|---|---|---|
| flow | 小白流程助手 | 流程节点待办、退回、办理结果；SKU 申请通过通知；通用流程节点任务（排除 SKU 避免重复） |
| task | 小白任务助手 | 独立任务分配、负责人变更、完成/待复核（复核事件随提交版本去重） |
| supervision | 小白督促助手 | 任务/节点临期、逾期、人工催办（节点时效：SKU 仓库、财务各 60 分钟，提前 20/10 分钟提醒，超时满 5 分钟起每 5 分钟提醒，完成后停止，退回重新计时） |
| notice | 小白通知助手 | 站内通知、非 SKU 任务完成告知（不外发业务正文/表单/附件） |
| business | 小白经营助手 | 真实成本变更记录，通知有财务维护权限的操作人（不传价格/核算快照） |
| system | 小白系统助手 | 商品/组合装同步失败、接口后台任务失败、接口授权到期（提前 24h，需配置启用）；只发显式配置的管理人员；不传密钥/原始错误/成本 |

### 2.3 账号绑定（OAuth）
- 员工本人授权绑定，禁止手填他人飞书 ID 或按姓名猜测。流程：`POST /binding/start`（生成一次性 state，写 `oa_feishu_states`，10 分钟有效，浏览器 HttpOnly Cookie 校验）→ 飞书授权页 → `GET /api/auth/feishu/callback`（状态机 `pending → awaiting_confirmation → authorized → completed`，含二次确认 `confirm`）→ `POST /binding/complete`。员工已停用/企业身份(tenant_key)不同则拒绝。只取身份标识，不取手机号/邮箱/聊天；不保存用户令牌。
- 跨应用身份：app 专属 `open_id` 不可复用；其他应用用 `union_id` 发送，旧绑定缺 union_id 时补一次。
- 未绑定员工登录后提示绑定；仓储成员需各自绑定后才会外部提醒，站内待办不受影响。

### 2.4 队列与可靠性
- 表：`oa_feishu_settings`（企业飞书配置：app_id、`secret_cipher` 加密、tenant_key、origin）、`oa_feishu_bindings`、`oa_feishu_states`、`oa_feishu_outbox`（SKU 旧队列）、`oa_feishu_channels`（各通道 app_id、secret_cipher、enabled、`recipients_json`、基线 floor）、`oa_feishu_messages`（通道新队列）；另有早期占位表 `feishu_user_mappings`、`feishu_message_logs`（已不再使用）。
- 发送循环：每个 tick 先（每 30 秒）扫描各启用通道产生候选；再事务内领取一组 → `status='sending'`，租约 5 分钟，同 `(company, employee, channel, node…)` **合并成一条卡片**；发送前对每条重新验证（员工在职、部门成员资格、待办仍有效、权限未撤销、期限未变），失效的置 `cancelled`（部分失效不虚报已发送）；发送使用持久化 UUID 作为飞书幂等 uuid；失败 `attempts<6` → `pending` 且 5 分钟后重试，否则 `failed`。
- **首次配置保存各数据源基线，历史事项不补发**；审核通过通知"在最终审核落库的同一事务内入队"，校验/退回/取消/失败事务不发；"审核通过≠聚水潭同步成功"。
- 管理页：顶部飞书通知、机器人设置、发送记录、"仅向管理员本人测试"。旧的"演示发送成功"接口 `test-notification` 已停用返回 410。
- 现状遗留：6 个应用 App ID 写死在源码（`cli_aa4e…`）；密钥加密存库。

## 4. 会话管理（Session Manager）——店铺托管浏览器 + Windows 助手 + 远程协助

### 4.1 产品定位与硬性原则（`session-manager-release-checklist.md` + 代码）
- 目的：多平台（拼多多 pdd、淘宝/天猫、抖音电商、快手电商、京东）店铺的"独立登录环境"。每家店铺在**授权的 Windows 电脑**上有一个独立 Chrome for Testing Profile；员工在 OA 点"立即登录/首次登录"，由该电脑上的助手打开店铺后台；需要时别的员工经 WebRTC 远程协助操作该浏览器。
- **本机优先（local only）**：登录态（Cookie/Profile）**只保存在授权电脑本机**，不上传云端。agent `sessions.js` 里 `publishSessionState / syncPendingSession…` 全是返回 `{mode:'local_only', disabled:true}` 的空函数；服务端 `overview-service` 把 `remoteVersion/recoverableVersion/hasRemote` 写死为 0/false。
  - **但**迁移 0079 建的"加密云端登录态"表仍在：`session_versions`（encrypted_state + iv + tag + hash）、`session_device_keys`（每设备封装密钥）、`session_device_shop_bindings.session_version/applied_session_version`，且验收清单第 5 节"设备 B 加密恢复"仍描述该能力。**文档与现实不一致：云端加密恢复已被关闭，表是遗留。**
- 禁止行为（清单第 8 节扫描必须为零）：自动上架/填写/点击/提交/推广、指纹伪装、验证码绕过、敏感信息入日志；证据不得含 Cookie/Token/私钥/二维码/验证码/完整密文/密码/Profile 内容。注意其中含"远程鼠标键盘"，与现有"安全标签页内远程点击/拖动/滚动/键盘文本输入"的功能存在字面矛盾（实际策略：只允许浏览器内输入，禁止全局 Windows 输入）。

### 4.2 工作区（workspace）与权限
- 同一套页面/接口用 `session_workspaces(company_id, workspace_key, permission_key)` 区分两个工作区，所有表都带 `workspace_id`（0088 迁移回填为 finance_withdrawal）：
  - `finance_withdrawal`「店铺提现」权限 `finance.session-manager.manage`，凭据标签"提现运营账号/密码"，导航在经营财务下；
  - `company_store_maintenance`「公司店铺维护」权限 `resources.company-store-maintenance.manage`，凭据标签"主账号/主账号密码"，**额外提供"店铺档案状态"管理**（正常/异常(必选异常原因)/注销/停用，直接改 `stores.status`，写审计）。
- 前端请求带 `X-Session-Workspace` 头或 `workspaceKey` 查询参数；`/agent/*` 路径不走工作区/权限校验，走设备令牌认证。
- 权限判定 `canManageSessionDevices`：员工在职 + (管理员角色 admin/company_admin/boss) 或 (职位/角色/个人 allow 授予且无个人 deny)。**个人 deny 优先**。
- 店铺凭据：`resources.stores.credentials.view` 另控店铺密码查看（`canViewBusinessSecrets`）。

### 4.3 用户可见功能（`SessionManagerPage.jsx` 三个标签）
**① 登录状态（店铺列表）**
- 工具栏：搜索（平台/运营/店铺名/编码/平台店铺ID）、店铺状态筛选(公司店铺维护才有)、本机登录态筛选（登录有效/过期/未登录/待验证/异常）、负责电脑筛选(全部/未分配/具体电脑)、`添加店铺`、`刷新`；分页（默认 50，10–200 可调，服务端上限 200）；多列可排序。
- 列：店铺名、平台、运营（当前领取人）、店铺编码/平台店铺ID、登录状态徽标、最近验证/打开时间、负责电脑（行内下拉改绑）、凭据账号/密码（行内编辑，失焦自动保存，密码默认掩码，"查看/复制"会写审计）、自动登录开关、打开进度条、操作按钮。

**② 授权电脑**
- 生成一次性绑定码（8 位，字母表去掉易混字符 I/O/0/1，10 分钟有效，哈希入库，使用即失效，第二次使用必须失败）；Windows 助手下载（显示最新版本/大小/SHA-256/是否已签名）；设备表：电脑名/备注(≤80)/设备编号(12 位)/系统/助手版本/店铺数/最近心跳/状态（含更新进度）；操作：撤销、恢复(重置 last_seen)、删除(必须先撤销，且不能仍负责店铺)、改备注、单台/全部"远程更新助手"。撤销立即终止该设备所有远程会话，心跳/任务领取返回未授权。

- 最近 100 条安全审计：`session_audit_logs(event_type, outcome, summary≤500, device, store, open_request, request_id)`；事件含 managed_shops_added/removed/assigned、device_registered/revoked/restored/deleted、shop_open_completed/failed、凭据更新/清除/查看/复制、自动登录开关、`store_auto_login_credentials_delivered`、store_archive_status_updated 等。日志不记录 Cookie/Token/密码。
**④ 远程协助对话框（拼多多等，`PddRemoteAssistDialog.jsx`，约 1000 行）**
- 步骤：请求远程电脑 → 等待助手打开店铺浏览器 → 等待助手连接 → WebRTC 协商 → 已连接（显示是否 TURN 中继）→ 操作画面。
- 视频：`操作画面/移动画面`切换、适应窗口、缩放、全屏、**画质 自动/清晰(6Mbps)/均衡(4Mbps)/流畅(2Mbps)**（自动按 RTT≥260ms、丢包≥5%、丢帧、可用带宽自适应降档，需连续 6 个样本降、25 个样本升）。
- 输入：点击、双击、拖动(实时轨迹)、滚动、键盘按键/文本、上/下一个标签页、关闭标签页；输入通道最多 1 个在途命令（`MAX_PENDING_INPUT_COMMANDS=1`），16KB 上限，命令有确认回执（"操作发送中/成功/失败/确认超时"）。
- 恢复：断线自动 ICE restart（最多 2 次，间隔 1.5s）；"重试实时连接/恢复连接"；失败可降级到 **JPEG 帧回退传输**（`transport_mode='jpeg_fallback'`，助手上传 JPEG ≤900KB 存 `frame_data MEDIUMBLOB`，前端轮询取帧；点击/拖动/滚动命令入 `session_remote_commands` 表由助手领取执行并回报）。
- 结束：`结束远程操作`（含安全关闭浏览器：停止远程控制 → 通知助手 → 安全保存本机 Profile → 关闭浏览器 → "店铺已安全关闭"，60 秒无进展超时，可"重试关闭"）与`仅退出界面`（不关浏览器）。

### 4.4 打开店铺流程与状态机
**`session_open_requests`**（action: `first_login`(此设备此店铺从未成功打开) / `immediate_login`；`dispatch_mode` 默认 remote）
- 状态：`queued → claimed → running / waiting_human / opening / restoring / waiting_login → completed | failed | cancelled`。进度单调不倒退（倒退报错）；终态不可再改（相同终态幂等返回 `unchanged`）。
- 租约：助手领取后租约 30 秒（`REQUEST_LEASE_MS`），助手每 10 秒续进度；服务端每次创建/查询时把过期未续的 claimed 以外活动请求标 `failed / OPEN_REQUEST_LEASE_EXPIRED / "打开任务心跳已超时，请重新连接"`；`queued` 不过期；过期的 `claimed` 可被重新领取。
- 创建前置校验（事务内 `FOR UPDATE`）：店铺已加入工作区；**已分配负责电脑**且与请求目标一致；电脑 active 且**心跳 ≤15 秒**（"助手离线，无法打开店铺"）；平台受支持；该设备**同时只能有一个店铺浏览器**（另一店铺 open/closing 时分别提示"请先结束远程操作并安全关闭"/"正在安全关闭当前店铺…"）；同店同设备无进行中请求。
- 助手端（`agent/open-shop.js`）步骤与进度：`opening_profile 20 → checking_local 35 → auto_login 55 → waiting_login 70 → verifying 85 → completed 100`。有本机有效登录态直接进后台；否则若服务端下发了一次性解密凭据且适配器支持 → 自动输入账号密码（平台适配：pdd / taobao / douyin / kuaishou / jd 各有选择器配置）；遇验证码/短信 → `LOGIN_VERIFICATION_REQUIRED`，转人工在远程窗口完成（最长 30 分钟）；之后 **稳定性验证**（`platform_page_stable_v2`：连续 ≥2 次检测、≥2 个信号、URL 属于平台允许域名、无可见登录表单），生成"认证证据"上报；服务端要求 `valid` 必须带证据且 30 分钟内、域名白名单通过，否则拒绝。
- 自动登录凭据：仅当店铺 `auto_login_enabled=1` 时，**助手领取请求那一刻**才解密店铺凭据并一次性下发（`Cache-Control: no-store`），写审计 `store_auto_login_credentials_delivered`；解密失败不阻止打开，退化为人工登录。助手侧用后即置空。
- 本机登录状态 `login_status`：`pending / synced / valid / expired / error`；转换表 pending→{valid,error}；valid→{valid,expired,error}；expired→{pending,valid,error}；error→{pending,valid}。

### 4.5 托管浏览器会话与远程会话
- `managed_browser_sessions`（status `open → closing → closed | error`；`last_agent_at` 由助手心跳带上 `activeBrowserSessionIds` 更新）。
- `session_remote_sessions`：status `requested → connected → closing → ended | closed | expired | error`，有效期 **10 分钟**（`REMOTE_SESSION_SECONDS=600`，可续期 `heartbeat`），存活判断 45 秒，关闭超时 60 秒，**远程所需最低助手版本 0.2.5**（低于则拒绝）；仅创建者本人可操作自己的会话(user_id 校验)；页面离开平台允许域名（`isAllowedPlatformUrl`：https + 域名白名单/后缀，含拒绝名单）则 403 终止；设备撤销/浏览器关闭时终止相关远程会话。
- WebRTC：`POST /remote-sessions/:id/webrtc-ticket` 发 **30 秒一次性票据**（内存 Map，sha256 摘要保存，按角色 viewer/agent）；WebSocket 信令路径 `/api/session-manager/webrtc`，挂在 `httpServer`（`webrtc-signaling-server.js`）；ICE：STUN/TURN 配置 `WEBRTC_STUN_URLS / WEBRTC_TURN_URLS / WEBRTC_TURN_SHARED_SECRET`（TURN REST 临时凭据，TTL 10 分钟），`WEBRTC_FORCE_RELAY=true` 强制中继。票据在进程内存，**多实例/重启即失效**。
- 助手侧视频采集：C#/.NET 10 sidecar（`Kudesi.RemoteCapture`，Windows Graphics Capture，`BoundedLatestFrameQueue`）+ C++ 原生 WebRTC bridge（`agent/native/webrtc-bridge`，Media Foundation 硬件 H.264 编码）+ Node `webrtc-assistance.js`；输入注入 `remote-input.js`（限定在受管浏览器内）。

## 7. 数据加密（business secrets）

- 算法：AES-256-GCM，12 字节随机 IV，密钥 = `sha256(密钥文本)`。密文格式：业务秘密 `enc:v1:{iv}:{tag}:{cipher}`（base64）；集成秘密（app_secret/token/AI key/飞书 secret）是**无前缀**的 `{iv}:{tag}:{cipher}`。**两套实现**：`server/core/business-secrets.js` 的 `createBusinessSecretCodec` 与 `index.js` 内联的 `encryptSecret/decryptSecret`，密钥来源一致但后者不支持旧密钥回退、解密格式不对时静默返回空串。
- 密钥来源优先级：加密 `SECRET_KEY → SESSION_SECRET → JWT_SECRET → 硬编码开发回退 'kudesi-oa-local-secret'`；登录签名另有优先级 `SESSION_SECRET → JWT_SECRET → SECRET_KEY`。**换了顺序或值，历史密文全部不可解**；codec 解密时会尝试 [当前密钥, 开发回退密钥] 两把。无密钥轮换机制、无 KMS/信封加密、无 key id。
- 受加密字段：店铺登录密码 `store_password`、提现支付密码 `withdraw_payment_password`、资质平台登录密码、各类账号密码 `account_password`、网银盾 `login_password/trade_password`（迁移 0041 批量加密历史明文）、会话管理店铺凭据 `withdrawal_login_password`、集成 app_key/secret/token、AI api_key、飞书 secret_cipher。展示层：`maskBusinessSecrets` 替换为遮罩，列表仅显示 `*_masked`。
- 查看明文需权限：店铺密码 `resources.stores.credentials.view`；会话管理凭据 reveal 走工作区权限并写审计（view / copy 两种用途）。
- 对外 API 密钥与助手设备令牌/绑定码/WebRTC 票据不用加密，而是**只存 sha256 哈希**（正确做法）。

## 8. 部署与迁移机制

### 8.1 环境
单台 Linux（宝塔风格路径 `/www/wwwroot/oa.kudesi.com`）：Nginx 静态 + `/api/` 反代 4000（`proxy_read_timeout 3600s`、WebSocket 升级头，`client_max_body_size 30m`）；PM2 进程 `kudesi-oa-api`（`ecosystem.config.cjs`）+ `kudesi-oa-ocr`（Python venv EasyOCR，8001）；MySQL 8（utf8mb4_0900_ai_ci）；附件目录 `UPLOAD_DIR`（默认站点 `uploads`，**应用鉴权读取，不对 Nginx 开放静态**）。Docker Compose 只启 MySQL/OCR，不含 API/Nginx。

### 8.2 CI/CD（`.github/workflows/`）
- **deploy.yml**：`push main` 或手动触发即**自动上线**（并发组 `deploy-oa-main`，不取消进行中的）。步骤：Node 20 `npm ci` → 约 45 项测试命令串联（单元/同步/飞书/流程/部署回滚等）+ `bash -n activate-release.sh` → `vite build` → 写 `dist/deployment-sha.txt` → `validate:production-web`（校验关键功能文案已进入最终静态资源，防旧构建覆盖）→ 打包 `dist server shared docker/mysql/init/001_schema.sql docker/ocr package*.json ecosystem.config.cjs`（排除 .env、测试、desktop、`dist/session-manager-agent`）→ scp 到 `/tmp/kudesi-oa-release/<sha>` → ssh 执行 `server/scripts/activate-release.sh <staging> <sha>`。Secrets：`DEPLOY_HOST / DEPLOY_USER / DEPLOY_SSH_KEY`。
- **activate-release.sh**（125 行）：核对 SHA → 文件快照(优先硬链接旧文件) → 数据库备份规划(`deployment-database-plan.cjs`；后端/依赖变化或有迁移时必做完整备份，纯前端无迁移时仅复用同库 30 分钟内校验通过的备份，保留最近 10 份，流式 gzip，失败的 partial 清理) → 替换受管运行文件 → 按签名决定是否重装依赖 → 执行增量迁移 → 部署 OCR → PM2 reload → API 健康后才切换前端入口 → 公开页面/资源检查（**公开验证 URL 写死 `https://oa.kudesi.com`**）→ 失败则文件回滚(`release-files.cjs restore`)。**文件回滚不回滚数据库**。每阶段记耗时。前端旧版本资源保留至少 10 版/3 天/最多 30 版，防旧页面报错。
- **publish-windows-agent.yml**（windows-latest）：校验 → 构建（Node 22.23.2 + .NET SDK 10.0.302 + NSIS + 原生 WebRTC bridge 按变化缓存）→ 产出 installer/update/patch 工件 → 可选 `activate` 上传到服务器（ssh/SFTP）。**activate-existing-windows-agent.yml** 复用已有构建 run 的工件做并行断点续传上传与激活。**inspect-agent-transfer.yml** 诊断。
- **sync-bundle-minimum-prices.yml**、**reassign-sku-review.yml**：手动触发的**运维任务**（preview / apply / status，apply 必须带预览 SHA256 token），通过 ssh 在服务器上跑脚本——这是该项目对"生产数据写入需明确授权"的落地方式。

### 8.3 迁移机制
- `server/migrations/NNNN_name.js`（当前 0001–0177），导出 `{id,name,up({connection})}`；`schema_migrations(id,name,checksum,executed_at)`；`migrate.js` 逐个事务执行（注意 MySQL DDL 自动提交，事务回滚对 DDL 无效），**已执行迁移的文件内容 checksum 变化会终止**（可通过 `acceptedChecksums` 兼容历史改动）；幂等写法普遍（`IF NOT EXISTS`、information_schema 判列）。首次空库需要 `docker/mysql/init/001_schema.sql`。
- **双轨 schema**：迁移之外，后端启动时还有 `createSchemaInitializer` 执行一批 `ensure*Schema`（platform-admin、组织、集成、飞书、流程超时、资源、任务、财务单据、`jst_skus`……）。即同一批表可能同时由迁移和启动代码创建，文档要求"不得跳过迁移直接启动新后端"。
- 大量"种子/修复"迁移掺在 schema 迁移里（如 0090 华艺 OEM 包装、0095–0096 供应商 OEM 成品、0111–0114 物流种子、0143–0148 一系列 verification 快照修复），说明迁移已承担数据修复职责，新系统应把种子/数据修复与 schema 迁移分离。
- 备份：`npm run db:backup`（`backup-database.js`，`ecommerce-oa-*.sql.gz`）；恢复靠手工 `gzip -dc | mysql`。灾备不在脚本里。

### 8.4 迁移到新机器要点（`部署与迁移指南.md`）
必须单独安全迁移：数据库备份+`schema_migrations`、原 `.env`（**SECRET_KEY/SESSION_SECRET/JWT_SECRET 原值**）、`jushuitan-api.env`、完整附件树、GitHub Secrets/SSH/Nginx/TLS/DNS/PM2 开机项、Windows 助手独立发布资源（latest.json 与安装包）、各员工电脑上的本机 Profile。恢复后**先隔离真实聚水潭与飞书网络、确认队列**再启动（无统一禁用开关）。

## 10. 对新系统重写的建议

### 10.1 核心业务（必须在第一/二阶段完整重做，规则一条不能丢）
1. **外部写入安全框架**（通用，与具体平台无关）：授权目标指纹 + 管理员启用规则 + 事务内入队事件 + 预览签名确认 + 写前再读 + 意图先落库 + 结果不确定只回查 + 写后逐字段回查 + 不接管未关联资源 + 公司级互斥锁 + 全程证据日志。建议抽成一个"出站同步引擎"（状态机：blocked / pending / confirming / success / failed + 回查调度 10/30/60 秒），商品、组合装、分类、调价、禁用都是它的 adapter。**重写时应改成一个明确的 outbox 表 + 单一 worker + 可配置全局开关（含"一键停所有外部写入"，现在缺失）。**
2. **聚水潭商品/组合装/分类/调价的字段与比对口径**：§1.3–1.6 的字段表、重量精度、分类以 c_id 映射、组成合并规则、依赖顺序（分类→基础商品→组合装→调价）、组合最低售价公式与向上取整。
3. **聚水潭授权管理**：平台级 app key/secret + 企业级 token/coid/过期时间；**补上 refresh_token 刷新**与到期预警（现在是缺口）；授权目标指纹。
4. **改码/删除策略**：保留"不自动另建、不盲重发、编码永不复用"的原则；在 JST 无改码/删除 API 的约束下，保留"禁用旧码+新建新码"需人工确认的路径，并在确认弹窗里**真正检查**库存/在途订单/BOM/店铺映射（现状只是让人勾选声明）。
5. **敏感信息保护**：统一一套带版本号/key id 的加密（建议 envelope + 可轮换），库内秘密、API 密钥哈希、一次性令牌哈希；查看明文需权限+审计；前端永不接收明文。
6. **飞书"通知不阻塞业务"的契约**：事务内入队、发送前重验资格、合并去重、持久化幂等 uuid、基线不补发、成本不外发。这是流程系统的通知底座，建议和流程中心一起设计，第一版至少做"流程待办→飞书"。
7. **部署流水线的安全属性**：先备份再迁移、迁移 checksum 校验、纯前端复用备份、健康检查后切流量、失败回滚文件、发布 SHA 可核对、手动运维任务带预览 token。可以简化实现，但这些属性建议保留。

### 10.2 可后置 / 可拆分的外围能力
| 能力 | 建议 |
|---|---|
| 会话管理全套（助手/WebRTC/Profile/设备/凭据自动登录） | **整体拆成独立产品/独立服务**（独立仓库、独立版本、独立发布流水线）。与 OA 的耦合点只有：店铺档案(stores)、员工/权限、审计。新系统第一版只需保留"店铺-账号凭据（加密）+ 谁能看"，会话功能放后期。若要做，先问清业务目标：目前最实际的价值是"为店铺提现提供稳定登录环境"。 |
| 远程协助（WebRTC+TURN+JPEG 回退+C#/C++） | 复杂度最高、运维依赖 TURN，建议最晚做，或改用成熟远程桌面/RPA 方案；需要时再评估。 |
| AI 服务商管理、快递价格表/加收通知 AI 识别、营业执照 AI 识别 | 拆成"AI 网关"小模块；业务页只调用"识别任务"接口。规则保留：仅 GPT 系列（如业务仍要求）、人工核对后入库、任务持久化（现在是内存 Map，重启丢失）。 |
| 本地 OCR 容器（EasyOCR） | 现在服务端业务已不依赖，仅桌面端用；建议砍掉或并入 AI 网关的可选 provider。 |
| 对外数据 API（组合品/成本只读） | 独立"开放平台"小模块：密钥表+scope+限流+调用审计（补"最近使用"）。 |
| 飞书的 6 个通道 | 通道数量可先收敛为 2–3（流程/督促/系统），其余并入通知；应用凭据配置化而非写死 App ID。 |
| 聚水潭只读同步（店铺/订单/售后/库存/采购） | 全部后置。若要做，应直接设计成"入站同步引擎"（分页+时间窗口切片+原始 JSON 日志+限流+游标），不要沿用 `jst_skus` 旧镜像和 `sync-demo` 假接口。 |
| 售后 | 先写需求再开发（见 §5），首选范围：工单 CRUD + 状态机 + 72 小时/高金额监督 + 聚水潭售后单入站 + 截图预填(AI 或 OCR 二选一)。 |
| Electron 桌面壳 | 最后做；目前只是截图/剪贴板/通知；可以改成 PWA + 浏览器剪贴板/截屏 API 覆盖大部分需求，必要时再做壳。 |

### 10.3 建议的技术调整（不复用代码，仅规则层面）
- 队列/worker 从"进程内 setTimeout + 命名锁"升级为明确的任务表 + 租约字段（lease_until）+ 单 worker 进程，WebRTC 票据、AI 识别 job 等放持久化或 Redis，支持多实例。
- 设备在线窗口、租约时长、回查时序等魔法数字集中配置。
- 区分"迁移（schema）"和"种子/数据修复"，禁止启动期隐式建表。
- 保留租户隔离（所有表带 company_id）与"个人 deny 优先"的权限模型。

## 11. 现有 UI / 操作逻辑与实现上的问题

**聚水潭**
1. 商品/组合装同步入口分散：基础编码页、二次验证页、"同步维护"弹窗、"删除/禁用记录"、分类管理里的"聚水潭商品分类"、组合装页各一套，状态词不统一（未同步/排队中/等待回查确认/已同步/同步失败/资料待补齐，加上分类的"待回查/接口拒绝"）；用户很难知道"先同步分类→再同步商品→再同步组合"的依赖顺序，只能看到 blocked 的文字提示（"等待分类自动同步…"）。
2. 手动确认依赖用户自觉：改码确认只是一个勾选框"已处理旧码库存/在途订单/组合装/店铺映射"，系统并未检查；确认后又无法迁移这些关联。
3. 自动同步默认关闭且需要 4 步（手动核对→全部无差异→勾选确认→开启），目标指纹变化会静默停掉自动同步（只在状态里体现），运营不易察觉。
4. "全局找不到停止外部写入的开关"；恢复数据库到测试环境存在误写生产聚水潭风险（CLAUDE.md 自己承认）。
5. 没有 token 刷新，授权到期靠人工；平台级 app 密钥与企业授权在一页长表单里，规划里的拆页尚未做到位（"API 密钥管理页面改版规划"仍是规划）。
6. 失败后的处理路径靠看日志里的 `evidence_json` 差异；没有"一键重新核对""批量重试失败项"（仅分类有 retry）；回查 3 次耗尽后只能人工点击重新提交。
7. 分类同步在 JST 不返回排序/启用状态时无法检测远端人工修改，UI 只在备注里提示。
8. 代码重复/分叉：商品与组合装同一引擎靠 adapter 开关（`adapter?.` 到处分支）；分类服务按 dictionaryType 复制一套路由；旧入站镜像 `jst_skus` 与新出站并存；`sync-demo` 假同步接口仍在；一个测试商品 `QA-SKU-…` 硬编码在业务代码里。
9. 文档与实现偏差：`聚水潭同步能力文档.md` 描述的店铺/订单/售后/库存同步（含"第一阶段落地建议"）完全未实现；`AGENTS.md` 说"当前阶段仅基础数据"与实际已上线外部写入并存。

**飞书**
10. 6 个机器人对管理员心智负担大（要分别配置密钥、启停、接收人）；普通员工必须先绑定才能收通知，未绑定只给登录提示，缺少"谁没绑定"的管理视图（文档未提）。
11. 绑定需要两次确认（authorized→awaiting_confirmation→completed），流程复杂；"Mac 客户端显示另一昵称身份"这类跨账号问题靠人工核对。
12. App ID 硬编码在源码，换企业/换租户不可配置；旧 `feishu_user_mappings`/`feishu_message_logs` 表废弃未清理。

**AI / OCR**
13. 营业执照识别页提示语引导用户到"系统 > AI API 接口"配置——对普通员工不可操作；OCR 设置页文案仍说"免费本地 OCR：EasyOCR"，但实际不走 OCR（死代码+`BUSINESS_LICENSE_OCR_PROVIDER` 无效），用户配置与实际行为不一致。
14. 快递识别 job 存内存、1 小时过期、重启丢失，用户上传大文件后若服务重启只能重传；轮询无超时 UI 约束。
15. 仅允许 GPT 的限制写死在服务端，换模型必须改代码。

**会话管理**
16. 单页承载太多职责：店铺列表同时做 档案状态管理（公司店铺维护）、凭据行内编辑、自动登录开关、电脑分配、打开进度、历史抽屉；表格列非常多（`sm-credential-col`…），移动端不友好；凭据**失焦自动保存**容易误存/误清（清空账号会同时关闭自动登录）。
17. 同一电脑**一次只能开一个店铺**，用户点"首次登录"另一店铺时只得到报错文案，没有"关闭当前并切换"的一键操作；100 店场景（验收清单）仍未验证。
18. 在线判定不一致：创建打开请求用 15 秒，设备管理常量 45 秒，助手心跳 5 秒，网络抖动时"助手离线"会误报。
19. 打开请求租约过期后直接 `failed` 并要求"重新连接"，但 `claimed` 状态的请求过期会被重新领取，两种路径行为不同，用户难以理解。
20. 登录凭据由服务端解密后**明文下发给助手**（TLS 内、一次性、no-store、写审计），仍意味着服务端能解密所有店铺密码；列名 `withdrawal_login_account/password` 在"公司店铺维护"工作区被复用，语义错位。
21. 云端加密登录态相关表与验收清单第 5 节仍在，但实际已禁用（local_only）；设备 B 无法接管同一店铺，换电脑必须"改绑负责电脑"并**重新首次登录**，文档/UI 对此没有说明。
22. 验收清单严重滞后（写 0.1.3，代码 0.3.44；"禁止行为"含远程鼠标键盘但功能已实现），100 店、重启、设备 B、生产环境证据全是"待填写"，无法作为发布依据；正式下载按钮还受"无代码签名证书"限制，只能发未签名测试版。
23. WebRTC 票据存进程内存；单进程部署可行，但 PM2 cluster / 多实例会失败；远程画质、TURN 需要额外服务器才可靠，OA 基础部署文档未覆盖。
24. 远程会话只有 10 分钟有效期，需续期；会话结束要走 5 阶段安全关闭，若助手离线则无法确认关闭，用户只能"仅退出界面"。
25. 助手卸载/更新/修复路径多（patch/component/full/repair_required/`repair-agent-0.3.0.ps1`），"updaterProtocol 变化必须重装"对非技术员工不友好。

**售后 / 桌面端**
26. 售后页：没有创建/编辑/关闭工单入口，"识别并预填"结果无处保存；默认文本框里预置了示例订单文本；假识别（金额 328 固定值）容易被误认为真实识别；72 小时监督、高金额提醒仅出现在文案里；列表无分页/筛选。
27. 桌面壳标题"电商经营流程中台"与产品名不一致；功能只在售后页和营业执照页生效；Electron 没有打包/升级/签名流程；`sandbox:false`。

**部署**
28. 部署脚本强绑定域名/路径（公开验证写死 `oa.kudesi.com`；OCR 与激活脚本的 `APP_ROOT` 语义相反），迁移到新服务器不是一键；Nginx/证书/PM2 开机项不在仓库。
29. `main` 推送即上线，且流水线里 45+ 条测试串联在一个 shell 步骤，任一失败即中断，缺少分阶段预发环境。
30. 迁移内混杂大量数据修复，`npm test` 依赖演示数据不能用于真实库；`schema_migrations` 校验异常即终止，现场修复成本高。
