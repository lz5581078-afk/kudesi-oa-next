## 0. 一句话总览（先看这个）

系统实际上有 **三套并存的"流程引擎"** 加一套"任务系统"，这是现有设计的最大特征，也是重写时最该收敛的地方：

| 引擎 | 标识 | 运行器 | 状态 |
| --- | --- | --- | --- |
| A. 通用图引擎（旧） | `workflow_instances.graph_status in (active/abnormal/completed)` | `server/index.js` 内 `completeWorkflowNodeRecord / activateWorkflowNode / evaluateWorkflowJoinNode` + `/api/workflow-instances/*`、`/api/workflows/*` | 设计器仍可配置模板，但**没有任何前端发起入口**；接口无处理人校验；仅历史/演示数据 |
| B. SKU 批量引擎 | `graph_status='batch'`，`related_object_type='bundle_application'` | `W/batch-requests.js`（`/api/workflow-batches`） | 生产在用。一张"申请单"(batch) + N 个"规格"(item，每个规格一条独立 workflow_instance) |
| C. 业务运行引擎 | `graph_status='business'`，`related_object_type in (purchase, product_exclusive)` | `W/business-runs.js` + 适配器 `purchase-adapter.js` / `product-exclusivity.js`（`/api/business-runs`） | 生产在用。一张申请 = 一条 workflow_instance + 一条 workflow_business_run（payload 为业务状态机 JSON） |
| D. 任务系统 | `task_instances / task_templates / delay_requests / exception_records` | `server/index.js` `/api/task-*`、`/api/delay-requests`、`/api/supervision` | 周期/手工任务；同时承载 B/C 引擎节点生成的"待办"行 |

另有遗留表 `tasks`、`exceptions`、`workflows`（docker 初始 schema 的演示数据）仍被 `/api/tasks`、`/api/supervision`、`/api/dashboard/*` 读取。

## 1. 流程引擎概念模型

### 1.1 核心实体
- **流程模板 workflow_template**（`workflow_templates`）：公司级；`related_object_type` 决定它接入哪个业务引擎（`bundle_application` / `purchase` / `product_exclusive` / 其他=仅配置不能发起）；`status` active/inactive；`department_id`（使用部门，仅用于目录归类，不是权限）；`form_schema`（业务模板级配置：`starterRoles` 或 `starterSources` 发起人范围、`businessType`）。
- **模板节点 workflow_template_nodes**：`node_key`（流程内唯一）、`node_type`、`node_order`、`next_node_keys`(JSON 数组)、`reject_to_node_key`（旧"退回线"）、`exception_to_node_key`（异常线）、`join_policy/join_required_node_keys`（汇合）、`handler_source_type/id`（处理人来源）、`due_hours`（**实际单位是分钟**）、`creates_task`、`visible_fields/editable_fields`、`action_config.actions`（自动动作）、`form_schema`（见下）。
- **节点 form_schema 内的约定字段**（真正的"节点配置"都塞在这个 JSON 里）：
  - `nodeTemplate`：办理器(processor)标识，如 `bundle_sales / purchase_plan / exclusive_approval`；
  - `businessTemplateKey/businessTemplateRevision/processorName`：选用的节点模板库条目及其修订号快照；
  - `assignment: {mode:'single'|'any', sources:[{type,id}], supervisor?}`：处理人；
  - `timing: {enabled, beforeMinutes[≤5], overdueEveryMinutes}`：督促提醒；
  - `waitingTiming`：按业务日期（承诺发货/预计到货）的催办；
  - `notifications: {ccEmployeeIds[≤20], escalations[≤5:{afterMinutes,source}]}`：抄送、业务级超时升级；
  - `routes:[{fact,equals,unless?,target}]`：条件流转；`controlRoutes:{amend,cancel}`：发起人变更/废除走哪个审批节点；`deadlineField`：截止时间取业务状态里的哪个字段。
- **节点库 workflow_node_library**（`company_id+template_key` 主键，`definition` JSON，`revision`）：企业对内置目录（`shared/workflow-node-catalog.json` 48 个模板、46 个字段）的覆盖/复制。办理器(processor)与模板 key 分离：企业可复制多份"采购批准"，但 processor 仍是 `purchase_approval`，业务动作由服务端继承，**客户端不能注入新动作/字段/来源**。
- **流程实例 workflow_instances**：`status`(draft/processing/returned/completed/cancelled/…)、`graph_status`(区分哪个引擎)、`current_node_id/current_owner_id`、`active_node_keys`、`due_at`（当前节点截止，**总览/待办用它**）、`workflow_data`、`requester_id`。
- **节点记录 workflow_node_records**：每次"进入"节点就新建一行（退回再进入=新行）；`is_active`(1=当前)、`status`(pending/completed/returned/rejected/cancelled/skipped/abnormal)、`action`(pending/submit/approve/return/cancel/reject/withdraw/transferred/amend/joined)、`owner_id`（建立时=单一处理人；部门共享时为 NULL，办理后写实际操作人）、`form_payload`、`timing_json`（**进入时规则快照**：timing + timeoutPolicy + notifications + assignmentSource + handledBy）、`comment`。
- **待办 task_instances**：节点生成的 `source_type='workflow'` 待办，每个**接收人一行**（部门共享时同一节点 N 行）；`relation_type`(workflow_batch / workflow_business) + `relation_id` 指回申请；`due_at` 与实例截止同步。
- **共享接收人 workflow_node_recipients**（`node_record_id+employee_id` 唯一）：进入节点时冻结的部门成员名单，权限判断时再关联员工/部门的在职状态（调岗、停用立即失效）。
- **业务事件 workflow_business_events**：审计流水（batch_transition / batch_edit / node_operation …）。

### 1.2 节点类型（`workflowNodeTypes`，设计器与目录共用）
`submit` 发起 / `approval` 审批 / `execute` 执行 / `finance` 财务 / `payment` 付款 / `inbound` 仓库 / `quality` 质检 / `reimbursement` 报销 / `exception` 异常处理 / `join` 汇合 / `end` 结束 / `system` 系统（自动，不产生待办）。
- 校验规则（设计器 `validateWorkflowDesignerNodes`）：必须有发起节点；必须有 join 或 end；节点 key 唯一；非 submit/join/end/system 必须有处理人来源；非 end/join 必须有后续节点；join 必须声明 `joinRequiredNodeKeys`；可选节点(is_optional)必须允许填 `notRequiredReason`；`create_finance_entry` 动作必须有 `amountField`+`direction`；所有引用 key 必须存在。**注意：校验失败时 `PUT /templates/:id/nodes` 仍会先保存再返回 errors**。

### 1.3 处理人解析（`W/node-recipients.js::resolveNodeRecipients`，B、C 引擎共用）
- 来源类型：`employee` / `role`(employees.role_key) / `position`(employee_positions 有效+岗位有效+岗位所在部门有效) / `responsibility_group`(有效成员) / `department`(部门直属在职员工，**必须 mode='any'**) / `requester`(仅 C 引擎，转成指定申请人)。
- 规则：**非部门来源必须"恰好匹配 1 个在职人"**，0 或 ≥2 都报错（"匹配到N名处理人，请在流程设计器中指定唯一人员"），**不会兜底到管理员/发起人**。部门来源：全员共享、任一人处理；不含停用成员、不含子部门；名单在进入节点时冻结，之后修改配置不改派已有待办。
- 解析时机：**节点进入时用"实时配置"，路径用"申请快照"**——SKU 的 `template_snapshot`（batch）和采购的 `template_snapshot`（run）保存节点结构与路由，但进入节点时回读 `workflow_template_nodes` 的当前 assignment/timing/notifications/due_hours（并校验 processor 未变，否则"节点配置已变化"）。
- 旧通用引擎(A)的 `resolveAssignee` 另有一套：支持"委托(delegations)"、requester_manager、previous_handler、related_owner，且**无人时静默回退到发起人/ID=1 员工**——与新引擎行为相反，重写时应只保留新引擎语义。

### 1.4 流转 / 退回 / 转交 / 抄送 / 超时升级 / 独立流转
| 能力 | B：SKU | C：采购/专属 |
| --- | --- | --- |
| 前进 | 线性 `next_node_keys[0]`；只支持串行（可串行加同类节点如二级审核）；无并行、无条件分支、无自动动作 | `chooseNext`：有 `routes` 则按业务事实 `facts(state)` 匹配**恰好一条**，否则取唯一 next；`pendingException` 且节点配了 `exception_to_node_key` 优先走异常线；`system` 节点进入即自动执行并继续（最多 20 层） |
| 退回上一步 | 取"实际办理历史里最近一个已关闭的人工节点"（`previousStep`），跳过 system/end/join 与 cancel/reject/withdraw 记录；首个 submit 节点无上一步；重新进入目标节点时处理人按当前配置重解析 | 同左，另需适配器 `canReturn`（采购：已付款后不得回到付款前节点；已过账批次不得再从结算/费用付款/检查退回；存在 pending/failed 的收付款命令时禁止退回） |
| 废除(cancel)/拒绝(reject) | 当前节点处理人、原因必填≤500；作用于**所选规格自己的流程**；节点记录 status=cancelled/rejected；规格 status=cancelled；已完成规格不可操作 | 当前节点处理人；采购无资金/物流事实→立即 cancelled；有事实→按发起节点 `controlRoutes.cancel` 进入异常审批→退款→归档收尾（`terminationRequest` 记录），收尾完成才最终 cancelled；专属品→释放待申请占位 |
| 发起人操作 | 申请人可删除"未提交仓库的草稿/仓库退回运营的申请"、新增/复制规格、改公共设置 | `withdraw`(撤回，仅无付款/发货)、`amend`(付款后变更，回到 `controlRoutes.amend`，保留已付款/已过账批次再审批)、`cancel`(终止并退款) |
| 转交 | **无**（文档说"沿用现有交接"，代码里 B 引擎没有转交接口） | 仅**公司管理员**可转交当前非发起节点给指定员工；关闭旧记录(action=transferred)，同节点重进，保留原截止/原计时规则/待转交的提交证据 |
| 抄送 | 无 | `notifications.ccEmployeeIds`（写 `workflow_business_observers`，可查看该申请，**不能办理**，且不自动获得成本权限；进入节点发飞书 `business_cc`） |
| 超时升级 | 公司/流程/节点三级 `workflow_timeout_policies`（见第 5 节） | 同左 + 节点级 `notifications.escalations`（afterMinutes→接收来源）；当三级策略已启用通知时，节点级升级不再发（防重复） |
| 批量明细独立流转 | 一张申请单（batch）下每个规格是**独立 workflow_instance + 独立节点记录 + 独立待办 + 独立版本号**，同一申请的规格可同时处于运营/仓库/财务/已完成/已废除；申请单状态由聚合得出 | 不适用（一单一实例；采购"批次"是 payload 内的数组，不是独立实例） |

### 1.5 并发与幂等原则（重写必须保留的"不变量"）
1. 任何写操作先 `SELECT … companies FOR UPDATE`（公司级互斥）再锁申请/规格行，事务内重新校验"当前活动节点 + 当前处理资格 + 资料版本(revision)"。
2. **乐观版本号**：SKU 规格 `revision`、业务 run `revision`；每次编辑/流转递增；旧页面提交被拒。
3. **幂等**：采购/专属创建支持 `requestKey`(12–80 字符)；节点提交先落 `workflow_business_commands(request_key 唯一, status pending/failed/completed/superseded)`，**失败保留证据可原样重试**，成功才推进；财务单据 `source_key` 唯一、银行流水号唯一（`finance_payment_references`）。
4. 办理资格 = `owner_id==我` 或 我在该活动节点的 recipients（且员工在职、部门在职、部门未变）；**管理员身份不自动等于处理人**（防止代办）。
5. 业务数据与流转在同一个事务里提交（SKU 终审生成组合编码+成本表+验证快照；采购记账+入库草稿+成本发布+节点流转）。

## 3. 各业务流程逐步规则

### 3.1 SKU 批量申请流程（B 引擎，processor：bundle_sales → bundle_fulfillment → bundle_review → end）

**模板建立/启用**（`W/batch-requests.js`）
- 管理员"建立SKU申请模板"：创建 4 节点 `sales(submit)→warehouse(execute)→finance(finance)→end`，`reject_to`: warehouse→sales, finance→warehouse；仓库、财务默认 `due_hours=60` 且 `timing={enabled,[20,10],5}`；模板初始 inactive，**不预设任何处理人**。
- `validateTemplate`：必须恰好含三类 processor + 一个 end；节点 key 唯一；从 sales 沿 next 走一条无环链覆盖全部节点；每个业务节点恰有一个有效 next；财务前必须有仓库；**只有审核节点可连到 end**；退回目标必须是已走过的上游；仓库/财务必须配退回；不允许额外自动动作/异常线；`bundleRows` 可见，运营/仓库可编辑、财务只读；`due_hours` 1–100800。
- 启用(`PUT /templates/:id/status`)要求校验通过且**每个节点能唯一解析处理人**；停用随时可。模板在**第一张申请单创建时保存 `template_snapshot`**；已有申请后只允许"补配处理人/时限/提醒"（`updateBatchAssignments` 比较结构不变），要改结构须复制模板；不能换节点模板、不能启用后换业务模板。
- 发起权限：`POST /api/workflow-batches` **只校验企业内在职，未走 `canStartWorkflow`**（发起人范围配置对 SKU 无效）。未启用模板允许建草稿、保存规格、查重，**提交/审批时才强制模板 active**，进入下一节点时才检查负责人。

**步骤 0：新建申请单（两步弹窗）**
1. SKU 查询（参考）：必须先搜索（商品名/规格/基本编码，限启用且未隐藏的基础编码，≤30条），结果展示"已成功组合 N / 申请中 N 单"仅作参考，**无匹配、已有记录均不阻止下一步**；可选一个商品→自动作为首个规格的主商品(qty 1)。
2. 填标题(≤140)、选模板、输入 1–100 个**互不相同(忽略大小写)的内部规格名**（≤100字）→ 一次事务创建：1 个 `workflow_batches`(含 `template_snapshot`、`settings_json`) + N×(`workflow_instances`(graph_status=batch) + `workflow_batch_items`(payload_json) + 运营节点记录)。运营节点对 `draft` 规格**不生成待办**。
- 申请公共设置 `settings_json`（对整张申请所有规格统一）：组合分类(`bundle_category` 字典)、销售场景(启用的 scenarios)、平台列表(≤20，启用的 `finance_sales_platforms`)、默认品牌(`brand` 字典，名称+短码都非空)。**申请人**可改，且仅当所有未取消规格都还在运营节点(draft/returned)；改动会清空各规格 review_snapshot/identity_hash 并递增 revision、写 batch_edit 事件。

**步骤 1：运营（bundle_sales，处理人=申请人）**
- 可编辑：规格名、品牌(手选标记 brandManual)、组合分类、场景、平台、**主商品及数量(整数件)**、**赠品及数量**、备注。
- 主商品可选来源档案：供应商OEM成品/原料档案/原装采购成品；赠品另可选"发货物料档案"(2026-10-21)；均要求基础编码启用且已验证。品牌：主商品有品牌自动带入；无品牌则必须手选，不回填原料档案。
- 便利：单行复制为新运营草稿（保留运营内容，丢弃仓库内容）；"数量系列"（主商品只能 1 项，一次最多 30 个不同正整数→生成多个规格草稿，赠品数量不放大）；一单最多 100 规格；规格名在申请单内不可重名。
- 编辑保存：`PUT /:id/items/:itemId`(带 revision)→`editPayload`：运营只能改 salesKeys 与 main/gift 行，**保存即清除 notRequired/reuseInfo（仓库确认作废）**，revision+1，清 review_snapshot。
- **校验(check/submit)**：`inspect` ——必须有 main；行数≤100；数量>0 且 main/gift 为整数；商品必须属本公司且在允许来源档案内；`composeBundle` 生成名称/规格/重量(称重重量×数量)；品牌解析；平台 1–20；`service.prepareComplete` 做编码生成与冲突预检；所有组成基础商品必须有有效成本；结果含 `snapshot{platforms[finalCode,productName,existing,conflict], sources[id,签名], labor, totalCost, weight}` 与 `signature`、`identity`。
- **查重（三层）**：
  1. 编码冲突（阻断）：在途(非 draft)其他规格已预留的最终编码与本规格相同→阻断；草稿只提示。
  2. 主商品组成相同(仅 main 的 基础编码×合并数量，不看赠品/品牌/分类/场景/平台)→提示"主商品相同，赠品不同可继续"或"主商品和赠品相同，请核对是否重复申请"（非阻断）。
  3. **已有组合SKU匹配**(`generatedMatches`：当前 BOM 的 main+gift 组成与本规格相同)：列出已有编码，**必须二次确认并填写继续申请原因(≤500)**，确认令牌 `hash(item.id,revision,signature,matches)` 绑定版本，提交/审核时重新查询，任何变化需重新确认；确认人/时间/原因写入节点 payload 与事件。
- 运营提交 `submit` → 规格 status=processing，下一节点（仓库）由 `activate` 解析处理人、建待办。

**步骤 2：仓库（bundle_fulfillment，来源常配"仓储部全员·任一人处理"）**
- 可编辑：包装(`package`)、标签/说明书/贴纸(`label/instruction`)、打包材料(`other`)、人工(`laborLines`)、`notRequired` 原因、`warehouseNote`、`reuseInfo`。运营资料只读。
- 角色→允许来源档案：包装=产品包装档案；标签/说明书/其他=发货物料档案。
- **提交校验**(`warehouse:true`)：包装、标签、打包材料、人工**四类每一类要么有配置要么必须填"不需要的原因"**（区分"无需"与"未处理"），否则拒绝。
- **历史配置复用**(2026-10-08)：`GET /:id/items/:itemId/reuse-sources?keyword=` 返回最近 100 份"已被仓库提交到下一步"的仓库配置（按主商品名/编码检索；排除 SKU 已归档删除的；不要求终审成功），前端按主商品总重量接近度排序；复用只替换仓库可填部分(包装/标签/材料/人工/无需原因/说明)，保留运营资料；已有仓库内容先确认；复用后停留编辑页，**不自动保存/提交**；打"已复用·待核对"(蓝)/"无法完整匹配"(橙)标记，停用/缺失物料不带入；运营改资料时清除标记。批量套用：可对所选多规格分别按重量推荐或统一套用。
- **整单退回运营**(`/:id/warehouse-return`)：仅当该申请下**所有**仓库待处理规格都归当前用户处理、且快照退回路径指向运营时可用；一次填原因，同事务对全部仓库规格 `transitionItem(return)`，任一失败整体回滚。
- 仓库提交 → 规格流转到财务；节点记录保存仓库 payload。

**步骤 3：财务（bundle_review，只读核对）**
- 动作：`approve` 通过(需 `confirmed:true` 明确确认)、`return` 退回、`cancel/reject`。
- 通过前校验：模板 active；再 `inspect`；`signature` 必须等于仓库提交时保存的 `review_snapshot.signature` **且**等于页面刚校验的签名（来源资料/成本/命名任一变化→"请退回仓库重新确认"）；有已存在同组成SKU需二次确认；非 bundle_review 节点不得使用 approve。
- 若下一节点为 end（最终审核）则 **`finalize` 同事务**：①操作人须有成本表编辑权限(`bundle-cost-register.mayEdit`，"仅财务人员可更新成本表")；②`service.createComplete` 创建或复用组合定义+BOM+各平台编码(完全相同的定义/BOM/人工/平台复用已有编码；同码但内容不同→阻止，禁止覆盖)；③核对最终成本=审核成本；④写 `finance_bundle_data_verifications(+events)` 验证快照；⑤`publishBundleCosts` 发布/更新成本表（按企业+组合编码唯一，复用编码更新同一条，不清空财务维护的快递/运费/利润率；最低售价=(预发货成本+运费)÷(1−利润率)向上取两位）；⑥为每个编码**入队聚水潭同步**（`bundleSyncService.enqueue`，见第 7 节冲突）。任一失败整体回滚。
- 串行追加的"二级审核"节点：中间审核节点 approve 不 finalize，只有连到 end 的那个节点 finalize。
- 通过后规格 status=completed，节点记录 completed，`enqueueApproval` 给申请人写飞书"SKU 审核通过"（含规格名/数量，不含成本）。

**统一的规格状态机**（`workflow_batch_items.status`）：`draft`(运营未提交) → `processing`(流转中) → `returned`(被退回；仍在上游节点，该节点重新生成待办) → `completed` | `cancelled`。申请单状态由规格聚合：全 draft→draft；有 returned→returned；有未结束→processing；全 completed→completed；否则 cancelled。

**退回(return)细则**：目标=`previousStep`（不是模板 reject 配置）；记录 `returned`；规格 status=returned（若回到运营则可编辑）；目标节点重新 `activate`（新记录、新待办、新截止、新计时）；仓库退回需填原因，不要求先校验。

**删除**：整张申请——仅申请人；且每个规格要么是未提交的 draft(只有 pending 记录)、要么曾经只被**仓库**退回运营且现已回到运营 pending、要么已取消；进入过财务/已完成/有 result 的都不可；同事务删除申请、规格、实例、节点记录、待办、事件、异常记录，**不删商品编码/成本表**。单规格草稿删除：申请人或管理员、必须原因≤500、规格仍在运营首节点、无历史记录/无业务事件(除 batch_edit)，写 `workflow_batch_item_deletions`。

**权限/脱敏**：申请可见=管理员 | 申请人 | 任一规格的历史处理人/当前处理人/共享接收人；财务数值字段（键名含 cost/price，及 source_snapshot_json）对无成本查看权限者（`employee-profile.canViewCosts`）整体剔除（`costResponse`）。

### 3.2 商品专属领取（C 引擎，processor：exclusive_submit → exclusive_approval → end）
- 创建：`POST /api/business-runs/templates/product_exclusive` 生成 3 节点 `request(submit)→approve(approval, 时限1440分钟)→end`，approve 退回 request；`timing={enabled,[20,10],5}`，`notifications={ccEmployeeIds:[],escalations:[]}`；未启用、不指定审批人。发起范围默认角色 `operator/sales/operations/admin/company_admin/boss` 或配置的部门/岗位/人员来源（`starterSources`）。
- 校验(`validate`)：恰有一个 `exclusive_submit` 与一个 `exclusive_approval`；前进路径无环；必须经过审批才能到 end；退回目标须为上游。
- **基础商品族身份**：以 **(分类, 品牌, 商品品种名)** 的哈希 `family_key` 为准（规格/平台不参与；基础编码"马甲"用本体资料识别）；首次申请把族内全部基础编码写入 `product_exclusive_members`，之后改名不丢身份，同族新增规格自动匹配；存在"同指纹不同 key"冲突时报错要求核对资料。
- 发起(`initialize/apply exclusive_submit`)：选基础商品 + 领取理由(≤500) → `reserve`：锁公司 → 族占位 `product_exclusive_slots(pending_run_id)`；**已有有效归属或他人正在申请→拒绝**；退回后重提**不可更换商品**（须撤回重建）。
- 审批(`exclusive_approval`)：审批人选专属期 `periodDays`(1–3650 整数)或明确带时区的 `endsAt`（未来、≤3650天）→ 写 `product_exclusive_grants`(starts_at=NOW, owner=**原申请人**，客户端不能指定领取人, approved_by=审批人) 并清 pending 占位设 `grant_id`。可退回补充 / 拒绝(=废除)；发起人可撤回(释放占位)；管理员可转交审批节点。
- 归属效果：`bundleOwnership` —— 组合 SKU 通过其 BOM 的 **main 行**基础商品继承归属（所有规格/平台/赠品组合；仅作赠品出现不继承；多个不同主商品各自显示）；定价调试显示领取人/期限，"我的专属品"筛选。
- 取消归属：`POST /exclusive/grants/:id/cancel`：领取人/原审批人/管理员，原因必填≤500；写 cancelled_at/by/reason，不删历史，推送结果给领取人和审批人；**到期按服务端时间即时失效，不靠定时任务改状态**；到期/取消后可重新领取，不自动转人。独立"专属品管理"入口：领取人/审批人看自己的，管理员看全公司（≤500）。

### 3.3 采购申请流程（C 引擎，processor 见 2.2）

**默认 15/16 节点图**（`W/business-template.js::purchaseNodes`；生产实例#10 在"采购申请"后又用"添加业务节点"插入了"完善采购方案"，共 16 节点）：
`request(submit)→plan(finance)→approve(approval)→payment→prepayment_review→dispatch→arrival→receive→quality→expense→settlement→[feeDue?]expense_payment→close(system)→[remaining?]dispatch | end`；异常：`quality/receive --exception_to--> exception → (refundNeeded→refund→end | retryShipment→dispatch | 否则→quality)`；`controlRoutes={amend:request, cancel:exception}`。默认时限 60 分钟，收货 120，质检 240；`waitingTiming` 用于 dispatch/arrival（按业务日期催办）。条件路由事实 `remaining/pendingException/retryShipment/refundNeeded/feeDue`。

**发起(新版"需求模式"，模板含 purchase_plan)**：只填 商品(商品档案 finance_products，status normal；原料只能选"马甲品名" rawFinishedNames，不展示本体)、数量(>0，保留 4 位小数)、要求到货日期(明确时区、未来)。**禁止填报价/付款字段**；标题自动生成；单位取商品档案系统计价单位(`purchaseSpecification||systemSpecification||unit`)，档案缺单位不阻止提需求；同一申请不可重复同一本体的多个马甲；`requestKey` 去重。`submitNow=true` 时创建+关闭发起节点+进入下一节点一次完成，否则停在 draft。旧"legacy 模式"（含供应商/报价/付款字段、约定发货/到货时间）仍兼容历史模板。

**每一步（谁做/做什么/校验/落库）**
| 节点 | 处理人(配置) | 本步输入 | 关键校验 | 落库/副作用 |
| --- | --- | --- | --- | --- |
| 采购需求 | 申请人 | lines[productId,quantity,(rawFinishedNameId)], requestedArrivalAt | 商品存在且 normal；原料需选有效马甲；数量>0；日期有效；需求模式拒绝多余字段 | `workflow_business_runs.payload_json` 初始状态 `{requestMode,lines,shipments:[],batches:[],payments:[],fees:[]…}` |
| 完善采购方案 | 配置人(如财务) | supplierId、warehouse、每行 unitPrice、paymentMode(new/existing/mixed)、payeeName、payeeAccount、attachments(选填)、comment | 供应商取自 `finance_shared_archives.suppliers` 且有效；仅允许填单价；单价>0；总额≥0.01；商品计价单位须与申请时一致；已付款后不得换供应商/仓库；已结算商品不得改历史单价 | `planReady=true, approved=false`，写入供应商/收款资料/单价 |
| 老板审核 | 配置人(老板) | comment 选填 | 需求模式须 planReady | `approved=true, approvedAmount=已过账货值+剩余数量×单价`；变更重审则 `paymentReopened=true` |
| 货款安排 | 出纳 | payments[{bankAccountId,amount,payeeName,payeeAccount,reference,attachments}] 和/或 prepayments[{documentId,amount}] | 已批准；金额>0；收款人/账户须与批准资料一致；银行流水号全库唯一；凭证必传(≤12份,png/jpeg/webp/pdf,单份≤3MB,data URL 或 /uploads/)；总额≤批准额度(变更时≤max(批准额,旧额)) | 每笔新付款：生成 `supplier_prepay` 单据→过账(预付款+，银行−)→占用到本采购(`finance_prepayment_allocations`)；已有预付款：只占用同公司同供应商已过账可用余额(账上余额−未释放占用)，不再减资金；上一版挂账草稿 superseded；新建"未到货挂账采购入库草稿"(`purchase_inbound`,draft) |
| 预付款使用确认 | 财务 | comment | 必须已有付款 | `prepaymentReviewed=true` |
| 发货跟进 | 财务/采购 | 未发货：承诺发货时间+跟进说明(走 `/progress`)；已发货：lines(本批数量≤待发)、logisticsNo、attachments、expectedArrivalAt、(shipmentId 续同一发货批次) | 预付款已确认；预计到货晚于要求到货日须写原因；本批数量>0 且 ≤ 可发数量 | 新增 shipment(首次)与 batch；`/progress` 追加 followups，更新实例与待办 due_at 为承诺日期并换用 waitingTiming |
| 到货登记 | 仓库(部门共享) | attachments | 有未过账批次 | batch.arrived=true，**此时才开始收货计时** |
| 收货核对 | 仓库 | lines(实收≤本批发货)、receiptComplete、attachments、comment | 数量差异必须写原因；零实收需明确"本次到货结束"；receiptComplete 时缺失量记 `deliveryShortage` | batch.received；零实收→pendingException |
| 质检 | 仓库 | lines(合格数量≤实收)、attachments、comment | 有不合格必须写说明；无可入库且无待处理异常→要求走换货 | batch.accepted；不合格/未补缺→`pendingException` → 走异常线 |
| 异常处置 | 老板/配置人 | resolution(replace/accept_discount/reinspect/cancel_remaining)、comment、attachments | 折价接收不能处理短缺；reinspect 须有实收；cancel_remaining 需凭证 | replace：记录退回量、关闭缺失量并可能 `retryShipment`；accept_discount：`discountApproval=true`；cancel_remaining：`cancelApproved=true`→进退款 |
| 预付款退款确认 | 出纳 | payments[{documentId,amount,bankAccountId,reference,attachments}] | 须已批准终止；逐笔未使用预付款全额；流水唯一 | 生成 `receipt` 收款单→过账(预付款−，银行+)，`released_amount`+；`cancelledQuantities`=剩余量；取消未到货草稿；`cancelledRemaining=true` |
| 费用申报 | 仓库 | fees[{type freight/handling, amount, payeeName, payeeAccount, attachments}] 或 zeroReason | 须已质检；无费用必须写原因；旧模式还需选分摊方式 | batch.fees（paid=false） |
| 财务结算 | 财务 | offsetAmount、allocationMethod(value/quantity/weight)、(折价时 lines[unitPrice])、comment | 预付款冲抵≤本批货款且本采购可冲抵余额够；折价单价≤批准单价；普通到货不得改单价；挂账草稿必须仍是 draft/unposted | `allocateFees` 分摊（分为单位、尾差归确定明细、合计=批准费用）；草稿改为本批合格明细并 issued→过账：库存+（货值+分摊物流）、预付款−冲抵、应付−（货款−冲抵）、费用应付−；`publishPurchaseCosts` 更新商品 purchasePrice/freight/handling 三项分开存储+成本历史+刷新 BOM 下游成本（受阻时失败要求先重新验证）；剩余数量重建挂账草稿 |
| 费用付款 | 出纳 | payments[{bankAccountId,reference,attachments,amount,feeIds[]}] | 同收款人+账户的费用才可合并一笔付款；金额须=所含费用合计；流水唯一 | 标准 `expense` 单据+过账（应付−、银行−，**不再加成本**）+`finance_expense_vouchers` 展示记录 |
| 批次结算检查(系统) | 系统 | — | 本批已过账且费用全付；成本发布无 blocked | 无剩余数量→释放全部预付款占用；`remaining`→回到发货跟进，否则归档 |

**终止/变更**：见 1.4。变更数量不得低于已入库；已发货在途批次须先处理完；付款后更换供应商/仓库须"终止退款→重新申请"。

**财务落账规则速查（`F/document-posting.js`）**：单据状态 `draft → issued+unposted → posted`，红冲生成反向单据(采购流程不用)；`postDocument` 要求分录**借贷平衡(合计=0)**，科目仅 `bank/prepayment/payable/inventory/expense/opening`，银行余额直接加减；`createDocument/consume/reserve` 全部在调用方事务内；`source_key`、`bank_reference` 保证重试不重复。库存查询=`finance_posting_entries` 里 `inventory` 科目(账号为 `[仓库,商品ID]` JSON) 汇总；期初预付款可由财务人工核实+凭证登记（`/api/finance-posting/documents/:id/opening-prepayment`，借预付款贷"opening"，不动银行余额）。

## 4. 任务中心 / 待办 / 通知的行为

### 4.1 页面与入口（导航 `src/app/navigation.js`）
- **流程**组：`流程中心`(=配置中心 `WorkflowConfigurationCenter`)、`流程总览`(`WorkflowOverview`，只读)、`节点模板`(`NodeTemplateLibrary`)；**任务**组：`任务中心`(`TaskSystem`)，其中有两个页签："日常任务"和"流程申请与待办"(`WorkflowWorkspace`)；运营/岗位工作台也嵌入 `WorkflowWorkspace`/`OperationsWorkspace`。
- 因此员工的"待办"分散在：任务中心·流程申请与待办（真待办）、任务中心·日常任务（周期/手工任务）、各岗位工作台、飞书消息。

### 4.2 "流程申请与待办"（`WorkflowWorkspace`，数据来自 `/api/workflow-center?page=…`，SQL 在 `W/workspace-list.js`）
- 视图：待我处理 / 发起流程 / 我的申请 / 全部流程 /（管理员且 showConfiguration 时）流程配置。每页 20，服务端过滤：view、status、templateId、overdue、keyword（标题/发起人/节点/处理人/模板名）。
- **待办的口径是"按申请单汇总"**：SKU 为一张申请（`todo` = 我名下或我作为共享接收人的未结束规格数），其他为一条实例。点击进入真实业务表单（SKU→`BundleApplicationCenter`，采购→`PurchaseApplicationCenter`，专属→`ExclusiveProductApplication`，legacy→只读记录弹窗）。
- 可见范围：管理员(role_key ∈ admin/company_admin/boss)=本企业全部；其他人=自己发起 | 当前/历史办理 | 共享接收人(含历史) | 业务抄送人。
- "发起流程"卡片：仅 `bundle_application/purchase/product_exclusive` 且 active 且 `canStart` 且 `issues` 为空的模板可发起；其他显示"尚未接入办理表单/未启用/配置待完善"。
- 服务端一次最多统计 500 批量申请/500 普通实例（旧版接口 `truncated`），分页版按 SQL 全量。
- 冗余：每次切换筛选并发 3 个请求（workflow-center + workflow-batches/templates + business-runs/templates）。

### 4.3 流程总览（`W/overview.js`，只读，需求见 docs/流程总览.md）
- 默认纳入：已进入办理(非 draft/completed/cancelled/rejected/skipped)的申请，加"退回待补充"；SKU 有进行中规格才算（草稿+取消不算进行中）。
- 列表字段：当前节点(规格不同节点不合并成虚假节点)、处理人、完成规格数、**当前活动节点最长停留时间**(取活动记录 created_at 最早值，不是申请创建时间)、最早截止时间、发起时间；筛选：关键词/流程类型/发起人所属部门/处理人/状态/仅超时；统计：进行中、退回、超时；每 20 张分页；列表可见时每分钟重读、窗口聚焦重读。
- 详情：只读节点记录（进入/结束时间、实际处理人=`timing_json.handledBy` 优先、动作）；SKU 规格每页 20 并可展开历史。**不读成本快照、付款载荷、表单、审批备注**；仅 GET；详情再校验访问权。

### 4.4 日常任务（`TaskSystem` + `server/index.js` 路由）
- **周期任务模板** `task_templates`：频率 daily/weekly/monthly/yearly/manual；`schedule_key` 保证一周期一次（`daily:YYYY-MM-DD` / `weekly:YYYY-Wnn`(简化周号) / `monthly` / `yearly`）；负责人来源 position/role/responsibility_group/employee（**取第一个匹配成员，无则回退到 fallback/boss**，与流程引擎的"唯一匹配"语义不同）；监督人可自动取直属上级(manager_id)否则 boss；`requires_review`(默认需复核)；`feedback_schema`（预设：通用反馈、客服店铺数量检查、运营日报、手机号畅通检查；字段类型 text/number/amount/date/select/file；file 只是文本框"先填写附件说明，后续接上传组件"）。
- 生成：`POST /task-templates/:id/generate`（可 force）、`/generate-due`（批量，**手动点击触发**，无后台调度器）。手工任务：`POST /task-instances/manual`（标题、负责人、监督人、feedbackTo、severity、dueAt、completionStandard）。
- 状态：pending → in_progress? → (提交)reviewing(需复核)/completed/abnormal → 复核 approved→completed / rejected；overdue 由"扫描超时"手动接口置位。
- 提交 `POST /task-instances/:id/submit`：写 submit_payload、result_note（前端固定写"已按完成标准提交"/"提交结果异常，需要主管复核"）；`abnormal` 创建 `exception_records(type=abnormal_result, severity=important)`；来源是 B/C 引擎的待办→409 "请在申请与待办的业务表单中处理"。
- 复核 `/review`：`actorId`、decision approved|rejected、comment；必须是 `task.supervisor_id`。
- **延期申请 delay_requests**：目标 task_instance 或 workflow_instance；审批人=任务监督人(或 boss)/节点 supervisor；`decide` 通过后改 `due_at`（任务从 overdue→pending）。
- **扫描超时** `/api/supervision/scan-overdue`（按钮触发，非定时）：把 pending/in_progress/submitted/reviewing 且过期的任务置 overdue，并为没有开放 overdue 异常的任务创建 `exception_records(type=overdue, severity=urgent, escalated_level=2)`。
- 页面分桶：今日/明日/7日内/30日内待办（只含 pending/in_progress/rejected；**overdue 不在任何桶内**，仅在指标"已超时"）。

### 4.5 站内通知
- `GET /api/notifications` 与 `/api/bootstrap`：读 `notifications` 表，**按公司而非按员工过滤**，顶栏"通知 N"展示最近 10/30 条，含他人姓名与正文。**代码里没有任何地方向 `notifications` 插入数据，也没有"标记已读"接口**——站内铃铛实质是死功能（docs 也说"不新增站内通知铃铛"）。

### 4.6 飞书通知（`I/feishu.js` + `I/feishu-channels.js`）
- **六个飞书企业自建应用(机器人)**：流程助手 flow / 任务助手 task / 督促助手 supervision / 通知助手 notice / 经营助手 business / 系统助手 system；员工只通过**流程助手**授权绑定一次（OAuth，单次 state + HttpOnly Cookie，企业 tenant_key 首次由管理员确认，不存令牌，不取手机号/邮箱）；其他应用用 `union_id` 发送（open_id 为应用专属不可复用）；绑定表 `oa_feishu_bindings`，禁止手填他人飞书 ID/按姓名猜。
- **队列**：新通道统一写 `oa_feishu_messages`(`company+channel+employee+event_key` 唯一=去重，`group_id` 合并，`attempts`≤6，`lease_until`，`next_at` 5 分钟重试)；SKU 待办沿用旧 `oa_feishu_outbox`(`task_id` 唯一)；后台 10 秒一轮发送，15 秒合并窗口（同申请+节点+人的多个规格合成一张卡片"SKU 申请待处理 N 个规格"）；发送前**重新校验**：绑定/配置仍有效、待办仍 active、员工在职、仍是当前处理人或共享接收人，否则标记 cancelled/已失效；失败不阻断业务事务；未绑定仍有站内待办。
- 事件与通道：
  - 流程助手：SKU 节点待办（outbox，事务内入队）、SKU 终审通过（`sku_approved`，给申请人，不含成本、不代表聚水潭同步成功）、采购/专属 `business_assigned`(新待办)、`business_result`(完成/废除/退回/撤回/收尾完成/专属取消)、`business_cc`(抄送)；通用引擎生成的 task_instances（排除 batch/business 防重复）。
  - 任务助手：独立任务分配(`task_new`，workflow_instance_id IS NULL)、任务待复核(`task_review`，含提交版本去重)。
  - 督促助手：节点时效提醒(`node_timing:{taskId}:{dueVersion}:{stage}`，stage=`before:N`/`overdue:N`；离线者只保留当前有效阶段)、业务超时升级(`business_escalation`)、三级策略升级(`timeout_escalation`)、已存在的异常事项(`exception`)、普通任务逾期(`due_task`，排除已被节点时效/三级策略覆盖的)。
  - 通知助手：站内 notifications 行与非流程任务完成告知；经营助手：真实成本变更(不传数字)；系统助手：同步失败/接口授权到期/采购记账失败（`business_failure`，发给提交人+配置的系统告警接收人）。
  - 首次启用通道记录 `source_floor_json` 基线，历史事项不补发。
- 卡片只含申请/节点标题、提醒阶段、期限、OA 链接(`/?skuApplication=<batchId>` 或 `/?businessApplication=<runId>`)；点击后 OA 重新校验登录与处理权。
- 现有飞书 `test` 接口仅向管理员本人发文本；旧的演示成功逻辑已移除。

## 5. 节点时效与超时（重写需要的完整规则）

### 5.1 三层模型（互相独立、常被混淆）
1. **节点提醒 `timing`**（给"当前处理人"，督促助手）：`{enabled,beforeMinutes[≤5,必须<时限],overdueEveryMinutes(1–1440)}`；SKU 仓库/财务、采购内部节点、专属节点默认 `[20,10]`+每 5 分钟。
2. **三级超时策略 `workflow_timeout_policies`**（公司默认 template_id=0,node_key=''；流程；节点，按"通知"和"处罚"两段分别继承）：
   - 通知：`supervisorAfterMinutes`(默认15) / `bossAfterMinutes`(默认30，不得早于主管)；接收人 = 经办人直属主管 (`manager_id`)/指定员工，老板 = role 'boss'/指定员工；每级一次；找不到接收人写 `unresolved` 记录。**默认 enabled=false**。
   - 处罚：`mode` fixed/repeat/tiers、`unit` task/node/batch(同批次同节点同责任人计一次)、阈值/金额/累计/封顶；金额只"计算"，写 `workflow_timeout_penalties(pending)`，**财务需在台账人工确认/豁免（原因必填，金额≤计算额）**，不自动扣款。**只有节点有单一指定责任人(owner_id==assignee)时才计罚，部门共享不计个人**。默认 enabled=false。
   - 台账 `workflow_timeout_incidents`(按 `task_id+due_version` 唯一，状态 open/closed/extended/cancelled)、`workflow_timeout_escalations`、`workflow_timeout_policy_events`(审计)。
3. **业务级升级 `notifications.escalations`**（仅 C 引擎节点配置）：见 1.4。

### 5.2 计时语义
- **以进入当前节点的服务器时间计时，自然时间，不排除非工作时间**；`workflow_instances.due_at = NOW + due_hours(分钟)`，待办 due_at 取实例 due_at；部门多人共享同一截止，任一人提交关闭所有待办；退回后再次进入=新记录/新待办/新截止。
- 配置变更**只影响之后进入的节点**；进入时把 `timing` + `timeoutPolicy` 快照写入 `workflow_node_records.timing_json`；已运行的时钟不重置，已进入旧环节不补发提醒。
- 业务日期型 `waitingTiming`（采购 dispatch/arrival）：截止=业务字段 `deadlineField`（到货登记用 `expectedArrivalAt`；发货跟进登记承诺日期后换成承诺日期），默认到期满 **5 分钟**首次提醒，之后每 **1440 分钟(每天)**；财务首次接手发货任务按 60 分钟处理。
- 阶段计算 `timingStage(remaining)`：剩余>0 且 ≤ 某 beforeMinute → `before:N`（取满足的最小值）；已超时：有 `overdueFirstMinutes` 则从该分钟起每 `overdueEveryMinutes` 一档，否则第 k 个间隔 `overdue:k*every`。事件键 `node_timing:{taskId}:{dueVersion}:{stage}` 唯一→重复扫描不重复入队。

### 5.3 后台工作器
- 提醒发布：督促通道候选扫描时执行（随 `feishuService.start()` 每 10 秒 tick 触发 channelWorker）。
- 超时策略扫描 `timeout-worker.js`：每 **30 秒**；找 `timing_json.timeoutPolicy` 存在且 `due_at<NOW()` 的待办（含已完成但超时的，补记 closed 事件）；事务内 `FOR UPDATE` 重算；延期(due_version 变化)→旧 incident 置 `extended`；已结束的 incident 关闭并**取消仍 pending 的升级消息**；每个级别每个事件只升级一次。
- 非精确闹钟：网络/队列拥堵可延迟。

### 5.4 未解决/空白
- 无"节假日/工作时间"概念；无 SLA 暂停；任务中心周期任务无后台调度（靠手动按钮）；无统一"催办"手工按钮（文档提过"人工催办"通道但无 UI）。

## 7. 现有 UI / 操作逻辑 / 实现上的问题（具体到文件/现象）

### 7.1 架构与数据
1. **三套引擎+遗留表并存**：`server/index.js` 约 13000 行，旧通用引擎(A)仍在（`completeWorkflowNodeRecord`、`/workflow-instances/:id/advance`、`/workflows/expense|approve`），但无前端入口；设计器可建 `related_object_type='business'` 的通用流程，却**无法发起**（`WorkflowWorkspace` 显示"尚未接入办理表单"）。重写应只保留"模板→业务适配器→统一运行时"一套。
2. **配置全塞 JSON**：`workflow_template_nodes.form_schema` 同时放办理器、模板快照、处理人、提醒、抄送、升级、路由、控制路由；`due_hours` 名称与单位(分钟)不符；`timing/timeoutPolicy/notifications/assignmentSource/handledBy` 全挤在 `timing_json`。难以查询与演进。
3. **一个待办一个接收人一行**，部门共享 N 行 + `workflow_node_recipients` 又存一份，需要 `recipientPredicateSql` 复杂 EXISTS 反复拼接；待办口径又被"按申请汇总"，用户看到的"待办数"≠ task_instances 行数。
4. **SQL 极重**：`workspace-list.js/overview.js` 用 UNION + 多层子查询 + GROUP_CONCAT 计算汇总；`business-runs.js GET /:id` 每次拉全部记录、节点、命令、文档；设计器列表用 5 个独立请求（`WorkflowConfigurationCenter.load`）。
5. **附件**：凭证以 base64 data URL（单份≤3MB、每节点≤12份）直接放入 `payload_json`，会让 run payload 膨胀并随接口返回（`purchase-adapter.js::evidence`）。
6. **模板快照与实时配置混用**：路径用快照、人员用实时、processor 变更则失败（"节点配置已变化"），导致配置变更时进行中的申请可能无法前进；SKU 已有申请后改结构需复制模板，运营心智负担大。
7. **`PUT /workflow-designer/templates/:id/nodes` 校验失败仍保存**（`server/index.js` ~11536），只在响应里带 errors；启用只能通过各业务路由，`/designer/.../status` 仅允许 `inactive`。启用前检查分散在三个 `validate*`。
8. 设计器前端 `WorkflowDesigner.jsx` 2017 行，字段选项列表与 `shared/workflow-node-catalog.json` 重复维护且不一致（缺 `exclusiveForm`），节点类型常量在前端硬编码。

### 7.2 权限 / 安全（应在重写时作为必须修复项）
1. `POST /api/task-instances/:id/submit` **不校验提交人是否负责人**；`/review`、`/delay-requests`、`/delay-requests/:id/decide` **以请求体里的 `actorId/requesterId` 为准**（前端传 `task.supervisor_id` 等），可被伪造；`/api/workflow-instances/:id/node-records/:recordId/complete` 与 `/advance` **不校验当前处理人**（`completeWorkflowNodeRecord` 无资格检查）。
2. `GET /api/process-center`（任务中心数据源）返回**整个公司**最近 200 条 task_instances、全部任务模板、`supervision_rules`（无 company_id 隔离）、异常、延期申请、业务事件，**不按当前员工过滤**；前端再自行过滤"我的"。普通员工能看到全部人的任务。
3. `GET /api/notifications` / bootstrap 通知**不按员工过滤**，展示他人姓名与内容；`/api/tasks` 读遗留 `tasks` 表且仅按公司过滤；`/tasks/:id/complete` 用 `query` 执行 UPDATE 且不校验人。
4. SKU 发起（`POST /api/workflow-batches`）**未使用模板的发起范围**（`canStartWorkflow` 仅采购/专属使用）。
5. `delay_requests` 的审批人固定为监督人/节点 supervisor，未检查请求人是否为任务负责人；延期通过会直接改 `due_at`，**不重置/不记录提醒版本**（与时效模块的 `due_version` 约定仅靠 UNIX_TIMESTAMP 巧合衔接）。
6. 旧引擎的 `resolveAssignee` 在找不到人时静默回退到发起人/ID=1 员工（可能把审批派给错误的人），与新引擎的"严格唯一匹配"相反。

### 7.3 交互与易用性（页面/现象）
1. **入口分散且命名混乱**：同一件事出现在"流程中心(配置)"、"任务中心→流程申请与待办(待办)"、"运营工作台/岗位工作台(嵌入)"、"流程总览"、"节点模板"。`docs/流程中心重规划.md` 把"待我处理/发起/我的申请"定义在"流程中心"，实际落在"任务中心"页签里（`WorkflowCenterPages.jsx::TaskSystem` 第一行就是 workspace 切换）；而"流程中心"点开是配置目录。用户要在"任务"菜单里找"流程"。
2. **任务中心页面信息过载且含演示默认值**：`TaskSystem` 同屏 5 个指标 + 4 个分桶 + 周期模板表 + 手工任务表单 + 弹窗；手工任务表单预填"临时检查店铺资料完整性"、默认负责人=员工列表第 1/2 位（`firstEmployeeId/secondEmployeeId`），新建周期模板默认"每日客服店铺数量检查"——违背 docs 中"不再提供预设人员演示"的要求；`file` 字段只是文本框；提交时结果说明被前端写死。
3. **逾期任务不在"待办"桶**：`pendingStatuses=['pending','in_progress','rejected']`，最需要处理的 overdue/returned 反而不进今日/明日桶；`reviewing/abnormal` 只在指标里。
4. **手动按钮代替调度**："生成今日周期任务""扫描超时并生成异常"是人工按钮，无自动执行；容易漏。
5. **SKU 申请弹窗是一个巨型 Modal**（`BundleApplicationCenter.jsx` 68KB / 单组件上百个 useState）：申请列表、详情、新建、编辑器、重复确认、复用选择、批量套用、删除确认均在一个模态里；跨规格批量操作靠"勾选+先校验+再提交"的三段式（`check`→`action`），结果需手动对照 `results`；失败行保留选中。`发起流程`、`历史申请` 入口与"新建"弹窗互相跳转。
6. 新建 SKU 第一步"必须先搜索"但搜索结果**既不阻止也不必选**，纯粹增加一步（用户已确认，但属于冗余交互）；重复判断语义分散在三处（编码冲突/主商品相同/已有SKU二次确认），文案与阻断强度不同，用户难以理解。
7. **配置页复杂度**：`WorkflowConfigurationCenter` 一行内混杂 处理人来源/时限/提醒两档提前/间隔/抄送(`<select multiple>`)/升级/业务日期催办；三套"超时"配置（节点 timing、三级策略、节点 escalations）UI 在不同位置，且**同时开启时语义需要靠后端 `enabled=false` 判断规避重复**，管理员无法直观知道最终谁会收到什么。
8. 部门共享的处理人在列表只显示"部门名 · 全员共享"，看不到具体谁已看过/处理；任一人处理后其他人待办直接消失，没有"已被XXX处理"的提示。
9. 采购表单需切换"采购资料/办理"页签，流程轴为常驻横向长线；步骤多(15+)时信息密度高；`PurchaseFlowProgress` 说明"后续人员可能随配置调整"，但仍展示为确定的人名。
10. 站内通知铃铛无数据来源/已读（见 4.5）；顶栏同时有"飞书绑定提示 FeishuNotice"与铃铛，两个通知体系各自为政。
11. 加载策略：`WorkflowWorkspace` 每次筛选并发 3 个请求；总览 60 秒轮询+聚焦刷新；配置页一次拉 5 个接口——没有统一的缓存/失效机制。
12. 文案与状态词不一致：docs 要求"废除/拒绝"统一话术，但数据库状态仍为 `cancelled/rejected`、事件类型为 `cancel`，流程总览/设计器里"驳回线/退回线/拒绝"混用；`workflowStatus` 同时有 `rejected(已驳回)` 与"拒绝并废除→cancelled"，用户看到的"已废除"可能其实是被拒绝。

### 7.4 文档与代码不一致（重写时以真实运行逻辑为准，需向业务确认）
1. docs/SKU批量申请流程.md 写"审批完成不自动同步聚水潭，外部同步走人工确认入口"，而 `bundle-application.js::finalize` 在终审事务内 `bundleSyncService.enqueue(...)` **入队同步**（"existing worker uploads after commit"）。飞书文档又强调"审核通过不代表聚水潭同步成功"。
2. docs/SKU批量申请流程.md 称"沿用现有工作流交接"，B 引擎无转交接口；仅 C 引擎有管理员转交。
3. docs/飞书通知接入.md 称"不新增站内通知铃铛"，前端顶栏已存在铃铛但无数据源。
4. docs/流程中心重规划.md（历史稿）与 docs/业务模板配置中心.md 对"流程中心首页是什么"互相矛盾，后者说以其为准，但页面行为仍是前者的"待我处理/发起/我的申请/全部流程"工作台挂在任务中心。
5. 文档写"员工仅能查看自己发起或参与过的申请"，而 `/api/process-center` 实际返回全公司任务（见 7.2）。

## 8. 重写建议（可直接据此设计）

1. **一个运行时**：`flow_definition(版本化、发布后不可变) → flow_run → run_step(进入一次一行) → work_item(每个有效接收人一行或共享一行+接收集合) → event`；业务通过"适配器"注册字段、校验、动作与事实，不再出现 `graph_status` 三态与遗留表。
2. **批量单据**：保留"一个申请单、N 个独立流转的明细(item)"模型，明细拥有独立 revision/状态/步骤/待办/截止；申请单状态为聚合视图。
3. **处理人**：保留"进入节点解析、唯一匹配、部门共享冻结名单、停用/调岗即时失效、绝不静默兜底管理员"；增加"解析失败→进入 blocked 状态并提醒管理员"而不是让前一节点提交失败；补上 SKU 的转交/抄送。
4. **四基础操作** pass/return/cancel/reject 作为引擎内建，业务适配器声明"某步可否退回/废除及收尾路径"（采购的受控收尾必须保留）。
5. **时效**：单一模型（节点级 SLA：时限、提前提醒、超时重复、升级链 [主管/老板/指定人]、处罚(待确认台账)），进入节点时快照；统一的调度器（秒级精度不必需，30–60 秒轮询即可）；延期审批必须递增 due_version 并让提醒/台账自然失效。
6. **待办视图**：以"我的 work_item"为第一等公民（含逾期、退回、被抄送），申请汇总视图作为派生；任务中心与流程待办合并为一个"我的待办"；周期任务由后台调度生成。
7. **通知**：事件→模板→通道（站内、飞书各应用）的统一队列；站内通知落库、按员工隔离、可已读；飞书沿用 union_id/合并/发送前复核/去重键/失败不阻断。
8. **权限**：所有任务/流程读写均以服务端会话身份判定（禁止信任请求体 actorId）；成本/价格字段统一做服务端脱敏（现有"键名含 cost|price 就剔除"的做法可以保留但应改为显式字段级权限）。
9. **附件**：独立文件存储，payload 只存引用。
10. **保留的业务规则清单**：见第 3 节各步骤的"校验"列、第 1.5 节不变量、第 5 节计时语义、财务过账规则（借贷平衡、source_key/流水号幂等、预付款占用/消耗/释放、成本三项分离存储与下游刷新）、SKU 查重三层与"已有SKU二次确认令牌"、专属品族身份与即时到期规则。
